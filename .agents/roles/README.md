# Rattle 역할 지침 (2026-11-17 사용자 검토 완료)

Orca에서 Codex 작업자를 띄울 때 과제와 함께 넘기는 역할별 지침이다. 진입점은 루트 `AGENTS.md`이며, 이 폴더는 그 규칙을 넓히지 않는다. 역할의 책임 원문은 `docs/에이전트-협업-기술참고.md`의 「역할과 산출물」이다.

| 파일 | 역할 | 쓰기 여부 |
|---|---|---|
| `pm.md` | 기획자 (PM) | `docs/` 명세 |
| `designer.md` | 웹/앱 디자이너 — 시안을 만든다 | `docs/design/`, `dev/` 시안 |
| `ux-reviewer.md` | UI-UX 디자이너 — 만든 것을 검토한다 | 읽기 전용 |
| `backend.md` | 백엔드 개발자 | `lib/services/`, `supabase/functions/` |
| `frontend.md` | 프론트엔드(앱) 개발자 | `app/`, `lib/hooks/`, `lib/components/` |
| `dba.md` | DBA | `supabase/migrations/`, SQL 검증 스크립트 |
| `security.md` | 보안 전문가 | 읽기 전용 |
| `qa.md` | QA 전문가 | `__tests__/`, QA 기록 |
| `ux-writing.md` | 앱 화면 문구 기준 (역할 아님, 문구를 쓰거나 검토하는 모든 역할이 따른다) | — |

**디자인 짝 규칙 (2026-11-17 사용자 지시):** 디자이너가 시안 과제를 마치면, 사용자에게 보여주기 전에 UI-UX 검토자(`ux-reviewer.md`)가 같은 시안을 검토하고, 디자이너가 그 소견을 반영하거나 반영하지 않은 이유를 적은 뒤 사용자에게 올린다. 사용자 확정과 충돌하는 제안은 사용자에게 먼저 묻는다.

**짝 작업자 직접 소통 (2026-11-17 사용자 지시):** 작성자와 검토자가 서로 피드백을 주고받아야 하면 둘이 짝 파일로 이어서 주고받고, 조정자는 내용을 바꾸지 않고 중계만 한다. 최대 5번(보내기 기준, 두 사람 합계)까지만 한다.
- 조정자가 짝 파일(`/tmp/rattle-pair-<주제>.json`)을 만들어 준다: `{"topic","limit":5,"count":0,"members":{"<역할>":"<현재 dispatch id>"},"log":[]}`.
- 과제를 시작하면 자기 항목의 dispatch id 를 지금 값으로 고친다(새 과제마다 dispatch id 가 바뀐다).
- 상대에게 넘길 때: count 를 1 올리고 log 에 한 줄 요약을 남긴 뒤, worker_done 보고에 '<역할>에게 보낼 요청'(요청·근거·파일 경로)을 적는다. Orca 는 작업자끼리 직접 dispatch 로 보내는 것을 막으므로(2026-11-17 확인: task_not_found / coordinator or originating worker required) 조정자가 그 요청을 손대지 않고 그대로 상대에게 중계한다.
- count 가 5에 닿았거나 더 주고받을 것이 없으면 상대에게 보내지 않고, worker_done 보고에 '짝 소통 종료(n/5)'와 남은 이견을 적는다. 사용자 확정과 충돌하는 이견은 조정자에게 넘긴다.

조정자(PL)는 작업자를 띄운 세션이다. 범위·파일 소유·통합 순서·최종 보고를 맡는다.

## 작업자 배정과 운영 (2026-11-19 사용자 확정)

이 절이 2026-11-17의 "작업자 medium 고정" 운영 메모를 대체한다. 이 지침의 기준본은 Git에 커밋된 이 파일이며, 조정자는 과제마다 작업자가 읽을 **기준 커밋**을 과제 파일에 적는다.

| 작업 종류 | 모델 / 추론 강도 |
|---|---|
| 일반 구현, 자료 분류, 문서 정리, 확정 UI 구현, 디자인 시안, UX 문구, 정해진 시나리오의 기기 QA | `gpt-6.1-sol` / medium |
| 여러 데이터를 연계하는 백엔드·DBA 구현(근태·급여 등), 여러 정책을 조율하는 PM 기획, 계정·매장 전환·지연 응답 등 상태가 복잡한 프론트 구현 | `gpt-6.2-astra` / medium |
| 독립 검토 — 일반 코드·UI·UX | `gpt-6.1-sol` / high |
| 독립 검토 — 급여·근태 계산, DB 마이그레이션, 보안·접근 권한, 잠금·재시도 | `gpt-6.2-astra` / high |

- 다음 근태·급여 연동 과제는 구현 `gpt-6.2-astra` medium + 독립 검토 `gpt-6.2-astra` high.
- 같은 수정이 반복되거나 원인 구분이 어려운 진단은 그 진단만 high로 올린다.
- 효과 기록: 과제마다 첫 검토에서 발견·재현한 결함, 재검토에서 새로 발견한 결함, 수정 왕복 횟수, 소요 시간을 기능 대표 기록에 남긴다.

**기능 대표 기록:** 기능마다 기존 대표 문서 하나(예: QR 출퇴근은 `docs/QR-출퇴근-설계안-2026-11-16.md`의 「릴리스 상태」 절)에 대상 커밋·미해결 지적·실기기 검증·DB 적용·main 반영·다음 담당자를 모은다. 새 문서를 만들지 않는다.

**수정·재검토 연속성:** 같은 변경의 수정과 재검토는 처음의 구현자·독립 검토자 역할과 모델로 이어간다. 후속 과제 제목에 `<기능> · 검토 N회차`를 넣고, 본문에 이전 지적 ID·대상 커밋 범위를 적는다.

**실기기 QA:** 로그인·매장·유효한 QR 표시·카메라 준비를 조정자/QA가 먼저 끝낸 뒤 사용자에게 필요한 조작만 한 번에 요청한다. 시간 제한 있는 QR은 사용자가 준비됐다고 한 직후 발급한다.

**릴리스 직전 대조:** 승인된 브랜치·커밋, DB 환경(개발/운영 프로젝트), 배포 채널(EAS preview/production, runtimeVersion)을 실제 대상과 대조해 기록한 뒤 배포한다.

## 화면 설계·검증 기본 순서 (2026-11-20 사용자 확정)

- 화면을 새로 만들거나 크게 바꾸는 작업은 사용자가 말하지 않아도 **시안 → UI-UX 검토 → 사용자 시안 확인 → 구현** 순서다. 디자이너·프론트·검토자는 [design-playbook.md](design-playbook.md)를 먼저 읽고 첫 시안부터 반영한다.
- 구현 완료 기준: 단위 테스트에 더해 **시뮬레이터 빌드 앱에서 실제 흐름을 끝까지 눌러 본 녹화/스크린샷**. 이 증거 없이 실기기 설치·사용자 확인을 요청하지 않는다.
- 사용자에게 요청하는 확인은 '시안 확인'과 '최종 앱 확인' 두 번으로 한정한다.

## 컨텍스트 관리와 사실 확인 (2026-11-20 사용자 요청: 할루시네이션 방지)

- **과제가 바뀌면 새 세션**: 관련 없는 다음 과제를 기존 탭에 이어 붙이지 않고 새 작업자로 띄운다(스펙에 기준 커밋·근거 파일을 적는다). 같은 변경의 수정·재검토 왕복만 같은 탭을 유지한다.
- 작업자 보드(http://127.0.0.1:8799/)는 컨텍스트 사용률을 **표시만** 한다(자동 `/compact` 끔). 같은 변경 왕복 중 70% 이상이면 과제 경계에서 한 번 `/compact`를 고려하고, **85% 이상이면 현재 과제가 끝날 때 교체**: 작업자가 `/tmp/rattle-handoff-<역할>.md`(기준 커밋·결정·미해결·다음 단계·근거 파일 경로, 추측 금지)를 쓰고 탭을 닫은 뒤 같은 역할 새 작업자가 인수 파일을 읽는다.
- 모든 작업자는 정리·교체 직후와 보고 전에 **기억이 아니라 저장소·커밋·DB 조회로 사실을 다시 확인**한다. 커밋 해시·파일:줄·명령 출력이 없는 주장은 '추정'으로 표시한다.
- 조정자는 작업자 탭 이름을 `역할 이모지 + 역할명`(예: 🛠 백엔드)으로 붙이고 `~/.local/share/rattle-worker-board/roles.json`에 같은 이름과 담당 범위를 기록한다.

## 모든 역할 공통

1. **시작:** 작업 경로, `git status --short`, 브랜치, HEAD를 확인한다. 루트 `AGENTS.md`와 수정 대상 폴더의 `AGENTS.md`, 과제에 적힌 근거 문서를 읽는다.
2. **범위:** 과제에 적힌 "수정 허용 파일"만 고친다. 그 밖의 파일을 고쳐야 하면 고치지 말고 조정자에게 묻는다. 다른 작업자의 미커밋·미추적 파일을 덮어쓰거나 정리하지 않는다.
3. **공유 파일:** `types/index.ts`, `lib/contexts/AuthContext.tsx`, `lib/query/`, 공통 토큰, `package.json`·lockfile, `AGENTS.md`는 과제에 소유자로 지정된 경우에만 고친다.
4. **하지 않는 것:** push·merge·PR 생성, 원격 Supabase SQL 적용·운영 데이터 변경, EAS 발행, 실제 직원 초대·알림 발송, 스킬·패키지 설치, 비밀값 출력. 필요하면 조정자에게 요청한다.
5. **기기:** 시뮬레이터·실기기 조작은 과제에서 조작 담당으로 지정된 역할만 한다. 다른 입력이 보이면 멈추고 보고한다.
6. **구분:** 확인한 사실, 사용자 확정 결정, 추정, 확인 대기를 나눠 적는다. 실행하지 않은 검증을 통과로 적지 않는다.
7. **질문:** 제품 의도·정책이 불분명하면 임의로 정하지 않고 조정자에게 묻는다.
