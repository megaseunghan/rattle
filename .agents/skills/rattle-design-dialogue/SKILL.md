# Rattle 디자인 대화

Rattle의 사용자가 실제로 보고 눌러 결정하도록 돕는다. **현재 화면 확인 → 필요한 질문 하나 → 실제 시안 → 선택한 부분 고정 → 해당 부분 수정·검증 → 마무리**를 기본 흐름으로 삼되, 이미 답한 질문이나 충분한 요구사항이 있으면 바로 작업한다.

## 범위와 시작점

- 현재 Rattle 체크아웃·워크트리를 확인하고 `AGENTS.md`, `README.md`, `DESIGN.md`, 대상 화면·토큰·관련 명세부터 읽는다. 미커밋 작업을 보존하고 다른 작업소의 구현이나 자료가 전달됐다고 가정하지 않는다.
- 과거 취향보다 **현재 요청과 현재 코드**를 출발점으로 삼는다. 사용자가 이번 시안의 특정 디자인 규칙을 재검토하도록 허용하면 그 범위만 열어둔다. 이전 결정을 다른 화면의 고정 취향으로 확대하지 않는다.
- 작업 시작 때 대상 화면/기능 ID, 수정할 파일, 시안인지 앱 구현인지, 보존할 기능·권한을 짧게 명시한다. 단일 카드 요청을 전체 앱 개편으로 확장하지 않는다.
- 디자인 방향·구조·컴포넌트 목소리와 AI Slop 검토에는 프로젝트의 `../hallmark/SKILL.md` 및 필요한 참조만 함께 적용한다. 없으면 부재를 알리고 자체 검토로 진행하며 자동 설치하거나 Hallmark 실행 완료라고 주장하지 않는다.
- Nielsen H1~H10은 [검토 기준](references/review-and-handoff.md)을 적용한다. 저장소의 `docs/UIUX-휴리스틱-전체화면-검토-2026-10-30.md`가 있으면 원칙과 대상 ID를 참고하되, 과거 문제·통과 기록은 현재 근거로 재확인한다.

## 질문과 답변

- 기본은 **한 번에 한 가지 결정**이다. 첫 질문이 필요한 경우 범위·사용 목적처럼 결과를 크게 바꾸는 것부터 묻는다. 큰 설문이나 기능·색·모션·배치를 한꺼번에 묻지 않는다.
- 질문은 화면에서 구분 가능한 말로 쓴다. 예: “금액창은 누른 지점 근처를 따라갈까, 왼쪽 위에 고정할까?” 전문 용어를 사용자가 알아야 답할 수 있게 만들지 않는다.
- 사용자가 “감이 안 잡혀”, “여러 개 보여줘”라고 하면 추상적 설명 대신 보통 2~4개의 **작동하는** 대안을 만든다. 개수보다 실제 차이가 중요하다.
- 수정 요청은 합리적으로 바로 반영한다. 모호함이 작으면 해석을 한 문장으로 알리고 진행한다. 대상을 잘못 바꾸거나 권한·데이터 의미가 달라질 만큼 모호하면 그 부분만 묻는다.
- 맥락상 명확한 `ㅇㅇ`, `굿`, 숫자 선택은 직전 질문에 대한 답으로 해석한다. 의미가 불분명한 입력을 중대한 정책·배포 승인으로 간주하지 않는다. 새 메시지로 선택이 바뀌면 최신 선택을 반영한다.
- 진행 중 응답은 짧게 **“완료/확정: 실제 바뀐 내용” + “다음 질문: 남은 디자인 결정 하나”**로 쓴다. 사용자가 다른 행동을 요청하면 그 요청을 먼저 처리한다.
- “다음”은 사용자가 해야 할 실행 절차가 아니라 **현재 디자인에 관해 필요한 다음 질문**이다. 다만 질문을 만들기 위해 이미 승인한 모서리·색·정렬을 다시 열지 않는다.
- 사용자가 더 바꿀 것이 없다고 하면 마무리한다. 마지막 확인을 반복하거나 중요하지 않은 질문을 끝없이 추가하지 않는다. 다음 질문이 없어도 된다.

## 시안과 선택 고정

- 시안 요청은 기존 앱 로직과 분리된, 실제 열리는 미리보기에서 진행한다. 가상 금액·날짜·성공/실패 상태는 시안 검토 도구 영역에 표시하고 실제 기록이나 네트워크 응답이라고 설명하지 않는다.
- 동일한 데이터·모바일 폭·주변 맥락에서 대안을 비교한다. 사용자가 숫자 속도만 요청하면 배치·색·칩 형태까지 함께 바꾸지 않는다.
- 선택한 부분은 고정하고 다음 비교는 미정인 축만 바꾼다. 선택 확정 후 불필요해진 비교 컨트롤은 미리보기에서 정리한다. 이는 다른 파일이나 기존 앱 화면을 삭제할 권한이 아니다.
- 문구·범례·장식은 실제 판단에 필요한 만큼만 둔다. 구현 설명·샘플 상태 선택·시안 이름은 앱 UI 안에 섞지 않는다.
- 미리보기 파일과 함께 **하나의 `design-state.md`**를 유지한다. 중요한 결정 시 갱신하고 여러 개의 일지로 분산하지 않는다. 아래 내용을 짧게 기록한다.
  - 대상 화면/기능 ID, 소스 경로·브랜치·커밋 및 관련 미커밋 변경
  - 시안 파일·실제로 접근 가능한 링크와 실행 방법
  - 확정한 선택, 아직 결정하지 않은 내용, 바꿔도 되는 범위
  - 샘플 데이터/미구현 기능, 검증 환경·결과, 실제 앱 반영 여부
- 임시 경로는 임시임을 표시한다. 인수인계 시 사용자가 허용한 프로젝트 산출물 위치에 시안·토큰·필수 자산·결정 파일을 보존한다. 비공개 자료와 세션을 복제하지 않으며, 기존 앱 코드나 전역 디자인 기준을 시안 선택만으로 덮어쓰지 않는다.

## 모바일과 검증

- Rattle은 모바일 기준이다. 기본 375 논리 폭, 320·375·414에서 가독성·터치·여백을 확인하고 768 확장도 확인한다. 네이티브 pt, 웹 CSS px, 물리 픽셀을 구분한다.
- 주요 터치 영역은 최소 44 논리 단위로 유지한다. 더 조밀하게 만들 때 글자·금액·터치 영역부터 줄이지 않는다. 안전영역·키보드·스크롤·글자 확대도 관련 범위에서 확인한다.
- 기능과 데이터 의미가 필요한 경우 [검토 기준](references/review-and-handoff.md)을 읽는다. 최초 로딩, 실제 빈 상태, 0원, 미확인 값, 최초 실패, 기존 자료를 남기는 갱신·실패를 구분한다.
- 실제 브라우저에서 해당 변형을 렌더링한 뒤 보여준다. 새 모션은 중간 프레임과 완료 시점, 빠른 재선택·취소·최신 값, 동작 줄이기를 확인한다. 그래프 제스처는 좌우 끝과 팝오버 잘림·스크롤 충돌도 확인한다.
- 작은 문구·색 수정에 전체 검사를 매번 반복하지 않는다. 변경 영향에 맞는 검사 후, 확정 시 관련 상태·교차 흐름을 회귀 확인한다. 실행 못 한 부분은 미검증으로 남긴다.
- AI Slop 감사 요청은 우선 읽기 검토로 수행한다. 반복 문구·장식·의미 없는 여백·불필요한 모션과 **실제 가독성/동작 결함**, 사용자 취향을 구분해 설명한다. 자동으로 승인된 취향을 뒤집지 않는다. 수정 요청이나 기존 수정 권한이 있으면 해당 범위만 고친다.
- 자체 검토와 독립 검토, 정적 검사와 브라우저, 시뮬레이터·실기기·원격 데이터 검증을 구분한다. 적용/해당 없음/미검증 근거 없이 “전부 통과”, “AI Slop 0”, “앱 검증 완료”라고 쓰지 않는다.

## 완료와 앱 구현 경계

- 선택이 고정되고 관련 상태·접근성·모바일·모션 검증과 필요한 감사가 끝나면 **시안 확정**으로 마무리한다. 결과 링크, 핵심 결정, 검증 범위, 남은 실제 데이터·네이티브 차이를 짧게 남긴다.
- 시안 승인이나 “이걸로 할게”는 실제 앱 구현·원격 DB 변경·push·배포 승인이 아니다. 반대로 사용자가 이미 앱 구현까지 요청했다면 이 스킬 때문에 같은 권한을 다시 묻지 않는다.
- 실제 구현은 승인된 범위와 저장소 지침에 따라 진행한다. 웹 시안은 Expo/React Native를 대체하지 않으며 기존 서비스·계산·권한·라우트·공통 토큰 소유권을 보존한다.
- 네이티브 진동, 실제 기기 스크롤·키보드, JWT/RLS, 실제 데이터 조회·재시도는 웹 시안에서 확인한 것으로 보고하지 않는다.
