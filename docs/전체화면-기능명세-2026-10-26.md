- 실제 체크아웃 `/Users/cookhan/rattle`, `feature/operations-workflows`, HEAD `679c07593f8f8acd41528d94883a01202bcb7677` + 미커밋/미추적 247개. PR #128은 사용자 제공 식별자이며 원격 최신 상태는 조회하지 않았다.

## 요구사항 확인 및 코드상 위험 후보

1. 신규 매입은 단가 0을 허용하지만 상세 수정은 `price <= 0`을 거절한다 (`purchases/new:218`, `purchases/[id]:56`). 무상 매입의 수정 정책을 확인해야 한다. UI 재현 전 코드 불일치로 기록한다.
2. 재고 등록/수정은 화면에서 이름만 필수 검사하고 숫자를 `parseFloat(...) || 0`으로 보낸다. 음수/문자/무한대의 최종 거부 여부와 허용 범위를 서버까지 검증해야 한다. 입력이 0으로 조용히 바뀌는 것이 요구사항인지 미확정이다.
3. 루트 보호 경로는 재무 경로 및 admin/profit-loss/settings/pos-sync에 집중되어 있다. 설정·멤버·청소편집·정산·레시피 신규의 직접 딥링크는 메뉴 보호와 별도로 실제 비관리자 세션/RLS 검증이 필요하다. 취약점 확정이 아니다.
4. 로그인 화면의 법률 링크는 존재하지만 루트 비로그인 분기는 로그인 외 화면을 로그인으로 전환한다. 의존성/초기 진입에 따른 접근 동작을 네이티브 재현해야 한다.
5. 레시피 폼 내부의 식자재 생성/개당 용량 수정은 레시피 최종 저장 전 별도 쓰기다. 최종 취소가 이 부작용까지 되돌려야 하는지 요구사항 확인 필요.
6. `useConfirmLeave`는 네비게이션 이탈 경고다. 강제 종료·OS 프로세스 종료 후 초안 영속 복구를 보장하지 않는다. ‘중단 후 복구’와 ‘뒤로 답변 보존’을 구분한다.
7. settings/sales는 화면에서 supabase 직접 호출하여 AGENTS 서비스 레이어 관례와 다르다. 기능 수정은 하지 않았다.
8. 신규 매장에 사업자번호는 필수가 아니지만 직원 참여 신청은 10자리가 필요하다. 무번호 신규 매장의 직원 초대/참여 완료 경로는 제품 결정이 필요하다. POS 안내 표시를 실제 연동 완료로 판정하지 않는다.

## 입력 경계 기준

참여 시급 1~10,000,000, 주시간 0~168, 월급 1~1,000,000,000, 비과세 0~월급, 입사일 실제 달력 날짜 1900~2100, 은행 1~50자, 계좌는 하이픈/공백 제거 후 숫자 6~30자리 (`joinOnboarding.ts`). 허용값은 코드 관찰이며 법적/세무 적정성을 인증하지 않는다. 근무 분은 `workMinutes.ts`의 월별 상한·정수 검증 (미래월 이동은 화면에서 제한)을 기준으로 한다.

발주 화면은 현재 코드에 없다. AGENTS/SQL의 레거시 발주 설명은 현재 UI 범위에서 제외한다. 알림 설정은 매장 공통이며 수기 매출은 날짜별 대체 저장이다. 독립 검토 결과를 반영했다.

추가 동시변경 관찰(16:33경): app/_layout.tsx는 네이티브 스플래시 해제를 인증 로딩과 분리하고 SplashAnimation의 canExit로 인증 준비까지 종료를 대기한다. 관련 3파일을 최신 사본으로 갱신해 타입/Jest를 재실행했으며 실제 새 설치본은 미검증이다.
