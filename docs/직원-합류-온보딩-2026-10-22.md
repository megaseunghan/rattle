# 직원 합류 온보딩

> **현재 상태 · 2026-10-23:** 온보딩 테이블·함수와 선행 승인·알림 함수가 원격에 있고 본문이 일치함을 확인했다. 이번에 해당 파일을 재실행하지 않았다. 아래 미적용 서술은 당시 기록이다. 최신 근거는 [SQL 원격 적용 확인](archive/2026-10/SQL-원격적용-확인-2026-10-23.md)을 따른다.

## 현재 급여 확정 계약 · 2026-11-18 사용자 결정

관리자(해당 매장 사장·점장)가 최종 합류에서 고용형태별 급여를 확정한다. 파트타이머 시급은 0 초과 원/시간, 정규직 월급은 0 초과 원/월이며 NULL·0·음수·NaN·무한대는 허용하지 않는다. 직원의 과거 급여 제출값은 신청 참고 자료이며 본인 급여를 확정할 권한이 아니다. 아래 직원 급여 입력 설명은 과거 UX 기록이고 현재 관리자 확정 결정으로 대체한다. 실제 입력 화면·서비스 변경은 별도 앱 담당 범위다.

새 `supabase/migrations/20261118160000_join_wage_required.sql`은 원격 미적용이다. `approve_join_onboarding`·`resolve_store_member_approval`·`approve_store_member`·`create_employee_on_member_approve`·`create_employee_from_join`·`create_employee_with_initial_wage`의 이름·인자·기존 권한은 유지한다. 신규 직원 INSERT, 비활성→활성 UPDATE, 멤버 pending→approved UPDATE에 **DEFERRABLE INITIALLY DEFERRED constraint trigger**를 추가한다. RPC가 같은 트랜잭션에서 직원 생성/활성화와 급여 이력을 모두 반영한 최종 상태로 검증하고, 조건이 없으면 COMMIT 단계에서 전체를 거절한다. 반환값을 받았더라도 DB 트랜잭션 완료 전에는 성공으로 처리하지 않는다. 트리거 의미는 [PostgreSQL 공식 문서](https://www.postgresql.org/docs/current/sql-createtrigger.html)를 따른다.

재합류는 한국시간 오늘까지의 가장 최근 급여 조건 이력(동일 적용일은 created_at/id 내림차순)이 해당 고용형태에 맞는 양수면 아래 `approve_join_onboarding` 보존 payload로 그대로 재사용한다(온보딩 원본이 없는 구 신청에서는 기존 `resolve_store_member_approval` 경로도 유지). 기존 직원 현재 필드·이력·명세를 자동 덮어쓰거나 새 이력을 추가하지 않는다. 유효 이력이 없으면 관리자 입력으로 `approve_join_onboarding`을 사용하여 조건 이력을 같은 트랜잭션에서 저장해야 한다. 미래 이력만 있거나 최근 조건이 잘못된 경우 과거의 유효한 값을 찾아 우회하지 않는다. 기존 활성 직원 연결 승인도 현재 유효 조건(이력 우선)을 검사한다. 신규 직원에는 직원 행 자체의 양수 급여를 요구한다.

### 재합류 후보 요약과 보존 payload · 2026-11-18 추가 계약

백엔드는 새 `get_member_approval_wage_candidates(p_member_id:uuid)`를 사용한다. 기존 `get_member_approval_candidates`의 8개 반환 필드·함수는 호환 보존한다. 새 RPC는 동일한 관리자/신청/직원 후보 범위로만 다음 필드를 추가한다. 사장·해당 점장만 조회하며 직원·타매장 계정에는 열리지 않는다.

| 새 필드 | 타입·의미 |
|---|---|
| `existing_wage` | `{employment_type,hourly_wage,base_salary,effective_date}` 또는 null; 현재 유효 최신 조건이 형태별 유한 양수일 때만 객체 |
| `employment_type` | `regular|part_time` 현재 직원 고용형태 |
| `wage_condition_valid` | boolean; 비활성 후보·다른 계정 아님·현재 유효 최신 이력·형태별 유한 양수 금액을 모두 충족할 때 true |
| `wage_history_id` | UUID|null; 조회한 현재 유효 최신 조건의 식별자 |
| `wage_effective_date` | date|null; 해당 조건 적용일 |
| `wage_hourly_wage` | numeric|null; 기존 시급 원/시간 |
| `wage_base_salary` | numeric|null; 기존 월급 원/월 |

`existing_wage`는 표시·재사용용 요약이며 보존 가능 여부는 별도 `wage_condition_valid`로 판단한다(재직/타계정 후보는 유효 금액이 있어도 보존 불가). 이력이 없으면 요약 이력 필드와 `existing_wage`는 null이고 유효 여부는 false다. 이력은 있으나 금액이 잘못됐으면 개별 요약 필드에는 그 금액과 false를, `existing_wage`에는 null을 반환하므로 UI는 보존을 허용하지 않는다. 미래 조건을 현재 조건으로 표시하지 않는다.

보존 선택 시 기존 `approve_join_onboarding`의 인자를 그대로 사용하고 `p_choice='rehire'`, `p_employee_id=선택한 후보 ID`, `p_revision=현재 신청 프로필 revision(없으면0)`으로 호출한다. **이 경우에만** `p_review`의 급여·계좌·입사일 등 전체 입력 필드를 생략하며, payload는 아래 두 키만 보낸다. 보존과 변경 입력을 섞지 않는다.

```json
{
  "preserve_existing_wage": true,
  "wage_history_id": "후보 RPC가 반환한 UUID"
}
```

서버는 신청→매장→선택 직원·이력 잠금 후 현재 권한·신청 pending·퇴사 후보·다른 계정·프로필 revision·현재 유효 최신 조건을 다시 검사한다. `wage_history_id`가 바뀌면 `JOIN_WAGE_CONDITION_CHANGED`로 거절하며 새 후보 요약을 보여준 뒤 다시 선택해야 한다. 유효 이력이 없으면 `JOIN_WAGE_HISTORY_REQUIRED`, 금액 부적합이면 해당 급여 필수 오류로 거절한다. 기존 직원 현재 값(급여·입사일·계좌 포함)과 급여 이력·명세는 그대로 두고 계정 연결·활성화·멤버 승인만 처리한다. 기존 신청 프로필이 있으면 제출 원본 필드는 보존하고 `reviewed_revision`, `reviewed_by/at`, `reviewed_profile`의 보존 선택·이력 ID·조건 요약만 감사 기록으로 갱신한다. 프로필이 없으면 새 조건 프로필을 만들지 않는다.

`preserve_existing_wage`를 생략하거나 false로 두면 종전 전체 검토 payload가 필요하며 관리자가 입력한 새 조건을 저장한다. true인데 신규/자동 합류이거나 이력 ID 누락·잘못된 UUID·추가 필드가 있으면 `JOIN_WAGE_PRESERVE_INVALID`다. 새 후보 조회는 표시 자료이고 확정 권한·유효성 증거가 아니므로 클라이언트만으로 보존을 확정하지 않는다.

| 오류 코드 | 의미 / 앱의 다음 행동 |
|---|---|
| `JOIN_HOURLY_WAGE_REQUIRED` | 파트타이머의 유효 시급 없음. 관리자가 시급을 입력·확인 |
| `JOIN_BASE_SALARY_REQUIRED` | 정규직의 유효 월급 없음. 관리자가 월급을 입력·확인 |
| `JOIN_WAGE_PRESERVE_INVALID` | 보존 요청 형식/선택 오류. 재합류 선택과 후보 이력 ID 확인 |
| `JOIN_WAGE_CONDITION_CHANGED` | 조회 후 조건 변경. 후보 요약 재조회 후 다시 선택 |
| `JOIN_WAGE_HISTORY_REQUIRED` | 재합류의 현재 유효 이력 없음. 관리자 조건 입력 후 최종 합류 |
| `JOIN_EMPLOYMENT_TYPE_REQUIRED` | 고용형태 없음/지원하지 않는 값. 관리자가 고용형태 확인 |
| `JOIN_EMPLOYEE_REQUIRED` | 최종 합류에 연결된 활성 직원 없음. 신청·직원 연결 재조회 |
| `EMPLOYEE_FORBIDDEN` (`42501`) | 현재 해당 매장 관리자 아님. 권한과 매장 재조회 |

기존 `approve_join_onboarding`의 전체 검토 payload 형식 오류는 `JOIN_PROFILE_INVALID`, 직접 직원 생성 RPC의 입력 오류는 `INVALID_EMPLOYEE_CONDITIONS`도 유지한다. 내부 오류 코드를 그대로 직원 화면에 노출하지 않는다.

## 직원 입력 UX

직원은 한 화면에서 질문 하나에 답한다. 이름 → 휴대폰 → 사업자번호 → 근무 형태 → 해당 형태의 급여 질문 2개 → 입사일 → 은행 → 계좌번호 → 최종 확인의 10단계다. 파트타이머에게 월급·비과세를 묻지 않고 월급제 직원에게 시급·주시간을 묻지 않는다.

상단 진행률, 키보드 위의 다음 버튼, 질문 아래 오류 안내를 사용한다. 이전 질문으로 돌아가도 답을 유지한다. 마지막 요약에서 개별 답변을 수정할 수 있고, 고용형태를 바꾸면 새로운 급여 질문으로 안내한다. 입사일은 직접 입력 또는 기본 달력, 은행은 자주 사용하는 선택지 또는 직접 입력을 제공한다. 제출 실패 시 요약과 모든 답을 유지해 다시 시도할 수 있다. 제출 성공 뒤에는 관리자 확인 대기 상태를 보여준다.

관리자 화면은 기존대로 세부내역을 한 번에 비교·수정한다. 이번 질문별 UI 변경에는 새 SQL이나 서버 재배포가 필요하지 않다. 기존 온보딩 SQL이 적용되어 있어야 제출할 수 있다.

## 운영 흐름

1. 직원이 기존 매장 참여에서 이름·휴대폰·사업자번호를 입력한다.
2. 근무 형태를 선택하고 근무 조건 및 계좌 정보를 제출한다.
   - 파트타이머: 시급(원), 주 예정 근무시간(0~168 정수 시간).
   - 월급제 직원: 월 세전 기본급(비과세 포함 총액), 그 안의 비과세 금액.
   - 공통: 입사일, 은행, 본인 명의 급여 계좌번호.
3. 제출은 승인 대기 신청과 `store_join_profiles`에만 저장한다. 직원 생성, 급여 명세 생성, 기존 급여 수정은 하지 않는다.
4. 관리자가 멤버 관리 → 신청 확인에서 세부내역을 확인하고 수정한다. 겹치는 퇴사 기록이 있으면 기존 기록 연결 또는 새 직원 등록을 선택한다.
5. 관리자가 최종 합류를 확인하면 계정 연결·직원 조건·급여 조건 이력을 한 트랜잭션으로 반영한다. 그 전에는 변경 조건을 인건비 계산에 사용하지 않는다.

예전 신청에 온보딩 정보가 없으면 관리자가 직접 세부내역을 입력한 뒤 확정할 수 있다. 입력 계정은 `submitted_by`에 구분해 보관한다.

## 기존·재입사 직원

선택한 직원 ID와 이미 작성된 급여·근무시간 이력은 유지한다. 관리자가 확정한 고용형태·시급·주시간·월급·비과세·입사일·계좌는 현재 직원 정보에 반영하고, 급여 조건은 한국 시각의 오늘부터 새 이력으로 추가한다. 신규 직원은 확정한 입사일을 최초 급여 조건 적용일로 기록한다. 최종 합류만으로 월별 급여 명세를 만들거나 기존 명세 금액을 바꾸지 않는다. 기존 손익 집계의 현재 직원 상태·수습 조건 참조 방식 자체를 변경한 작업은 아니다.

다른 계정의 기록을 덮어쓰거나 여러 퇴사 기록 중 하나를 자동 선택하지 않는다. 이름·연락처 충돌 및 소속 매장 검사는 기존 서버 검증을 유지한다.

## 검토와 보안

제출 원본과 관리자가 확정한 수정본(`reviewed_profile`), 확정 계정·시각·버전을 보관한다. 계좌·급여 조건은 신청자 본인과 해당 매장 관리자만 조회할 수 있다. 클라이언트는 테이블에 직접 입력·수정·확정할 수 없고 RPC만 사용한다. 현재 버전과 다르면 승인하지 않는다. 기존 승인 RPC나 직접 상태 변경으로 새 온보딩 검토를 우회할 수 없다. 직원 생성·급여 조건 이력 중 하나라도 실패하면 신청 상태와 확정 기록까지 모두 롤백한다.

검토 중 직원 재제출이 있으면 관리자는 취소 후 신청 확인을 다시 열어 최신 버전을 확인한다. 제출 실패 시 화면의 입력값을 유지한다. 은행 계좌 실명·소유자 인증은 수행하지 않으므로 신청자와 관리자가 본인 명의인지 확인한다.

## Supabase 적용 — 아직 원격 미적용

기존 20261019 직원 자동 연결·급여 제출 및 20261020 보완 SQL이 적용되어 있어야 한다.

1. `20261021_member_approval_choice.sql`이 미적용이면 먼저 적용한다.
2. `20261022_employee_join_onboarding.sql`을 적용한다.

참여 알림 SQL은 기존 안내에 따라 별도로 적용한다. 홈 합계 SQL은 이 변경과 독립적이다. SQL을 먼저 적용한 뒤 앱을 갱신한다. 네이티브 모듈 변경은 없지만, 이미 설치한 Release 앱에는 새 화면이 자동 반영되지 않으므로 Release 재빌드·재설치가 필요하다.

## 검증

`npm run typecheck`, `npm test -- --runInBand --no-coverage`, `npm run test:sql`.

로컬 SQL은 축약 스키마의 PGlite 검증이며 원격 DB·실제 계정·기기 검증을 대체하지 않는다. 적용 후 실제 직원 제출 → 관리자 수정 → 최종 합류 → 고용형태·급여 조건·계좌 확인, 재입사 과거 명세 유지, 타 직원 계좌 비노출을 확인한다.
