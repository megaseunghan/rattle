> **전면 개편 시 해석 · 2026-11-02:** 아래는 10/30 당시 소스·설치본을 검토한 역사적 감사다. H1~H10의 사용성 원칙은 유지하지만, 기존 글래스·하루 업무 홈 순서 유지 등 당시 디자인 조건은 이번 새 디자인의 고정 조건이 아니다. 사용자는 역할별 홈·탐색·새 DESIGN.md 재검토와 Brutalist·Bold·Modern 방향을 허용했다. 현재 기능은 [갱신된 화면 명세](전체화면-기능명세-2026-10-26.md), 진행 상태는 [담당 작업계획](workspaces/README.md)을 우선한다. U01~U06/U08/U09는 후속 구현 존재가 확인됐으므로 아래 ‘미적용’ 진단을 그대로 현재 상태로 사용하지 않는다. 실제 업무·기기 검증 완료를 뜻하지는 않는다.

검토일: 2026-10-30 (KST). 기준 소스: `feature/operations-workflows`, `0d04e7860ed7b72af933854e5d347a7b8a23bb09`.

## 결론과 범위

추천은 전면 재디자인보다 **금액·저장 상태의 신뢰성 → 오류 복구·입력 보호 → 전체 자료 검색·반복 업무 → 정보 위계·접근성** 순서의 개선이다. 하루 업무 홈, 단계형 매입 등록, 급여 변경의 최종 검토, 확인 불가 금액을 0원과 구분하는 방향은 유지한다.

42개 화면의 현재 소스와 관련 훅·서비스·공통 UI를 검토했다. 실제 iOS 시뮬레이터에서는 실행 중인 설치본의 홈, 재고현황, 재고 탭 레시피, 레시피 등록, 식자재 선택창과 취소 복귀를 제한적으로 관찰했다. **42개 화면의 실제 조작·정상/오류/역할별 E2E를 완료했다는 뜻이 아니다.**

- 설치본: iPhone 16 Pro / iOS 26.3, 앱 1.0.0 (3). 설치본과 소스 HEAD의 일치는 확인하지 못했다. 화면 관찰은 그 설치본에만 유효하다.
- 조회 실패·역순 응답·저장 후 조회 실패는 코드에서 실행 경로를 검토했으며 실제 장애를 주입해 재현하지 않았다. 아래 ‘코드 확인’과 ‘위험’ 표현을 구분한다.
- 기존 실행 중인 앱에서 목록 탐색·등록창 열기·입력 없는 취소만 수행했다. 저장·삭제·초대·정산·연동 실행은 누르지 않았다. 홈에는 자동 POS 동기화 코드가 있으므로 앱 전체의 외부 부작용이 0이었다고 단정하지 않는다.
- 앱 코드·DB·설정 변경, push·배포는 하지 않았다. 본 보고서만 추가했다. 시작 시 기존 미추적 스토어 자산 7개 경로가 있었으며 그대로 보존했다. 원격 최신 여부는 이번에 조회하지 않았다.
- 소스 검토는 업무군별 별도 담당자가 읽고 주 담당자가 통합했다. 네이티브 관찰은 주 담당자만 수행했다. 사용자 시험이나 독립 QA 통과 판정은 아니다.
- 기준: [사용자가 지정한 휴리스틱 설명 글](https://therefrom.tistory.com/50), 현재 `DESIGN.md`, 화면 manifest·화면 명세·E2E 시나리오. 과거 검증 결과를 이번 통과로 이월하지 않았다.

## 판정 방식

H1 상태 가시성 / H2 현실 업무와 일치 / H3 제어·자유 / H4 일관성 / H5 오류 예방 / H6 기억 부담 감소 / H7 효율 / H8 간결함 / H9 오류 진단·복구 / H10 도움말.

## P1: 직원 확대 전 우선 해결

### U01. 수기 매출 ‘추가’가 기존 일 합계를 대체한다 — S26, H3/H5/H6

**코드 확인:** `app/pos/new.tsx:37,53`, `lib/services/manualSales.ts:22,37`. 날짜별 upsert인데 폼은 기존값을 조회하지 않고 빈 상태에서 시작하며 모든 필드를 전달한다. 같은 날짜 재등록 안내는 있지만 이전값과 변경값 비교는 없다.

**위험:** 카드 금액만 수정하려다 현금·할인·메모를 0 또는 빈값으로 덮을 수 있다. 실제 자료 덮어쓰기는 실행하지 않았다.

**개선:** 날짜 선택 → 기존 일 합계 조회 → 기존 자료가 있으면 ‘매출 수정’으로 전환 → 현금/카드/할인/메모 이전→변경 요약 → 확인 후 저장. 추가 거래 입력과 일 합계 변경을 같은 표현으로 다루지 않는다.

**완료 기준:** 기존 현금이 있는 날짜의 카드만 수정해도 현금이 보존되고 변경 범위를 저장 전에 알 수 있다. E-S26-C02/C05/C08/C09.

### U02. 급여명세의 월과 응답이 어긋날 수 있다 — S16, H1/H5/H9

**코드 확인:** `app/mypage/payslip.tsx:63-69`. 조회에 오류 상태·요청 식별·취소가 없고 월 변경 때 이전 payroll을 즉시 비우지 않는다.

**위험:** 9월 요청이 늦게 끝나면 10월 제목 아래 9월 명세가 표시될 수 있다. 조회 실패도 복구할 수단이 부족하다. 역순 응답 실측은 하지 않았다.

**개선:** 사용자·매장·직원·월을 키로 응답을 격리하고, 선택 월 로딩/조회 실패/명세 미작성 상태를 각각 표시한다. 재시도는 같은 월을 조회한다.

**완료 기준:** 빠른 월 이동과 이전 요청 지연에도 제목·명세 월이 일치한다. E-S16-C04/C06.

### U03. 과거 급여를 현재 직원 조건으로 설명한다 — S16, H2/H4/H5

**코드 확인:** `app/mypage/payslip.tsx:79-80,123-143`. 현재 직원의 고용형태·비과세를 과거 명세 표시 분기에 사용한다. 저장된 총액을 바꾸는 문제와 구분해야 한다.

**위험:** 현재 조건 변경으로 과거 기본급·비과세·공제 설명이 달라 보일 수 있다. 파트타이머 여부만으로 공제 분기를 나누는 표시도 관리자 화면과 대조가 필요하다.

**개선:** 해당 월 명세에 저장된 당시 조건·계산 결과를 표시한다. 근거가 없는 상세는 현재값으로 보완하지 말고 ‘당시 조건 확인 필요’로 표시한다.

**완료 기준:** 현재 조건을 바꿔도 과거 명세 설명이 바뀌지 않는다. 기존 데이터에 필요한 스냅샷이 있는지 먼저 확인한다. 세법 적정성 평가가 아니라 앱 내 표시 계약 개선이다.

### U04. 미저장 공제 예상액에 ‘확정’이라는 이름이 붙는다 — S05/M04, H1/H5

**코드 확인:** `app/(tabs)/payroll.tsx:279-280`. 정산 여부는 저장 payroll에서, 금액은 편집 중 deductionDraft의 previewNetPay에서 가져온다.

**개선:** ‘저장된 확정 실수령액’과 ‘수정 후 예상 실수령액 · 미저장’을 분리한다. 저장 시 정산 확정 해제를 미리 안내한다. 공제 draft가 재조회로 초기화되는 경로(`:143-163`)와 월 이동(`:417-418`)도 함께 보호한다.

**완료 기준:** 확정 명세의 공제를 입력해도 저장 전에는 확정액이 바뀐 것처럼 표시하지 않는다. 월 이동·재조회에서 편집값을 조용히 버리지 않는다.

### U05. 알림 설정이 저장되지 않아도 저장된 것처럼 보인다 — S21, H1/H9

**코드 확인:** `lib/hooks/useNotificationSettings.ts:11-29`, `app/notifications/settings.tsx:14,38`. 초기 조회 오류 상태가 없고, 먼저 바꾼 토글의 저장 실패에 rollback·오류 표시가 없다. savingKey도 UI에 사용하지 않는다.

**개선:** 조회 성공 전 설정을 확정값처럼 표시하지 않는다. 항목별 저장 중 표시·잠금과 실패 시 이전값 복구 또는 ‘미저장 · 재시도’를 제공한다.

**완료 기준:** 읽기 실패 때 기본값을 실제값으로 오해하지 않으며, 저장 실패 뒤 화면 상태가 서버와 다름을 알 수 있다. E-S21-C01/C04/C05/C09.

### U06. 체크리스트·요청함·수기 매출이 실패를 ‘없음’으로 보일 수 있다 — S11/S17/S25, H1/H9

**코드 확인:** `lib/hooks/useCleaningChecklist.ts:22-55`, `app/cleaning/index.tsx:34,68-91`; `lib/hooks/useRequestApprovals.ts:13-20`, `app/mypage/requests.tsx:37-38,49-52`; `lib/hooks/useManualSales.ts:11`, `app/pos/index.tsx:90,96,409,439`.

조회 error 상태가 없거나 승인 실패를 빈 catch로 버린다. 화면은 배열이 비었을 때 ‘등록 없음/요청 없음’을 보여준다. 수기 매출 삭제도 실패 안내가 없다.

**개선:** 첫 로딩 / 실제 빈 상태 / 첫 조회 실패 / 기존 자료를 유지한 갱신 실패 / 저장 중 / 저장 실패를 분리한다. 체크·승인·삭제는 대상 행과 함께 실패 이유·재시도를 표시한다.

**완료 기준:** 연결을 끊어도 ‘할 일 없음’이나 ‘매출 없음’으로 판정하지 않는다. 체크·승인 실패가 무반응으로 끝나지 않는다. 관련 E-Sxx-C04/C09.

### U07. 기존 식자재가 있는데 검색·선택할 수 없다 — S29/S32, H5/H6/H7

**코드 확인:** `lib/hooks/useIngredients.ts:16`은 페이지당 20개. 매입 등록은 `app/purchases/new.tsx:319`에서 로드된 자료에 startsWith 검색을 하고, `:649-667`에서 검색 0건이면 다음 페이지 로딩을 가진 FlatList 자체가 사라진다. 레시피 등록은 `app/recipes/new.tsx:66,512-517`에서 다음 페이지·오류를 사용하지 않는다.

**위험:** 21번째 이후 기존 품목을 찾지 못해 새로 등록하거나 사용을 포기할 수 있다. 캐시에 더 로드된 경우 발생 범위는 달라진다.

**개선:** 전체 자료 대상 검색·페이지 처리·로드 상태를 공유하는 선택기를 사용한다. ‘새 품목 등록’은 전체 검색 결과를 확인한 뒤 제공한다. 중간 단어 검색도 지원한다.

**네이티브 관찰:** 설치본의 레시피 식자재 선택창에는 검색 입력이 보이지 않았고 목록과 신규 등록만 있었다. 20개 초과 현상은 가상 대량 자료로 실제 재현하지 않았다.

**완료 기준:** 캐시가 빈 상태에서 21번째 이후 기존 품목을 이름 일부로 찾고 선택할 수 있다. 조회 실패를 ‘등록된 식자재 없음’으로 표시하지 않는다.

### U08. 레시피 상세의 재시도가 성공해도 오류 화면이 남는다 — S30, H9

**코드 확인:** `app/recipes/[id].tsx:26-35,64`. 실패 시 설정한 error를 다음 성공에서 지우지 않는다.

**개선·완료 기준:** 재조회 시작/성공 상태를 관리해 실패→재시도 성공 때 상세가 나타나고, 다시 실패하면 재시도를 유지한다. E-S30-C04.

### U09. 매장 정보·마감 시각이 저장된 뒤 ‘저장 실패’라고 할 수 있다 — S38/S39, H1/H9

**코드 확인:** `app/settings/sales.tsx:61-74`, `app/settings/store.tsx:34-39`의 저장과 refreshStore가 같은 try/catch다.

**개선:** S34 손익 공유의 패턴처럼 쓰기 성공과 후속 조회 실패를 분리한다. ‘저장됐어요. 화면을 새로 불러오지 못했어요’와 ‘화면 다시 불러오기’를 제공한다.

## 시각적 개선 제안과 검증할 항목

아래는 명백한 코드 오류와 구분한 디자인 제안이다. 모양만으로 합격/불합격을 단정하지 않는다.

1. **홈은 현재 단계와 미완료 업무가 먼저 읽히게 한다.** 현재 3단계와 여러 바로가기가 같은 카드/행 위계로 이어진다(`DailyOperationsHome.tsx:44-88`). 순서는 유지하되 해당 단계의 미완료 체크와 자주 하는 행동을 강조하고 나머지는 접을 수 있게 한다. 시간만으로 업무를 자동 완료 처리하면 안 된다. 현장 관찰로 ‘가장 먼저 찾는 업무’와 실제 탭 수를 비교한다.
2. **카드 안의 반복 카드를 줄인다.** 글래스 분위기는 승인 방향이므로 보존한다. 모든 행동을 같은 큰 버튼으로 만들기보다 핵심 행동·보조 링크·상태를 구분한다. 장식 효과보다 업무명과 금액 대비를 우선한다.
3. **중요한 보조 설명은 읽을 수 있는 크기로 올린다.** 알림 설정·체크 이력의 11pt/gray400, 도넛 바깥 라벨의 10~11pt는 작은 화면과 큰 글자에서 검증한다. 설명을 일괄 삭제하거나 한 줄로 축소하지 않는다.
4. **색 이외에도 상태를 읽을 수 있어야 한다.** 재고 부족·정산·선택 상태는 텍스트·아이콘·접근성 상태를 함께 준다. 최신 사용자 승인인 추세의 0원 이상 파랑/미만 빨강을 과거 문서의 초록 규칙으로 되돌리지 않는다.
5. **입력 라벨과 오류를 공통화한다.** `Field.tsx:17-40`은 라벨·도움말은 있지만 공통 오류/필수/접근성 연결 계약이 부족하다. 실제 호출부가 라벨을 전달하는지 함께 확인한다. 새 컴포넌트 하나만으로 모든 필드 문제가 해결됐다고 판단하지 않는다.
6. **보조 행동에도 대상이 있는 접근성 이름을 준다.** 재료 삭제·수기 매출 삭제·승인/거절에 품목·날짜·직원 대상을 포함한다. SheetModal의 모달/escape 지원은 유지하고 더보기 서랍의 포커스 가두기·복귀, Android 뒤로, VoiceOver 탐색을 실제 검증한다.
7. **비활성 이유를 설명한다.** S42는 query 오류로 disabled여도 saving 스타일만 바뀐다(`home-workflow.tsx:68`). 일별 급여 반영·필수 입력 누락도 같은 기준으로 버튼 옆에 막힌 이유와 해결 행동을 둔다.

## 추천 적용 순서와 검증

1. **금액과 저장 상태:** U01~U06/U09. 금액을 잘못 믿거나 자료를 다시 저장하게 되는 경로부터 고친다. 정상·조회 실패·저장 실패·저장 후 조회 실패·역순 응답을 각각 검증한다.
2. **업무를 막는 선택·복구:** U07/U08/U19/U23. 깨끗한 캐시와 21개 이상 품목·레시피로 전체 검색과 페이지를 확인한다.
3. **작성값 보호와 용어:** U11~U18/U20~U25/U28. 신규/수정·0/미입력·퇴사/삭제·요청/확정의 의미를 통일한다. 확인창을 모든 탭에 남발하기보다 실제 dirty 상태와 위험에 맞춰 적용한다.
4. **맥락과 도움:** U26/U27/U29~U34. 매장·기간·대상을 전달하고 관련 업무로 이어준다. 도움말은 해당 입력/오류 옆에서 찾게 한다.
5. **현장 UI 검증:** iOS 작은 화면·큰 글자, Android 키보드/뒤로, VoiceOver, 투명도 줄이기에서 실사용 경로를 확인한다. 운영 자료 대신 승인된 가상 매장과 역할 계정으로 수행한다.

각 수정은 기존 E-Sxx와 C01~C09를 재사용하고, 실행 환경·같은 소스 기준·빌드·기대/실제·저장 전후를 남긴다. 이번은 감사 보고서 작업이므로 앱 테스트·SQL 테스트를 실행하지 않았으며 수정 완료나 원격 적용을 주장하지 않는다.

성과는 주관적인 미관 점수 대신 첫 업무 찾기까지의 행동 수, 기존 식자재 검색 성공, 중단 후 재입력량, 실패 원인과 다음 행동 이해 여부로 확인하는 것이 적합하다. 현재 성과 수치를 측정했다는 뜻은 아니다.


## 새 디자인에서의 원칙 적용 — 2026-11-02

이번 보완은 원문 재감사나 코드 수정이 아니라 디자인 전달 기준의 정리다.

- **상태·저장 신뢰(H1/H5/H9):** 조회 실패≠자료 없음, 저장 성공≠조회 성공, 초안 예상액≠확정액. 새 시안에서도 각각의 상태와 다음 행동을 보여준다.
- **입력·제어(H2/H3/H6):** 대상 매장/월/직원/단위를 드러내고, 시간 환산·변경 전후 비교·누락 항목 이동·작성값 보호를 제공한다. 저장중 닫기의 의미도 명확히 한다.
- **일관성·효율(H4/H7):** 역할별 홈은 달라도 같은 행동의 표현은 통일한다. 검색/페이지는 전체 자료를 찾게 하고 기존 품목의 중복 등록을 유도하지 않는다.
- **시각 위계(H8):** 큰 숫자·굵은 제목·색면은 허용한다. 요약을 이해하기 쉽게 하는지로 판단하며, 포스터형 장식과 중복 카드로 실제 업무를 밀어내지 않는다. 목록/입력은 읽기 쉬운 밀도를 유지한다.
- **도움·접근성(H10 및 공통):** 필드/오류/비활성 이유 가까이에 설명을 제공한다. 상태는 색 이외의 단서로도 표현하고 큰 글자·한 손 사용·키보드·스크린리더·동작 줄이기를 고려한다.
- **취향과 오류 구분:** Brutalist·Bold·Modern은 표현 방향이다. 카드·그라데이션 자체를 사용성 오류나 AI Slop으로 판정하지 않고 기능/접근성 오류·문맥 없는 반복 패턴·사용자 선호를 구분한다.
- **설계 검토 산출물:** 대표 화면별 `역할/상태 → H원칙 → 실제 설계 → 남은 확인`을 연결한다. 정상 화면만 보고 모든 원칙을 통과 처리하거나 사용성 점수를 만들어내지 않는다.

원문 U01~U34와 기존 화면·E2E ID는 추적 근거로 보존한다. 이번에 기능 완료 상태·테스트·원격 적용·실기기 성공을 추가 선언하지 않았다.
