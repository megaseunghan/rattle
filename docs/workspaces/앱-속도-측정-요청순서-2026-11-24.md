## 1. 측정 환경

| 항목 | 값 |
|---|---|
| 기기 | MacBook Pro(Mac14,9)의 iOS 시뮬레이터 iPhone 17 Pro / iOS 26.3. **맥미니·실기기 아님** |
| 앱 | 시뮬레이터에 설치된 개발 빌드 `com.seunghan.rattle`(build 4, 2026-11-23 설치, dev-client). JS는 이 worktree의 Metro(포트 8082)에서 받음 = `2b1d4c8` + 측정 코드 |
| 서버 | 원격 개발 DB(서울 지역). 앱 URL과 CLI 연결 프로젝트가 같음을 확인 |
| 계정·매장 | 시뮬레이터에 이미 로그인돼 있던 관리자 계정, 매장 1곳 홈(store 모드). 매장 이름·ID는 기록하지 않음 |
| 네트워크 | Mac 기본 네트워크. Network Link Conditioner 등 시스템 설정 변경 없음 |
| 시각 | 2026-11-24 01:30~02:20(KST) |
| 회차 | 시나리오별 6회 실행 중 첫 회(번들 예열) 제외 5회씩. 앱 시작→홈은 두 시나리오 합쳐 10회 |

시뮬레이터·개발 빌드라 **시간(ms)은 참고값**이다. 주요 지표는 겹수·요청 수다.

## 2. 기준 숫자

겹수: **구조** = 코드로 확인한 "앞 요청 결과를 기다려야 시작하는" 단계 수. **실측** = 요청 시각만 보고 "앞 요청이 끝난 뒤 시작한" 요청을 이은 가장 긴 사슬(우연히 늦게 시작한 요청도 겹으로 셈 → 구조보다 크거나 같음).
시간: 홈은 JS 시작 → 홈 마지막 응답, 탭은 탭 이동 지시 → 그 탭 마지막 응답.

| 구간 | 요청 수(취소 제외) | 취소 | 겹수 구조 | 겹수 실측(5회) | 시간 중간값 / 최댓값 |
|---|---|---|---|---|---|
| 앱 시작 → 홈 (n=10) | 25 (매회 같음) | 1 | **5** | 6, 6, 6, 8, 7, 6, 7, 7, 7, 7 | 2,908 / 6,242ms |
| 매입 탭 첫 진입 | 6 | 0 | **2** | 2, 3, 3, 3, 2 | 732 / 2,470ms |
| 매입 탭 재진입 | 5 | 0 | **2** | 3, 3, 2, 3, 3 | 564 / 712ms |
| 인건비 탭 첫 진입 | 7 | 0 | **2** | 2, 2, 2, 2, 2 | 557 / 798ms |
| 인건비 탭 재진입 | 7 | 0 | **2** | 2, 2, 2, 2, 2 | 561 / 634ms |
| 탭 → 홈 복귀 (n=10) | 10 | 1 | 2 | 2 (10회 모두) | 매입 뒤 566/739, 인건비 뒤 426/514ms |

참고: 앱 실행 명령 → JS 시작은 중간값 3,742ms(개발 빌드가 Metro에서 번들을 받는 시간 포함, 출시 빌드 대표값 아님). 실행 명령 → 홈 마지막 응답은 중간값 6,764 / 최대 9,811ms.

## 3. 요청 순서표 (실측 + 코드 근거)

### 3-1. 앱 시작 → 홈 (25건 + 취소 1건)

| 겹 | 요청 | 기다리는 것 | 근거 |
|---|---|---|---|
| 1 | `rpc/get_my_store_bootstrap` | 없음(세션 복원 직후) | 실측 |
| 2 | `rpc/get_my_store_access`, `rpc/get_my_store_visibility` | 부트스트랩의 현재 매장 | 실측(둘 다 `p_store_id`) |
| 3 | `expenses`, `store_home_workflows`, `employees`, `notifications`, `rpc/get_financial_summaries_v2`, `toss_orders`, `cleaning_items`, `cleaning_logs`, `rpc/get_pos_daily_summaries`, `ingredients` (10건 동시) | 권한·공개 범위 | 실측 |
| 4 | `current_employee_wages`, `stores` | 시급: 같은 함수에서 직원 조회 뒤 순차 | `lib/services/employees.ts:19` |
| 5 | `employee_schedules` ×2, `attendance_effective_punches`(첫 요청은 시작 1~2ms 만에 취소, 곧바로 재요청) | 직원(+시급) 조회 결과로 본인 직원 확인 | 실측 시각(시급 응답 직후 시작) |
| 5 | `rpc/assert_store_finance_access` | 손익 요약 성공 **+ 유휴 작업 대기** | `lib/hooks/useHomeFinancialCard.ts:19-24` (`summary.isSuccess && readyScope`, `scheduleIdleTask`) |
| 6 | `rpc/get_daily_labor_sources` ×2, `rpc/get_daily_expense_series` ×2, `rpc/get_home_daily_sources` ×2 (이번 달·지난달) | 재무 접근 확인 통과 | `lib/services/homeFinancialTimeline.ts:9`, `:68` |

가장 긴 경로 두 개(가설과 같은 모양):
- **A** 부트스트랩 → 권한 → 손익 요약 → (유휴 대기) → 재무 접근 확인 → 일별 RPC 6개 = 네트워크 5겹. 유휴 대기 때문에 재무 접근 확인이 다른 렌더가 끝난 뒤 시작해 실측 겹수가 6~8로 늘어난다.
- **B** 부트스트랩 → 권한 → 직원 → 시급 → 출퇴근·스케줄 = 5겹.
- 홈 전체 겹수는 두 경로 중 큰 값이라 **A와 B를 함께 끊어야** 줄어든다.

### 3-2. 매입 탭

첫 진입(6건): `purchases`(500행 페이지) · `expenses`(500행 페이지) · `store_taxonomies` ×2 동시 → `purchases` 빈 페이지, `expenses` 빈 페이지.
- `readAllRows`가 0행을 받을 때까지 읽음 확인(`lib/services/readAllRows.ts:8`). 이번 자료는 매입 7행·비용 5행인데도 목록마다 2회.
- `store_taxonomies` 첫 진입 2회 동시 중복 확인(`lib/services/purchaseTypes.ts`, `lib/services/categoryTaxonomy.ts`). 재진입에서는 1회.
- 가설 "비용 최대 3겹"은 이번 자료에서 관측되지 않음(비용은 2겹). 자료 조건이 다르면 생길 수 있어 미확인으로 둔다.
- 재진입(5건)도 매입·비용·카테고리를 매번 다시 요청한다.

### 3-3. 인건비 탭

첫 진입(7건): `employees` · `payroll` · `employee_wage_history`(500행 페이지) · `payroll_work_submissions` · `rpc/get_admin_attendance_work_issues` 동시 → `current_employee_wages`(직원 뒤 순차, `employees.ts:19`) · `employee_wage_history` 빈 페이지.
- 직원 → 시급 2겹 확인. 홈에서 이미 직원을 받았는데도 직원을 다시 요청(가설의 "다른 캐시" 확인).
- 재진입도 7건을 모두 다시 요청한다.

### 3-4. 탭 → 홈 복귀

매번 10건 + 취소 1건(`employee_schedules` ×2, `attendance_effective_punches`, `ingredients`, `expenses`, `cleaning_items`, `cleaning_logs`, `store_home_workflows`, `toss_orders` → `stores`)을 다시 요청한다. 겹수 영향은 작지만 요청 수가 많다.

## 4. 서버 실행 시간 (pg_stat_statements, 참고)

관리 API의 읽기 전용 SQL 조회로 `extensions.pg_stat_statements`만 SELECT했다(쓰기·설정 변경 없음, CLI `inspect`는 임시 로그인 역할을 만들 수 있어 쓰지 않음). 값은 **통계 초기화 이후 누적**이며 이번 측정 외 사용도 포함한다. 같은 인자 모양의 RPC가 여럿이라 일부 대응은 추정이다.

| 요청 | 서버 평균 실행(ms) | 호출 수 | 앱에서 잰 소요 중간값(ms) |
|---|---|---|---|
| `get_financial_summaries_v2` | 565 | 787 | 506 |
| `p_store_id, p_year_month` RPC 2종(일별 인건비·비용 추정) | 391 / 237 | 623 / 621 | 457 / 267 |
| `get_home_daily_sources` | 235 | 233 | 258 |
| `p_store_id, p_from, p_to` RPC(POS 일별 추정) | 187 | 677 | 195 |
| `get_my_store_bootstrap` | 97 | 872 | 286 |
| `employee_schedules` (`select *`, 직원 필터) | 130 | 12,254 | 126 |
| `attendance_effective_punches` | 102 | 11,520 | 164 |

읽을 점: 손익 요약·일별 RPC는 기다리는 시간 대부분이 **DB 실행 시간**이다. 겹을 줄여도 이 RPC들의 실행 시간은 그대로 남는다. 스케줄·출퇴근 조회는 호출 수가 1만 건 이상으로 가장 많은 DB 시간을 쓴다(홈 복귀마다 재요청하는 것과 관련 있을 것으로 추정, 미검증).

## 6. 끊을 수 있는 순차 구간 후보 (예상 효과)

| # | 후보 | 대상 | 예상 겹수 | 예상 요청 수 | 변경 범위 |
|---|---|---|---|---|---|
| 1 | 홈 일별 조회의 "손익 요약 성공 + 유휴 대기" 조건을 풀고, 재무 접근 확인과 일별 RPC를 동시에 호출(또는 일별 RPC 안의 권한 검사로 대체) | 홈 경로 A | A: 5 → 3 | 같음 | 앱. 일별 RPC 자체 권한 검사 여부 **확인 필요** |
| 2 | 권한 응답(또는 부트스트랩)의 본인 `employee_id`로 출퇴근·스케줄 조회 앞당기기 + 시급 조회를 직원 조회와 동시에 | 홈 경로 B | B: 5 → 3 | 같음 | 앱(권한 응답에 직원 ID가 없으면 RPC 변경) |
| 3 | 부트스트랩에 권한·공개 범위 합치기 | 홈 A·B 공통 | −1 | −2 | 서버 RPC 변경(마이그레이션·DBA 검토 필요) |
| 4 | `readAllRows`: 받은 행이 500 미만이면 종료 | 매입·인건비 | 매입 2 → 1, 인건비 급여이력 −1 | 매입 −2, 인건비 −1 | 앱 한 곳 |
| 5 | 카테고리 조회 하나로 합치기 | 매입 첫 진입 | 0 | −1 | 앱 |
| 6 | 출퇴근 첫 요청 취소·스케줄 2회 중복 제거 | 홈 | 0 | −2 | 앱 |
| 7 | 재진입·홈 복귀 때 신선한 캐시는 다시 요청하지 않기(staleTime 검토) | 탭 재진입·홈 복귀 | 0 | 재진입 대부분 | 앱. 저장 후 무효화 규칙과 함께 검토 |

조합 예상: 1+2 → 홈 5 → 3겹(서버 변경 없이). 3까지 → 2겹. 4 → 매입 1겹, 4 + 시급 동시 → 인건비 1겹.
**제안 순서**: 1+2(홈, 앱만 수정, 효과 가장 큼) → 4·5(작고 위험 낮음) → 3(서버 변경, 별도 승인). 7은 요청 수 문제라 이번 "순서 줄이기"와 분리해 정하는 편이 좋다.

## 7. 다시 재는 방법

측정 코드·스크립트는 커밋하지 않고 로컬 비공개 폴더 `docs/private/perf-measure-2026-11-24/`(git 제외)에 보관했다: `perf-measure.patch`, `metro.sh`, `runs.sh`, `scenario.sh`, `analyze.py`, 결과 JSON.

1. 측정 브랜치에서 `git apply docs/private/perf-measure-2026-11-24/perf-measure.patch`
   - `lib/perf/requestTrace.ts`: `__DEV__`이고 `EXPO_PUBLIC_PERF_SCENARIO`가 있을 때만 Supabase `global.fetch`를 감싸 요청별 시작·끝 시각, 경로, 쿼리 **이름만**(값·UUID 제외), RPC 본문 키, Range, 상태를 `[PERF]` 로그로 남긴다.
   - `app/(tabs)/_layout.tsx`: 홈 요청이 3초 잠잠하면 대상 탭 첫 진입 → 홈 → 대상 탭 재진입 → 홈 순으로 자동 전환(각 이동 뒤 최소 2.5초 대기).
2. 다른 세션의 Metro(8081)를 건드리지 않도록 8082로 띄우고, 시뮬레이터 앱 설정 `RCT_jsLocation=localhost:8082`를 임시 지정한다(`rattle://` 주소는 다른 앱과 겹쳐 열리지 않음). 측정 후 `defaults delete com.seunghan.rattle RCT_jsLocation`으로 원복.
3. `scenario.sh purchases 6`, `scenario.sh payroll 6` → `analyze.py <로그> <탭>`. 첫 회는 번들 예열이라 제외.
4. 서버 통계는 관리 API 읽기 전용 SQL로 `extensions.pg_stat_statements`만 조회한다. 고친 뒤 비교하려면 같은 계정·매장·환경에서 다시 잰다. 누적 통계라 개선 전후 비교에는 앱 쪽 숫자를 우선한다.
5. 끝나면 패치를 되돌리고(`git checkout -- lib/supabase.ts 'app/(tabs)/_layout.tsx'`, `lib/perf/` 삭제) `git status`로 확인한다.

## 8. 미확인·한계

- 실기기는 10절에서 개발 빌드로 추가 측정했다. 느린 네트워크, 출시(release) 빌드 측정은 여전히 없다.
- 관리자 1명·매장 1곳만 측정. 직원·파트타이머 역할, 전체 매장 대시보드 모드, 매장 전환은 미측정.
- 이번 매장 자료가 적다(이번 달 매입 7행·비용 5행). 500행 넘는 매장에서는 `readAllRows` 페이지 수가 늘어난다.
- 홈의 "다 보여 줄 때"는 화면 렌더가 아니라 **마지막 응답 시각**(3초 잠잠)으로 대신했다.
- 후보 1의 "일별 RPC 자체 권한 검사"와 후보 2의 "권한 응답에 직원 ID 포함 여부"는 코드·SQL 확인 전이다.
- pg_stat_statements 초기화 시점은 확인하지 않았다.

새로 본 순서(코드 근거):
- **재고**: 레시피 → 레시피 원가(`lib/services/recipes.ts` `withCurrentCosts`, 레시피 ID로 원가 조회) 2겹. 첫 진입이 네 탭 중 가장 느렸다(중간값 1.1초, 레시피·원가 조회가 각각 0.5초 안팎). 재료·분류는 레시피와 동시에 나간다. 재진입 때는 요청이 없다.
- **매출**: 매장 정보 → 수기 매출 → 수기 매출 빈 페이지. 수기 매출은 `readAllRows`라 빈 페이지를 한 번 더 읽는다(23행). 매장 정보가 먼저 끝나야 수기 매출이 나가는지는 시각상 그렇게 보이나 코드로 확인하지 않았다(**추정**). 재진입 때는 수기 매출을 **2번 동시에** 요청한다(중복).
- **인건비**: 직원 → 시급, 급여 이력(`readAllRows`) 빈 페이지까지 2겹. 근무 확인 이슈 RPC(`get_admin_attendance_work_issues`)가 첫 진입 때 0.75초로 가장 길었다.
