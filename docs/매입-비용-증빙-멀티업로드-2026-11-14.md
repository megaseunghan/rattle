S12 비용, S27 매입 등록, S28 매입 상세에 적용한다. 거래당 10개까지 선택한다. 이미지 원본은 25MiB, PDF와 업로드 객체는 각각 10MiB가 상한이다. 매입 등록 전 선택한 파일은 거래 ID를 받은 뒤 전송한다. 일부 첨부가 실패하면 거래를 다시 만들지 않고 해당 파일만 재시도한다.

| 역할 | 매입 증빙 | 일반 비용 증빙 | 반복 고정비 월별 증빙 |
|---|---|---|---|
| 사장·점장 | 조회·첨부·삭제 | 조회·첨부·삭제 | 조회·첨부·삭제 |

공유 안 함은 일반 직원의 열람을 차단한다. 역할 미리보기에서는 실제 증빙을 불러오거나 변경할 수 없다. 권한은 매장과 대상 거래를 검사하는 서버 RPC 및 비공개 버킷 정책으로 확인한다.

## 변경 전후와 사용법

기존에는 첨부 저장 구조가 없었다. 이제 거래를 저장한 다음 같은 등록 흐름에서 이미지·PDF를 여러 개 첨부할 수 있다. 기본 제한은 **거래당 10개, 선택 파일당 10MiB**다. 기존 거래 금액·발생일·재고 계산을 증빙 저장 과정에서 변경하지 않는다.

1. 매입: 최종 등록 → 등록 완료 영역 → 증빙 여러 개 첨부. 이후 매입 상세에서도 증빙을 열고 추가·삭제할 수 있다.
2. 일반 비용: 저장 → 비용 저장 완료 상태에서 증빙 첨부 → 완료. 기존 비용은 편집창의 증빙 영역을 연다.
3. 기존 수기 고정비: 기존 비용 증빙 영역을 사용한다. 증빙 때문에 반복 일정을 생성할 필요는 없다.
4. 반복 고정비: 선택한 발생월별로 증빙을 구분한다. 새 일정은 확정한 처음 발생월에 첨부하며, 일정 생성 전 월이나 종료 후 월의 신규 첨부는 서버에서 거절한다. 과거 유효 월의 이미 저장된 증빙 조회는 보존한다.
5. 여러 파일은 한 번에 선택하지만 최적화·업로드는 한 개씩 처리한다. 대기·처리 중·실패를 파일별로 표시한다. 실패 파일만 다시 업로드하거나 첨부 취소할 수 있다. 거래 저장은 반복하지 않는다.
6. 앱 종료나 화면 이동으로 중단된 파일은 pending으로 남는다. 같은 거래에서 파일을 다시 선택해 이어 올리거나 삭제한다. 자동 백그라운드 업로드·강제 종료 후 자동 재개는 제공하지 않는다.

## 저장·보안·실패 복구

`transaction_evidence` 메타데이터는 매입/비용/반복 일정 중 하나와 정확히 연결된다. 반복 일정은 월까지 저장한다. 기존 레코드에는 자동 첨부나 가짜 빈 파일을 만들지 않는다.

- 버킷: `transaction-evidence`, 비공개. 일반 공개 URL은 만들지 않는다.
- 접근: 매장 금융 조회 권한 검사. 일반 비용·반복 비용 관리는 관리자, 매입 증빙 관리는 관리자/권한이 확인된 정규직. 파트타이머·직원 유형 미확인은 업로드/삭제 UI를 제한하고 서버에서도 검증한다.
- 업로드 전에 파일 UUID를 예약한다. 재시도는 같은 UUID/경로를 사용한다. 부모별 advisory lock으로 동시 예약의 10개 제한을 직렬화한다.
- 파일·썸네일이 모두 존재해야 ready가 된다. finish 응답 유실 후 재시도해도 ready 파일을 다시 업로드하지 않는다.
- pending 상태의 본인 파일만 덮어쓸 수 있다. ready 파일은 불변이며 교체는 새 첨부 ID를 사용한다.
- 기존 Storage permissive 정책에 우회되지 않도록 authenticated restrictive gate와 anon 차단 gate를 둔다. service_role 등 신뢰 서버 자격은 별도 관리한다.
- UI는 Supabase를 직접 호출하지 않고 services를 통한다. 계정·매장·권한·대상 변경 시 컴포넌트 키를 바꿔 이전 선택·서명 URL·상세 이미지를 제거한다. 처리 중인 요청은 단계 사이에서 중단하며 전송 중인 단일 네트워크 요청 자체를 강제 취소하지는 않는다.
- 삭제는 Storage 파일 → 메타데이터 순서다. 부모 삭제의 cascade나 직접 DB 메타데이터 삭제는 Storage 객체를 자동 삭제하지 않는다. 남은 객체는 메타데이터 기반 신규 접근이 거절되지만 저장 비용은 남는다. 고아 객체 정리 작업은 후속이며 자동 예약·일괄 삭제를 추가하지 않았다.
- 이미 발급된 서명 URL은 삭제·권한 변경 후에도 만료까지 최대 5분 접근될 수 있다. 즉시 철회라고 주장하지 않는다.

## 성능과 캐시 정책

기존 Expo SDK55/RN0.83 구성에 맞춰 `expo-image`, `expo-image-manipulator`, `expo-file-system`을 추가했다. FastImage 대신 expo-image를 사용한다. iOS는 SDWebImage, Android는 Glide 기반이며 Expo와 WebP/placeholder/캐시 API를 함께 쓸 수 있다.

- 접힌 영역은 메타데이터/이미지 URL을 요청하지 않는다. 펼친 후 가상화된 가로 목록에서 썸네일만 로드한다(초기/배치 3개).
- 선택 이미지는 네이티브 background 변환으로 긴 변 최대 2400px JPEG 품질 0.85와 긴 변 최대 384px 썸네일 품질 0.65를 만든다. 작은 이미지는 확대하지 않는다. PDF는 변환 없이 올린다.
- 상세는 탭할 때만 서명 URL을 발급하고 작은 썸네일을 placeholder로 표시한다. 이 문서의 ‘상세’는 업로드용 최적화 이미지이며 촬영 원본 비트 보존을 뜻하지 않는다. 사용자 원래 파일은 수정하지 않는다. 글자가 긴 영수증의 가독성은 실기기에서 추가 확인해야 한다.
- JS에서 픽셀 처리나 base64 인코딩을 하지 않는다. File.arrayBuffer 비동기 읽기 후 제한된 크기의 바이너리를 전송한다. 배열 복사·React 렌더·네트워크 콜백은 여전히 JS에서 실행된다. ‘JS thread 차단 0’이나 FPS 수치는 실측하지 않았다.
- iOS @2x/@3x·Android density suffix는 번들 정적 리소스 규칙이다. 업로드 사진에는 같은 규칙을 적용하지 않는다. 썸네일 384px는 128 논리 크기의 3배율을 고려한 상한이며 실제 물리 폭·메모리·텍스트 가독성은 네이티브 확인이 필요하다.

| 요구 개념 | 실제 구현 |
|---|---|
| immutable | ready 파일 경로를 불변으로 유지하고 교체 시 새 UUID 사용. 썸네일은 계정+첨부ID 캐시 키, expo-image memory-disk |
| web | Storage Cache-Control 3600초, 300초 서명 URL. CDN 토큰이 바뀌면 별도 캐시 키이므로 매번 재발급하지 않고 상세 URL을 발급 시점부터 240초 동안 메모리 재사용 |
| cacheOnly | 이번 구현에는 없음. 비공개 증빙을 오프라인 권한 확인 없이 보여주는 별도 모드를 추가하지 않았다. 연결 실패는 오류/재시도로 표시 |
| 상세 이미지 | 탭 시 로드, 메모리 캐시. 상세 이미지는 디스크 캐시를 요청하지 않음 |

썸네일 디스크 캐시는 앱 샌드박스에 남을 수 있다. 계정별 키를 사용하지만 로그아웃 시 물리적 캐시 전체 삭제 기능은 이번 범위에 추가하지 않았다. 서명 URL·메타데이터·재시도 큐를 영구 저장하지 않는다.

Supabase Storage 요청은 CDN을 경유하지만 Smart CDN 사용 여부·요금제·실제 hit ratio는 확인하지 않았다. 기존 버킷을 공개로 바꾸거나 외부 CDN 서비스를 추가하지 않는다.

공식 근거: [Expo Image SDK55](https://docs.expo.dev/versions/v55.0.0/sdk/image/), [ImageManipulator SDK55](https://docs.expo.dev/versions/v55.0.0/sdk/imagemanipulator/), [FileSystem SDK55](https://docs.expo.dev/versions/v55.0.0/sdk/filesystem/), [Supabase Smart CDN](https://supabase.com/docs/guides/storage/cdn/smart-cdn).

## 적용 순서와 검증 범위

1. 기존 마이그레이션이 적용된 대상에서 `supabase/migrations/20261114120000_transaction_evidence.sql`을 먼저 검토·적용한다. 이번 작업에서는 **원격 미적용**이다. 기존 매입 RPC는 유지하고 현재 함수의 가드가 포함된 정의를 복제해 새 UUID 반환 RPC를 추가한다. 예상 함수 본문 계약이 달라지면 마이그레이션이 중단된다.
2. SDK55 의존성을 설치하고 **새 네이티브 바이너리**를 빌드한다. 현재 runtimeVersion은 appVersion 정책이므로 기존 바이너리에 같은 runtime OTA만 보내면 안 된다. 실제 배포 때 버전/runtime 변경과 새 바이너리 범위를 별도 확정한다. 이번에 app.json 버전·채널을 바꾸거나 EAS를 발행하지 않았다.
3. 기존 UI 통합 파일만 현재 디자인 브랜치와 3-way 비교한다. 이 작업의 화면 레이아웃·토큰 변경은 없지만 같은 파일을 수정하면 충돌 가능성은 남는다. 자동 merge/push는 하지 않았다.
4. 테스트 계정/매장에서 이미지·PDF 다중 선택, 큰 영수증 가독성, 2x/3x 화면, 메모리·FPS, 부분 실패·재선택·삭제·계정 전환을 iOS와 Android에서 검증한다. 실제 사용자 증빙을 QA fixture로 복제하지 않는다.

로컬 확인: TypeScript, 앱 Jest, reduced-schema PGlite 권한/상태 검사, 42 라우트 manifest, iOS/Android Metro export. 테스트에는 example.invalid 가짜 환경을 사용했다. Expo export는 JS 번들 생성이며 네이티브 컴파일·설치·기기 실행을 뜻하지 않는다.

미실행: 원격 migration chain/실계정 JWT/Storage API/CDN hit ratio, 동시 트랜잭션 실서버, iOS/Android 네이티브 설치·실기기, UI 320/375/414 폭 및 스크린리더 조작, FPS·메모리 실측. 이 확인 전에는 전체 기능 배포 완료로 처리하지 않는다.

## Claude 코드 리뷰 보정 · 우선순위 1·2·4

사용자 요청 범위에 따라 세 항목을 수정했다. 기존 디자인·원격 업무자료·이전 적용 SQL을 덮어쓰지 않았다. 새 보정 migration은 **로컬 작성만 했으며 원격 미적용**이다.

1. **부모 삭제와 증빙 정리**: 매입/비용 삭제 함수는 서버 사전 점검 → 각 Storage 파일 삭제 → 파일 부재를 서버에서 확인하고 메타데이터 삭제 → 부모 거래 삭제 순서다. 연결된 고정비 원본이나 권한 없는 거래는 파일 정리 전에 거절한다. 부분 실패 시 부모를 유지하고 일부 첨부가 삭제됐을 수 있음을 안내한다. 메타데이터 직접 DELETE를 회수하고 전용 RPC로 제한한다. 네 가지 FK(매장/매입/비용/반복 일정)를 RESTRICT로 바꿔 구형 클라이언트·직접 DB 삭제·동시 새 첨부에 의한 cascade 고아 생성을 막는다.
   - 반복 일정은 원래 물리 삭제 서비스/화면이 없고 버전을 보존한다. 신규 물리 삭제 기능을 만들지 않았다. 버전 있는 규칙은 정리 사전 점검에서도 거절하고, FK가 증빙을 가진 규칙의 직접 삭제를 차단한다. 미래의 버전 없는 규칙 정리가 필요하면 같은 공통 사전점검/정리 함수를 사용할 수 있다.
   - 실제 로컬 정책 테스트에서 기존 삭제 정책의 unqualified `name`이 metadata의 f.name을 참조해 파일 삭제가 무시되는 문제를 발견했다. `storage.objects.name`으로 명시했다.
   - Storage DB 쓰기는 새 VOLATILE 권한 헬퍼에서 증빙 행을 FOR SHARE로 잠그고, 메타데이터 정리는 FOR UPDATE로 잠근다. 같은 pending 파일의 업로드/삭제 DB 쓰기를 직렬화한다. 실제 Storage API의 다중 세션 경합은 별도 미검증이다.
2. **정규직 명시 확인**: 매입 증빙 쓰기는 관리자 또는 같은 매장의 승인 멤버이면서 활성 직원 행의 employment_type='regular'인 계정만 허용한다. full_time은 현재 앱의 enum 값이 아니다. 직원 미연결·비활성·파트타이머는 서버 예약/Storage 쓰기·삭제/메타데이터 삭제가 거절된다. 다른 작성자의 첨부가 있으면 비관리자의 부모 삭제도 파일 정리 전에 거절해 일부만 지우는 일을 피한다.
3. **오류/재시도/로그**: EVIDENCE_LIMIT, EVIDENCE_NO_OCCURRENCE, SQL42501/HTTP403, 첨부 ID 충돌, 계정 변경을 구분한다. 같은 요청을 반복해도 해결되지 않는 오류는 재시도를 숨기고, 연결 실패는 파일별 재시도를 유지한다. 로그에는 분류·재시도 여부만 기록하고 원문 오류/문서명/주소/서명 토큰/사용자 ID는 남기지 않는다.

- 자동 만료·예약 작업을 추가하지 않았다. 작성자는 본인 것, 관리자는 해당 대상의 모든 미완료 첨부를 확인 후 일괄 삭제할 수 있다. 준비된 증빙은 삭제 대상에서 제외한다. 정리할 항목이 있는 경우에만 버튼을 표시한다.
- 매번 대상 목록을 다시 조회한 뒤 `begin_pending_evidence_discard`가 행을 FOR UPDATE로 잠그고 권한과 아직 ready가 아님을 재검사한다. `discarding`으로 전환하면 기존 Storage 쓰기 헬퍼의 pending 조건이 업로드를 막고 finish도 거절한다. 직전 ready로 완료된 파일은 claim 단계에서 거절하므로 Storage를 건드리지 않는다.
- Storage 정리 → 기존 `discard_transaction_evidence_metadata`의 실제 파일 부재 확인 → 메타데이터 삭제 순서를 유지한다. 정리 실패 시 discarding 행과 파일을 추적 가능하게 남기고 다시 삭제할 수 있다. 완전히 삭제되기 전까지 10개 한도에 포함한다. 한도를 무시해 누적 pending을 무제한 만들지 않는다. 다른 기기에서 업로드 중인 pending도 사용자가 명시적으로 정리를 선택하면 중단될 수 있으며 재선택이 필요하다.
- 일부 실패는 남은 목록을 재조회하고 복구 안내를 표시한다. 로컬 진행 중인 업로드와 정리는 패널 잠금으로 함께 실행되지 않는다. 실제 Storage API의 다중 세션 업로드 경합은 미검증이다.

### 6a. MIME 불명 PDF

- 최초 선택과 재선택에서 명시 PDF MIME, 대소문자 구분 없는 .pdf 확장자, 알 수 없는 MIME의 첫 5바이트 `%PDF-`를 사용한다. 전체 문서를 JS로 읽지 않고 FileHandle.readBytes(5)만 호출하며 실패 시에도 close한다. 지원 이미지 확장자는 헤더 확인 후 fallback으로 사용하고 알 수 없는 형식은 거절한다. PDF로 판별되면 10MiB 제한을 적용하고 PDF 메타데이터로 예약한다.
- 시스템 picker는 모든 형식을 표시하고 선택 직후 지원 형식을 검증한다. MIME 불명 파일도 고를 수 있게 하기 위한 변경이다. 재선택 시 기존 예약과 이미지/PDF 종류가 다르면 거절하며 기존 row의 종류는 바꾸지 않는다. 완전한 문서 유효성/악성 파일 검사는 이번 판별의 범위가 아니다.
- API 근거: https://docs.expo.dev/versions/v55.0.0/sdk/filesystem/#filehandle (설치본 File.open / FileHandle.readBytes / close 타입도 확인).
