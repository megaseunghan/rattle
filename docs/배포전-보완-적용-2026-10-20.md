# 직원 배포 전 보완 작업과 적용 순서

## 현재 상태

- 구현 기준: 기존 Supabase 구조. 최종 DB 선택을 확정한 것은 아니다.
- 개발/운영 분리는 사용자 요청에 따라 마지막 단계로 보류했다.
- 앱·SQL·서버 함수 수정 및 로컬 검증까지 진행했다. 원격 SQL은 사용자가 적용했으며, 서버 함수 배포·실제 백업·복원·실기기 검증 완료 여부는 확인하지 않았다.
- 탈퇴 연결 해제의 자동 재시도 예약은 초기 배포에서 제외했다. 즉시 처리와 실패 기록·수동 재처리만 유지하며 pg_cron·pg_net·Vault 추가 설정은 필요하지 않다.
- 기존 10월 19일까지의 SQL과 10월 20일 SQL 01·02·03 모두 사용자가 적용 완료했다고 안내했다. 원격 정의를 직접 대조한 상태는 아니다. 아래 SQL 절차는 적용 순서 기록이며 다시 실행하라는 안내가 아니다.

## 구현한 내용

| 영역 | 변경 후 동작 |
|---|---|
| 직원 정보 | 일반 직원은 연결된 본인 정보만 조회, 기본급·시급 등 수정은 관리자만 허용 |
| 급여·이력 | 본인 또는 관리자만 조회. 미승인·퇴사 계정 및 다른 매장 접근 차단 |
| 손익 | 본인 급여만 읽은 결과를 매장 전체 인건비로 오집계하지 않도록 관리자만 조회 |
| 매입·재고 | 재료의 매장 소속, 수량·단가를 서버에서 검증. 오류 시 전체 롤백. 품목 수정 시 부모 매입과 품목을 잠근 뒤 차액 계산 |
| 레시피 | 다른 매장 재료 연결 거절. 제거된 과거 발주 RPC의 일반 사용자 실행 차단 |
| 급여 계산 | 세액표 오류·누락 시 중단. 추정값 대체와 급여 콘솔 출력 제거. 대상 월 기준 조회 및 계산 버전 기록 |
| 계산 연도 | 현재 구현된 2026년 기준만 허용. 다른 연도는 해당 기준을 준비할 때까지 자동 계산 차단. 기존 내역은 삭제하지 않음 |
| 계정 탈퇴 | 매장 소유자는 승인된 멤버에게 소유권을 이전한 뒤 탈퇴. 매장 공용 급여·매입 자료 보존 |
| 외부 로그인 해제 | Auth 계정 삭제와 재처리 항목 생성을 같은 DB 트랜잭션으로 처리. 삭제 후 즉시 외부 연결 해제, 실패 내역은 보관한 뒤 개발자가 수동 재처리 |
| POS 웹훅 | 설치·해제·큐 저장·중복 방지 기록을 한 DB 트랜잭션으로 처리. 저장 실패는 실패 응답, 재전송 가능. 서명 시각·이벤트 헤더 검증 |
| 개발용 UI | 배포 빌드에서는 역할 미리보기 스위치와 역할 변경 차단 |
| 자동 검사 | Jest·타입 검사에 SQL 권한/복구 검사와 Deno 서버 함수 검사를 CI에 추가 |

세율·공제 적용 조건 전체의 법적 적정성을 새로 인증한 작업은 아니다. 급여 기준 검증과 실제 지급액 대조는 배포 전 별도 확인 항목이다.

## 원격 적용 순서 — SQL은 사용자 적용 완료

최종 DB 또는 이번 수정의 적용 대상을 먼저 선택한다. 다른 DB 제품을 선택한다면 아래 Supabase 전용 인증·권한·서버 함수를 그대로 적용할 수 없으므로 이식 범위를 별도로 정한다.

1. 적용 대상 프로젝트를 확인하고 백업을 확보한다. `supabase/operations/release-preflight.sql`은 조회 전용이다. 기존 매입 품목의 매장 연결 불일치가 있다면 자동으로 고치지 말고 원본부터 대조한다.
2. 기존 탈퇴 함수가 먼저 카카오 연결을 끊는 동작을 중지하기 위해 **새 `delete-account` 함수를 SQL보다 먼저 배포**한다. 새 함수는 SQL 준비가 안 되어 있으면 탈퇴를 중단하고 어떤 자료도 삭제하지 않는다. CLI 대상 프로젝트를 확인한 뒤 `npx supabase functions deploy delete-account`를 실행한다.
3. Supabase SQL Editor에서 아래 세 파일을 순서대로 실행한다. 이전 전환 SQL이 적용된 기존 구조가 전제다. 한 파일 전체가 한 트랜잭션이며, 적용 이력 없이 반복 실행하지 않는다.
   - `supabase/migrations/20261020_01_access_and_purchase_integrity.sql`
   - `supabase/migrations/20261020_02_account_deletion.sql`
   - `supabase/migrations/20261020_03_webhook_transaction.sql`
4. 같은 프로젝트에 나머지 서버 함수를 배포한다. CLI가 대상 프로젝트에 연결되었는지 먼저 확인한다.

```sh
npx supabase functions deploy toss-proxy
npx supabase functions deploy toss-webhook --no-verify-jwt
```

`toss-webhook`은 카카오/사용자 JWT 대신 기존 Toss 서명을 핸들러에서 검증한다. 서버에는 기존 `KAKAO_ADMIN_KEY`, `TOSS_WEBHOOK_SECRET` 및 Supabase 서버 환경 설정이 필요하다. 키 값을 앱이나 Git에 넣지 않는다.

5. 이후 앱을 배포하고 실제 직원·관리자 계정으로 아래 흐름을 확인한다. SQL과 서버 함수가 먼저 준비되어야 새 앱이 동작한다.

소셜 로그인 확장으로 `delete-account`에 Apple 연결 해제 처리가 추가됐다. 현재 재배포 절차는 [소셜 로그인 설정](소셜로그인-설정-2026-10-20.md)을 따른다. 위 표의 삭제 후 외부 연결 해제는 카카오에 해당하며, Apple은 소유권 검사와 재인증 후 연결 해제를 먼저 완료한다.

Toss 공식 웹훅 규격의 HMAC·밀리초 시각·이벤트 ID 형식을 대조했다. 본문 ID와 `x-toss-webhook-id`를 대조하고 5분을 넘긴 서명은 거절한다. 매출 조회 프록시는 20초 타임아웃을 적용했다. 실제 제공자 이벤트 수신은 별도 확인해야 한다. [Toss 웹훅 규격](https://docs.tossplace.com/reference/open-api/webhook.html)

## 카카오 연결 해제 실패의 수동 처리

정상 탈퇴는 `delete-account`만으로 즉시 처리한다. 카카오 연결 해제에 실패해도 Rattle 계정 삭제는 완료되며, 실패 항목은 `account_unlink_jobs`에 남는다. 주기적으로 자동 재시도하지 않는다.

실패가 발생했을 때 개발자가 `health.sql`과 서버 로그를 확인한 뒤 필요하면 `account-unlink-retry`를 배포해 POST 요청으로 수동 호출한다. 이 도구는 서버 서비스 키 요청만 허용한다. 요청 한 번에 최대 5건을 처리하며 중복 처리 방지를 위해 처리한 항목은 5분 뒤 다시 시도할 수 있다. 8회에 도달한 항목은 원인을 검토해야 한다. 호출 후 남은 항목 수를 다시 확인한다. 초기 배포의 필수 함수나 예약 설정에 포함하지 않는다.

이전 안내대로 **이미** `rattle-account-unlinks` 예약을 등록했다면 SQL Editor에서 아래 쿼리로 해당 예약만 해제한다. 예약을 등록하지 않았다면 실행할 필요 없다. 확장과 Vault 항목은 다른 작업에서 사용할 수 있으므로 삭제하지 않는다.

```sql
SELECT cron.unschedule(jobid)
FROM cron.job
WHERE jobname = 'rattle-account-unlinks';
```

## 실제 계정·휴대폰 확인

| 계정 | 확인할 결과 |
|---|---|
| 일반 직원 | 본인 급여만 조회, 타인 급여 및 시급 수정 거절 |
| 파트타이머 | 본인 시간 제출 → 관리자 반려 → 재제출 → 확인 → 급여 반영 → 정산 |
| 관리자 | 전체 급여와 손익 조회, 매장 전환 후 다른 매장 자료 혼입 없음 |
| 소유자 | 소유권 이전 전 탈퇴 차단, 이전 후 매장·급여 자료 유지 |
| 테스트 탈퇴 계정 | 계정 삭제 후 접근 불가, 외부 연결 해제 실패 시 작업 남음, 수동 재처리 성공 후 작업 삭제 |
| POS 테스트 이벤트 | 정상·중복·DB 실패 후 재전송·연동 해제의 최종 상태 일치 |

실제 직원 자료로 탈퇴·복원 실험을 하지 않는다. 이 단계의 삭제 검증은 별도 가상 계정과 자료를 사용한다.

## 장애 발견과 복구

- `supabase/operations/health.sql`은 식별자·금액·외부 원문을 제외한 조회 전용 점검이다. 연결 해제 대기 항목이 있으면 실패 원인을 확인하고 수동 재처리한다. 자동 재시도나 담당자 알림은 실행하지 않는다.
- 서버 함수 로그 이벤트: `account_delete_failed`, `account_unlink_pending`, `account_unlink_retry_failed`, `account_unlink_status_failed`, `toss_webhook_failed`.
- 로그에는 원본 급여·키·카카오 사용자 ID를 출력하지 않는다. 외부 오류 알림 서비스 연결은 아직 하지 않았다. 위 이벤트의 알림 연결과 담당자 지정은 서버 선택 후 마무리한다.
- 카카오 연결 해제는 성공했으나 DB 확인 저장이 실패한 경우에도 재시도할 수 있다. 카카오의 이미 미연결 응답(-101)은 완료로 처리한다. [카카오 오류 코드](https://developers.kakao.com/docs/ko/rest-api/error-code)
- 이전 버전에서 처리 실패한 이벤트가 완료로 잘못 기록된 경우는 자동 삭제하지 않는다. 제공자 이벤트와 DB 상태를 대조한 뒤 해당 이벤트만 복구한다.
- 새 정책을 과거의 넓은 정책으로 되돌리는 복구는 하지 않는다. 실패 시 앱 배포를 멈추고 권한을 유지한 상태에서 수정한다.

## 백업 — 실행 준비만 완료

`scripts/backup-postgres.sh`는 PostgreSQL을 선택했을 때 사용할 논리 백업 도구다. 접속 정보는 libpq 서비스 파일과 비밀번호 파일로 관리하고 백업 파일은 암호화된 별도 저장 위치에 보관한다.

```sh
bash scripts/backup-postgres.sh rattle-backup /안전한/백업/경로
```

백업 파일과 SHA-256을 생성하고 형식을 검사한다. 실제 백업, 일정 등록, 보관 위치 결정, 복원 시험은 아직 하지 않았다. DB 백업에는 Storage 원본 파일, 외부 비밀키, 서버 함수 배포 설정이 포함되지 않으므로 별도 보관해야 한다. 역할·확장·관리형 인증 스키마의 복원은 선택한 DB 제공자의 절차를 따른다. [PostgreSQL 백업 안내](https://www.postgresql.org/docs/17/app-pgdump.html), [Supabase 백업 안내](https://supabase.com/docs/guides/platform/backups)

복원 완료는 파일 생성으로 판정하지 않는다. 격리한 대상에 복원한 뒤 매장 수·품목 수·월별 급여/매입 합계, 권한, 로그인 및 직원 제출 흐름을 확인해야 한다.

## 로컬 검증의 범위

검증 결과: 앱 타입 검사 통과, Jest 27개 묶음·159개 테스트 통과, SQL 기존 50개 + 신규 65개 검사 통과, Deno 서버 함수 타입 검사 및 외부 연결 해제 재처리 테스트 5개 통과. 백업 스크립트의 셸 문법 검사와 변경 파일 공백 검사도 통과했다. GitHub 원격 CI는 이번 변경으로 실행하지 않았다.

SQL 검사는 가상 계정과 축약 스키마를 사용하는 PGlite 검사다. 실제 서버의 전체 마이그레이션 재생, 실제 GoTrue 계정 삭제, 여러 연결의 동시 요청을 대신하지 않는다. 서버 함수 테스트는 외부 호출을 가짜 응답으로 바꿔 실행했다.

## 마지막 단계

DB 제품과 운영 프로젝트를 정한 뒤 개발/운영 분리, 빌드별 연결 대상, 백업 일정·복구 시험, 외부 장애 알림을 확정한다. 이 단계까지는 직원 정식 배포 완료로 보지 않는다.
