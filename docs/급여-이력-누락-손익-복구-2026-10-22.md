# 급여 이력 누락 시 손익 조회 복구

> **현재 상태 · 2026-10-23:** get_financial_summaries_v2의 원격 본문 일치를 확인했다. 이번 sharing SQL 적용 전후 급여·급여 조건 이력 지문은 동일하다. 조건 이력의 업무상 누락을 자동 보정한 것은 아니다. 최신 근거는 [SQL 원격 적용 확인](SQL-원격적용-확인-2026-10-23.md)을 따른다.

## 계산 기준

1. 해당 매장·월의 저장된 급여 명세가 있으면 세전 `gross`를 그대로 합산한다. 현재 기본급이나 새 이력으로 다시 계산하지 않는다. 명시적인 0원, 퇴사자, 직원 연결이 해제된 급여도 포함한다.
2. 명세가 없는 재직 정규직은 적용 기간의 급여 이력이 충분할 때만 기존 일할 계산을 사용한다. 명세가 있는 직원은 이력 계산에서 제외해 중복 합산하지 않는다.
3. 명세와 적용 시작 이력이 모두 없으면 해당 매장·월의 인건비와 영업이익을 `null`로 반환한다. 월 중간 이력만 있는 경우도 앞 기간을 추정하지 않는다.
4. 매출·매입·비용과 정상 매장의 손익은 계속 표시한다. 미확인 월이 포함된 연간 합계, 미확인 매장이 포함된 전체 이익·지출·마진, 비교율은 확정 숫자로 표시하지 않는다. 추세의 미확인 구간은 0원 막대로 그리지 않는다.
5. 급여 자료 조회 실패나 권한 오류는 미확인 급여와 별개의 조회 실패로 처리한다.

급여 명세·조건 이력·정산 상태의 생성, 수정, 삭제를 수행하는 변경은 없다. 과거 금액이나 적용일을 자동 생성하지 않는다. 근거가 없는 금액은 관리자가 해당 월 명세 또는 실제 적용 조건을 확인해야 완전한 손익으로 표시된다.

## 서버 적용 전후

- 관리자 요약은 `get_financial_summaries_v2`를 요청한다.
- 정확히 이 함수가 아직 없다는 `PGRST202` 응답일 때만 관리자 호환 조회를 사용한다. 먼저 모든 요청 매장의 기존 `assert_store_finance_access`를 통과해야 하며 상세 조회에서도 다시 권한을 확인한다.
- 호환 조회는 동시에 최대 3개 매장·월을 처리한다. 주문·급여·직원·조건 이력·매입·품목·수기매출·비용은 서버 건수 제한으로 잘리지 않도록 고유 키 순서로 마지막 페이지까지 읽는다. 중간 페이지 오류는 부분 합계로 반환하지 않는다.
- 권한·네트워크·일반 서버 오류를 우회하지 않는다. 일반 직원 조회는 기존 서버 집계와 권한을 유지한다.
- v2 SQL 적용 후에는 한 번의 서버 집계로 같은 금액을 반환한다. 호환 조회보다 네트워크 요청이 적으므로 다매장·연간 조회에는 서버 적용을 권장한다.

## SQL 적용 순서 — 원격 미적용

이번 작업에서는 원격 DB를 수정하지 않았다. 프로젝트 지침에 따라 SQL은 사용자가 적용한다.

1. 기존 `20261023120000_read_models_and_integrity.sql`이 아직 미적용이면 먼저 기존 적용 문서에 따라 적용한다. 이미 적용했다면 재실행하지 않는다.
2. 새 `supabase/migrations/20261023122000_financial_wage_coverage.sql`을 적용한다.

기존 POS 마이그레이션 `20261023121000_pos_read_models.sql`을 함께 배포하는 경우에는 기존 안내대로 120000 → 121000 → 122000 순서다. v2 함수 자체는 POS 새 함수에 의존하지 않는다.

새 SQL은 읽기 전용 집계 함수만 추가한다. `payroll`·`employee_wage_history` 자료를 변경하지 않으며, 기존 v1 함수를 교체하지 않는다. 새 앱은 서버 적용 전에도 관리자 호환 경로로 동작한다.

**Supabase에서 SQL 적용을 진행해줘.**
