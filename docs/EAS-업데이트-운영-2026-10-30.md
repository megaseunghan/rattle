## 프로필과 채널

| 빌드 프로필 | 배포 방식 | 업데이트 채널 | EAS 환경 |
|---|---|---|---|
| development | 내부 개발 클라이언트 | development | development |
| preview | 내부 배포 | preview | preview |
| testflight | 스토어 형식(TestFlight 업로드용) | preview | production |
| production | 스토어 형식 | production | production |

TestFlight와 정식 앱은 각각 다른 설치본/빌드 프로필로 채널을 고정한다. 같은 TestFlight 빌드를 App Store로 출시하면 채널도 그대로 유지되므로 정식 출시는 production 빌드로 준비한다. EAS Build만으로 업로드·내부 테스터 배포가 자동 완료되지는 않는다.

## 최초 적용: 새 설치본 1회 필요

기존 TestFlight `1.0.0(3)`에는 업데이트 기능이 없다. 다음 설치본에 새 모듈과 설정을 포함해야 한다. 현재는 빌드 번호를 올리거나 TestFlight에 새로 업로드하지 않았다.

클라우드 빌드로 진행할 경우:

```bash
eas build --platform ios --profile testflight
```

빌드 성공과 인증·서명 확인 후 해당 빌드 ID를 지정하여 업로드한다. `--latest`로 다른 빌드를 선택하지 않는다.

```bash
eas submit --platform ios --profile testflight --id BUILD_ID
```

기존 Xcode 프로젝트를 계속 사용할 경우, 전체 prebuild/clean으로 덮어쓰지 않고 업데이트 설정만 동기화한다.

```bash
npm run updates:native -- testflight
npx pod-install
```

그 후 앱 버전·빌드 번호·서명·번들 환경값·native `Expo.plist`의 preview 채널을 확인하고 아카이브한다. 업로드는 이전 빌드와 다른 번호(다음 후보 4)를 사용한다. 정식 앱을 로컬로 빌드할 때는 `npm run updates:native -- production`을 실행한다. 이 명령은 생성 파일을 변경하므로 이후 TestFlight 빌드 전 다시 testflight로 동기화한다.

`ios/`, `android/`는 Git 제외된 생성 폴더다. 이번 로컬에서는 설정만 동기화하고 iOS Pod 연결을 실행했다. EAS 클라우드 빌드는 업로드된 Expo 설정에서 네이티브 폴더를 새로 생성하므로 기존 로컬 수동 설정과 빌드 결과의 동등성은 별도 확인해야 한다.

## 이후 작은 수정 발행

검증된 변경에 대해 사용자 배포 승인 후 실행한다. 아래 명령은 이번 작업에서 실행하지 않았다.

```bash
# TestFlight 설치본 대상: preview 채널 + production 환경
eas update --platform ios --channel preview --environment production --message "수정 내용"

# 정식 앱 대상: production 채널 + production 환경
eas update --channel production --environment production --message "수정 내용"
```

`eas.json`의 `build.env`는 OTA 발행에 자동 적용되지 않는다. QA 비활성 값도 EAS 환경에 등록한 이유다. `--environment`는 번들에 사용할 변수만 선택하며 수신 대상을 분리하지 않는다. 내부 preview와 TestFlight는 preview 채널을 공유하므로 동일 런타임이면 같은 업데이트를 받는다. 현재 세 환경의 공개 연결값은 같으며 TestFlight 검증에는 위 production 환경 명령을 사용한다. 추후 서로 다른 서버·환경값을 운용할 경우 채널도 분리한다. 기본 로컬 `.env`에만 기대지 말고 환경을 명시한다.

런타임은 현재 `1.0.0`이다. **네이티브 의존성·권한·SDK를 바꾸면 `expo.version`을 올리고 새 빌드를 만든다.** `buildNumber`만 올려서는 `appVersion` 런타임이 바뀌지 않는다. 호환되지 않는 코드를 기존 런타임으로 발행하지 않는다. JS/스타일 변경만 있을 때는 네이티브 호환성을 확인하고 기존 런타임으로 업데이트할 수 있다.
