# 직원 배포 전 서버·개발 점검

> 이 문서는 수정 전 점검 결과다. 후속 구현·적용 상태는 [보완 적용 문서](배포전-보완-적용-2026-10-20.md)를 참고한다.

- 점검일: 2026-10-20
- 기준: `feature/operations-workflows`, `679c075`
- 대상: 저장소의 서버 함수·SQL 정책·급여 계산·CI·배포 설정
- 상태: 코드 검토 및 가상 데이터를 사용한 로컬 DB 재현 완료. 수정·원격 DB 확인·실제 계정 삭제는 하지 않았다.

## 판단

직원 배포 전에 접근 권한, 매장 간 데이터 격리, 급여 조회 실패 처리, 계정 삭제 흐름을 먼저 보완하는 것을 권한다. 현재 구성만으로 별도 서버를 새로 구매할 필요는 보이지 않는다. Supabase의 권한과 운영 절차를 보강하는 것이 우선이다.

아래는 저장소의 정의를 기준으로 한 판단이다. 실제 Supabase에서 정책이나 함수를 별도로 수정했다면 현재 서버 동작은 다를 수 있다. 기존 SQL 적용 완료와 정책 자체의 적절성은 별개다.

## 1. 직원의 급여·인사 접근 권한 — 배포 전 필수

**확인 결과**

- `supabase/migrations/20260608_role_based_rls.sql:57`의 직원 조회 정책은 승인된 같은 매장 구성원 전체를 허용한다.
- 같은 파일 `:65`의 수정 정책은 일반 구성원에게도 파트타이머 행 수정을 허용한다.
- `supabase/migrations/20261016_manual_work_minutes.sql:133`의 급여 조회, `:53`의 근무시간·급여 변경 이력 조회도 같은 매장 구성원 전체를 허용한다.
- `20261019_payroll_submissions.sql`은 본인 제출 조회와 관리자 급여 쓰기를 제한하지만, 위 급여 조회 정책을 본인 전용으로 바꾸지는 않는다. 직원 계정 연결 보호 트리거도 기본급 변경을 차단하지 않는다.

**로컬 재현**

가상 계정 A·B를 일반 직원으로 승인한 뒤 다음을 확인했다.

1. B가 A의 파트타이머 기본급을 변경할 수 있었다.
2. A가 B의 급여를 조회할 수 있었다.
3. A가 B의 급여 변경 이력을 조회할 수 있었다.

**보완 방향**

- 관리자는 필요한 전 직원 자료, 일반 직원은 본인 급여·제출 자료만 접근하도록 서버에서 제한한다.
- 급여 기준 금액과 직원 계정 연결은 관리자만 수정한다.
- 동료 이름 목록 등이 필요한 경우 급여·연락처가 포함되지 않은 조회 경로를 별도로 제공한다.
- 화면에서 버튼을 숨기는 것과 별개로 DB 요청 자체가 거절되는지 검사한다.

**완료 기준**: 본인·다른 직원·다른 매장·미승인·퇴사·비로그인 계정의 조회/작성/수정/삭제 허용표를 정하고 DB 테스트로 검증한다.

## 2. 매입 등록으로 다른 매장 재고를 수정할 수 있음 — 배포 전 필수

**확인 결과**

`supabase/migrations/20260902_purchase_consolidation.sql:25`는 매입을 생성할 매장의 구성원 여부를 확인하지만, `:60` 이후 재고 변경은 입력받은 재료 ID만으로 실행한다. 그 재료가 같은 매장 소속인지 검사하지 않는다. 이 함수는 `SECURITY DEFINER`로 실행된다.

**로컬 재현**

다른 매장 재고를 직접 조회할 수 없는 일반 직원 계정으로 자신의 매장에 매입을 등록하면서 다른 매장의 가상 재료 ID를 전달했다. 요청이 성공했고 해당 다른 매장의 재고가 10개에서 15개로 증가했다. 다른 매장 재료 ID를 알아낼 수 있다는 점까지 증명한 것은 아니지만, 서버가 매장 간 쓰기를 차단하지 않는 것은 재현했다.

**보완 방향**

- 모든 품목의 재료 소속 매장을 확인한 뒤 전체 매입을 원자적으로 저장한다.
- 잘못된 재료가 한 개라도 있으면 매입과 재고 변경 전체를 취소한다.
- 수량·단가 범위도 서버에서 검증한다.
- `update_purchase_item`은 기존 값을 잠그지 않고 읽어 차액을 반영하므로, 같은 품목의 동시 수정도 검증하고 행 잠금 또는 버전 검사를 추가한다. 동시 수정 문제는 이번 점검에서 실행 재현하지 않았다.

**완료 기준**: 다른 매장 재료 입력 거절, 오류 시 전체 롤백, 같은 품목 동시 수정 후 합계·재고 일치.

## 3. 세금표 조회 실패가 정상 급여 계산으로 이어짐 — 배포 전 필수

**확인 결과**

`lib/services/payroll.ts:52`의 세금표 조회는 연도가 2026으로 고정되어 있다. DB 오류 또는 해당 구간 누락 시 예외를 전달하지 않고 근사 계산값을 반환한다. 호출부는 정상 조회 금액과 추정 금액을 구분할 수 없다. 계산 기준 금액과 조회 결과를 콘솔에도 출력한다.

**영향**: 서버 장애가 급여 계산 실패로 드러나지 않고 추정 세액으로 이어질 수 있다. 과거·다음 연도 급여에 적용할 기준도 명확하지 않다.

**보완 방향**

- DB 오류와 세액표 구간 누락을 구분한다.
- 자동 계산을 중단하거나 명시적인 검토 상태로 두고, 확인 없이 확정되지 않게 한다.
- 급여 대상 월에 맞는 세액표·보험 기준을 선택하고 계산 기준 버전을 보관한다.
- 운영 빌드에서 개인 급여 정보를 콘솔에 출력하지 않는다.

세율·간이세액표의 법적 정확성 전체를 검증한 점검은 아니다. 별도로 공식 자료와 대표 급여 사례를 대조해야 한다.

## 4. 계정 탈퇴와 매장 자료 보존·복구 — 배포 전 필수

**확인 결과**

- `supabase/migrations/20260416_delete_user_data.sql:17` 이후 소유 매장 공용 데이터를 삭제하고, 마지막에 소유 매장 자체를 삭제한다.
- `supabase/functions/delete-account/index.ts:74` 이후 카카오 연결 해제 → DB 자료 삭제 → Auth 계정 삭제 순서로 각각 실행한다.
- 중간 단계 실패 후 이미 완료된 외부 처리를 복구하거나, 단계별로 안전하게 재시도하는 흐름이 명시되어 있지 않다.
- 최근 추가한 급여 제출·이력의 보존 요구와 이 탈퇴 처리를 함께 검증한 근거가 없다.

**보완 방향**

- 일반 직원 탈퇴와 매장 소유자 탈퇴를 구분한다.
- 소유권 이전·매장 폐쇄·개인 계정 해제를 별도 처리하고 자료 보존 기준을 정한다.
- 중간 실패 후 재시도 가능한 상태를 보관하고, 사용자 안내와 개인정보 처리방침을 실제 동작에 맞춘다.

**미확인**: 실제 서버의 외래키 상태에서 어떤 삭제가 차단되거나 연쇄 삭제되는지는 실행하지 않았다. 실제 계정으로 탈퇴를 시험하면 안 되며, 복제한 테스트 환경에서 검증해야 한다.

## 5. POS 이벤트 저장 실패를 성공으로 응답 — 운영 안정성 보완

`supabase/functions/toss-webhook/index.ts:150`의 미매칭 설치 이벤트 큐 저장은 Supabase 응답의 `error`를 검사하지 않는다. 따라서 DB 저장이 실패해도 정상 응답으로 끝날 수 있다. 앞서 기록한 중복 방지 정보가 남으면 같은 이벤트가 다시 와도 처리가 생략될 수 있다.

저장 실패를 감지해 실패 응답·재처리 대상으로 연결하고, 중복 수신·중간 실패·재전송을 시험해야 한다. 웹훅 서명 검증 코드는 존재한다. 실제 POS 제공자의 서명 규격과 배포 환경 설정까지 검증한 것은 아니다.

매출 자동 동기화는 앱의 실행·포그라운드 흐름을 중심으로 구현되어 있다. 앱을 종료한 상태에서도 매출이 갱신되어야 한다면 서버 예약 수집 및 실패 재시도 작업을 별도로 설계해야 한다.

## 6. 개발·운영 체계

| 항목 | 이번에 확인한 상태 | 다음 확인 또는 보완 |
|---|---|---|
| 개발/운영 DB 분리 | 현재 원격 구성 미확인 | 테스트 입력과 실제 급여·매입을 분리하고 빌드별 연결 대상을 확인 |
| 자동 검사 | CI는 타입 검사와 Jest 실행 | DB 권한·마이그레이션·서버 함수 테스트 추가 |
| 기존 SQL 검사 | 로컬 PGlite의 축약 스키마로 운영 흐름 검사 | 전체 스키마와 권한 조합 검사까지 확장 |
| 실제 기기 검증 | 직원·관리자 전체 흐름 완료 근거 없음 | 초대/승인, 본인 시간 제출, 반려/재제출, 급여 반영, 매장 전환을 양 OS에서 확인 |
| 장애 추적 | 앱·lib에서 중앙 오류 수집 도구 연결 확인 못 함 | 개발자용 오류 추적, 연동 실패 알림, 개인정보 제거 설정 |
| 백업/복구 | 원격 설정과 복구 성공 여부 미확인 | 백업 주기·보관 위치·복구 담당자 확정, 테스트 환경 복원 시험 |
| 원격 서버 함수 | 배포된 버전·필수 비밀키·설정 미확인 | 저장소 버전과 배포 버전을 대조하고 테스트 이벤트로 확인 |
| 배포 설정 | `eas.json` iOS 제출 식별자 공란 | 실제 계정·프로젝트 연결 및 서명된 배포 빌드 검증 |

백업 제공 범위는 Supabase 요금제에 따라 다르며 DB 백업과 Storage 원본 파일 백업도 구분해야 한다. [Supabase 백업 안내](https://supabase.com/docs/guides/platform/backups)

실제 서버에서는 Security Advisor와 정책, 성능·가용성 설정도 확인한다. [Supabase 운영 배포 점검표](https://supabase.com/docs/guides/deployment/going-into-prod)

## 재현 범위와 한계

- 임시 PGlite DB, 가상 UUID와 가상 급여·재고만 사용했다. 원격 연결이나 운영 데이터 조회·수정은 하지 않았다.
- 기존 `scripts/validate-operations-sql.mjs`의 축약 스키마와 10월 전환 SQL을 기반으로 실제 직원 RLS 정의 및 매입 RPC 정의를 추가해 실행했다.
- 직원 기본급 수정·타인 급여 조회·타인 이력 조회·다른 매장 직접 조회 차단·다른 매장 재고 우회 수정의 5개 확인을 실행했다.
- 전체 마이그레이션을 처음부터 재생한 결과는 아니므로, 실제 서버 정책·함수 정의를 대조하는 후속 검증이 필요하다.
- 이번 작업은 점검 문서 작성까지다. 앱 코드·SQL 수정, 원격 SQL 적용, 배포는 하지 않았다.

## 권장 순서

1. 직원별 권한과 매장 간 쓰기 차단을 수정하고 DB 권한 테스트를 추가한다.
2. 급여 조회 실패 처리와 탈퇴·자료 보존 흐름을 보완한다.
3. POS 이벤트 실패 복구, 개발/운영 분리, 백업·오류 추적을 준비한다.
4. 복제한 환경에서 직원·관리자 흐름을 확인한 뒤 소수 직원에게 테스트 배포한다.
