## PM/PL에 전달할 범위 판정

파일 목록과 manifest를 독립 대조했다. `_layout.tsx`를 제외한 **41개 라우트와 명세 41개가 일치**하며 빠지거나 추가된 라우트는 없다. 화면 목록 완전성과 모든 기능·상태의 검증 완료는 별개다. 모달·하위 패널 10개는 주 문서 M01~M10과 연결한다.

명세에서 반드시 보정할 사항:

- **S21 알림 설정은 개인 설정이 아니라 매장 공통 설정**이다. `lib/services/notifications.ts:49`는 store_id로 읽고 `:61`은 store_id+setting_key로 upsert한다. 화면도 `app/notifications/settings.tsx:48`에서 매장 단위라고 안내한다. 본인만 영향을 받는다고 작성하면 부작용 범위를 축소하게 된다.
- **S26 수기 매출은 같은 매장·같은 날짜를 덮어쓰는 upsert**다 (`lib/services/manualSales.ts:21`, `:43`). ‘추가’ 버튼을 여러 번 누르면 새 기록이 증가하는 것이 아니라 같은 날 값을 교체한다. 할인액은 현금·카드 순매출에 이미 반영된 것으로 취급하고 다시 차감하지 않는다 (`:58`). 테스트는 전용 매장/날짜만 사용해야 한다.
- **S30 레시피 상세는 수정 버튼을 모든 진입 사용자에게 표시**, 삭제 버튼만 currentRole 관리자 조건을 둔다 (`app/recipes/[id].tsx:81`, `:137`). 파트타이머의 직접 진입은 루트/서버까지 별도로 확인한다.

## 직접 경로·권한 검토

`app/_layout.tsx:54`의 현재 경로 보호는 재무 비허용 경로와 비관리자의 `/admin`, `/profit-loss`, `/settings/pos-sync`에 집중된다. 따라서 메뉴가 보이지 않는 것만으로 S10(청소편집), S17(요청함), S22(정산), S32(레시피 등록), S35(멤버), S38(영업일), S39(매장 정보)의 직접 진입을 거부한다고 말할 수 없다. 실제 역할 계정으로 화면 접근·데이터 조회·쓰기 거절까지 분리해서 검증해야 한다. 이 검토는 RLS 취약점을 확정하지 않는다.

S13/S14는 로그인 화면에서 링크로 노출되지만 루트 인증 effect(`app/_layout.tsx:44`)의 초기 비로그인 분기는 로그인 이외 경로를 로그인으로 전환한다. effect 의존성이 `[loading,user,store]`여서 일반 링크 이동과 새 딥링크 시작은 동작이 다를 수 있다. **로그인 화면 링크 탭과 앱 종료 후 법률 경로 직접 시작을 서로 다른 시나리오로 둔다.** 모든 법률 링크가 항상 막힌다고 단정하지 않는다.

## QA 보완 우선순위와 완료 기준

1. UX01~UX03 실패→재시도/복구를 mock 응답으로 자동화한다. 각각 ‘성공 데이터 도착 후 오류 해제’, ‘설정 실패 시 서버값과 일치’, ‘조회 실패를 빈 목록과 구분’을 검증한다.
2. S26 같은 날짜 upsert와 S21 매장 공통 설정은 테스트 데이터 범위 선언에 포함한다. 기존 매장 값을 시험 대상으로 쓰지 않는다.
3. 관리자로 보이는 개발 미리보기 대신 실제 승인 정규직·파트타이머·대기·거절 계정으로 직접 경로를 확인한다. DB 변경까지 수반하는 권한 검증은 서버/DB 담당 결과와 결합한다.
4. iOS·Android 키보드, 안전영역, 스크롤, 접근성 라벨, 더보기/FAB 위치는 실제 빌드에서 기록해야 한다. 웹 결과나 코드 스타일 검토를 네이티브 통과로 올리지 않는다.

이 독립 검토는 읽기전용 조사 완료다. 제품 수정·DB 변경·실제 계정 로그인·E2E 실행은 수행하지 않았고, 남은 항목은 거절된 작업이 아니라 미실행 검증이다.
