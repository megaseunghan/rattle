# 공통 UI 기준 스킬과 전체 화면 UI/UX 검토 (의도 확정본)

**확정:** 2026-11-25, 사용자 명시적 "예" (grilling, Q1~Q12)

## 목표 (Why)

최초 매장 생성·합류 시안을 다듬으면서 같은 역할의 UI(날짜 고르기, 밀어서 삭제, 휠 등)가 시안마다·앱과 시안 사이에 다르게 나오고, 디자인이 어딘가 부족하다는 느낌이 반복됐다. 공통 UI 기준을 세워서

1. 시안끼리 같은 상황에 다른 UI가 나오지 않게 하고,
2. 시안과 실제 앱 구현이 어긋나지 않게 한다.

그 기준의 근거를 얻기 위해 먼저 앱 전체 화면을 하나씩 세밀하게 UI/UX 검토한다.

- 대상: 사용자 본인(디자인 결정자), 이후 화면·시안 작업을 하는 모든 세션·에이전트

## 시각 방향 다시 찾기 (2026-11-25 추가, 사용자 확정 — grilling 2차 Q1~Q11)

- 왜: 사용자가 컴포넌트 모양·배치·배경·서체 등 **앱 전체(홈 포함)의 구성 자체**가 마음에 들지 않음. 현재 `DESIGN.md`·플레이북 기준으로만 검토하면 "지금 디자인을 더 지금답게" 다듬는 데 그친다. 그래서 검토를 둘로 나눈다.
  - **바꾸지 않는 사용성 규칙**(44pt, 대비, 키보드, 오류 위치, 입력 보존, 화면 읽기, 해요체) → Fable 검토(방향과 무관하게 유효)
  - **취향**(모양·배치·배경·서체·색·아이콘) → 현재 기준으로 판정하지 않고 새 방향을 찾는다
- 다시 여는 것: 서체(Wanted Sans+Geist 2종 규칙 포함), 색, 배경(연파랑 캔버스·글래스), 카드 모양·모서리·그림자, 배치(홈 2×2 금액 등), 아이콘 스타일. AGENTS.md의 승인 방향(B안 따뜻한 분위기 + A안 2×2)과 플레이북 §0(홈 S04가 기준 화면)도 재검토 대상.
- 고정: 기능·권한·데이터 의미(미확인 ≠ 0원 등), 바꾸지 않는 사용성 규칙, 앱 이름 Rattle·공식 로고(Apple·Kakao·Toss), 해요체 문구.
- 찾는 방법(세 가지 모두): ① 래틀 전체 캡처에 좋음·싫음·애매함 표시(노션 화면별 페이지의 '느낌' 속성) ② 레퍼런스 보드 — 비슷한 앱(같은 사용자: 캐시노트·토스플레이스 사장님·배민사장님 / 숫자 보기: 토스·뱅크샐러드·Copilot Money·Mercury / 근태: 시프티·알밤·7shifts·Homebase / 매장 도구: Square·Toast)의 **앱스토어 공개 스크린샷**으로 결 3가지(금융 미니멀·업무 도구·따뜻한 생활)로 묶어 노션에만 둔다. 끌리는 앱은 사용자가 휴대폰에서 직접 캡처 ③ 같은 화면을 다른 방향으로 그린 시안 비교.
- 대표 화면: 홈(S04, 숫자 보기)과 새 매장 만들기(S02, 입력). 방향 **3개**를 같은 가상 자료·같은 모바일 폭으로 만들고, 고른 방향 안에서 세부를 1~2회 좁힌다.
- 확정 기준: 두 화면 시안이 같은 방향으로 둘 다 마음에 들고 사용자가 "이걸로"라고 하면 확정. 확정 시 기초 값 표(색·서체·배경·모서리·그림자·아이콘)를 함께 만든다.
- 기존 문서: 확정 전까지 `DESIGN.md`·플레이북·AGENTS.md 승인 방향 문구 유지(현재 앱 기준). 확정 뒤 기초 값을 갱신하고 기존 결정은 지우지 않고 '대체됨'으로 남긴다.
- 온보딩 12차 시안: 방향 확정까지 보류, 확정된 방향으로 다시 그린다.

## 진행 순서 (2026-11-25 갱신, 위 추가 결정 반영)

1. 검토 모델 시험 — 완료(아래 진행 기록)
2. 전체 화면 캡처(아래 원래 2번 조건 그대로)
3. 같이 진행: Fable 사용성 검토(점검 항목 보강) + 사용자 좋음·싫음 표시 + 레퍼런스 보드
4. 방향 시안 3개(홈·S02) → 좁히기 → 방향 확정·기초 값 표
5. UI 기준 스킬 작성(확정된 방향을 「현재 취향」으로) + 기준 문서 갱신안

노션 페이지 구성안은 쓰기 전에 사용자 승인. 아래 원래 순서는 단계별 세부 조건으로 유지한다.

## 진행 순서 (최초 확정본)

1. **검토 모델 시험** — 기존 실제 앱 캡처 3장(`docs/private/onboarding-design/current/`의 S02 새 매장 1단계, S02 2단계 오류, S03 참여코드 입력)을 Fable 에이전트와 새 Opus 에이전트에 같은 지시·같은 출력 형식(위치·문제·근거 원칙·고칠 방향·심각도)으로 서로 모르게 검토시킨다. 지시에는 닐슨 10원칙(`DESIGN.md`), `.agents/roles/design-playbook.md`, 화면 코드 경로를 넣는다. 결과를 실제 캡처·코드와 대조해 맞는 지적/틀린 지적/막연한 지적/한쪽만 찾은 지적으로 나눠 표로 보여 주고, 전체 검토에 쓸 쪽은 사용자가 고른다.
2. **전체 화면 캡처** — 화면 명세의 S·M 화면 전부를 사장님 기준으로, 역할(정규직·파트타이머)마다 다른 화면만 추가. iOS 시뮬레이터·QA 계정·가상 자료, 저장 없음. 빈 화면·오류 상태는 이미 그 상태인 화면만.
3. **화면별 세밀 검토** — 결과는 노션 「래틀 컴포넌트 디자인 UI | UX 레퍼런스」(승한 개인 작업자료 아래) 맨 아래 '화면 검토 결과'에 화면별 하위 페이지(캡처·지적·결정)로 정리.
4. **UI 기준 스킬 작성** — 저장소 `.agents/skills/`에 새 스킬. `AGENTS.md` UI/UX 절에 "모든 화면·시안 작업 전에 이 스킬을 읽는다"를 넣어 전역으로 적용.

## 스킬 구성 (확정)

- 역할 분담: `DESIGN.md` = 분위기·색·서체 기초 값, `design-playbook` = 문구·원칙, `rattle-design-dialogue` = 진행 절차, 새 스킬 = "어떤 상황에 어떤 컴포넌트·인터랙션을 쓰는가". 겹치는 내용은 가리키기만.
- 범위: 온보딩 시안에 나온 것 + 현재 앱 공통 컴포넌트(`lib/components/`, `lib/components/ui/`).
- 컴포넌트마다: 언제 쓰는지/쓰지 않는지(대신 쓸 것), 모양(크기·간격·토큰·터치 영역), 상태(기본·누름·선택·비활성·오류·로딩), 인터랙션(누르기·밀기·끌기·키보드·화면 읽기), 문구, 앱 컴포넌트 경로(없으면 '미구현'), **같은 역할의 다른 패턴 이름과 검색어**(사용자가 패턴 이름을 몰라도 찾을 수 있게), 레퍼런스.
- 시안 HTML 조각은 스킬 안 `snippets/`에 따로 두고 SKILL.md 본문은 짧게.
- 레퍼런스 원본은 노션 페이지의 컴포넌트 데이터베이스(이름·분류·다른 패턴/검색어·상태·결정일·앱 경로, 각 행에 사용자 레퍼런스와 가져올 것/가져오지 않을 것). 맨 위에 '레퍼런스 찾는 요령'(패턴 이름으로 찾기, 비슷한 사용자의 앱 먼저, 공식 가이드로 확인, 2~3개 비교, 움직임은 영상). 스킬은 노션을 가리키고 규칙·조각만 가진다. 레퍼런스 이미지는 저장소에 넣지 않는다.
- 기준의 성격: **바꾸지 않는 규칙**(44pt 터치, 대비, 키보드·화면 읽기, 오류 위치)과 **현재 취향**(모양·간격·움직임, 결정일 기록, 최신 결정이 이김)을 나눈다. 고정된 완성 기준은 두지 않고, 첫 판 작성 + 확인 필요 목록이 드러나면 1차 끝.
- 시안끼리·앱과 다른 경우: 통일안만 적고 '확인 필요'로 두며 확정은 사용자가 한다.

## 하지 않을 것 (Out of scope)

- 앱 코드를 스킬에 맞춰 고치지 않는다(별도 작업).
- 원격 DB 변경·배포·push 없음. 캡처 중 서버 쓰기 없음.
- 앱 전체를 역할별로 같은 화면까지 반복 캡처하지 않는다.
- 기존 클라우드 스킬 `rattle-design-system`이나 `DESIGN.md` 컴포넌트 절에 내용을 몰아넣지 않는다.
- 검토 의견을 그대로 결정으로 쓰지 않는다(대조 후 사용자 결정).
- 새 시각 방향을 실제 앱 화면에 적용하지 않는다(별도 작업). 방향 시안 확정은 앱 구현 승인이 아니다.
- 방향 확정 전에 `DESIGN.md`·플레이북·AGENTS.md 승인 방향을 고치지 않는다.
- 레퍼런스 앱 화면을 그대로 베끼지 않는다(결·패턴만 가져온다). 레퍼런스 이미지는 저장소에 넣지 않는다.

## 4단계 홈 정책 (2026-11-26 확정, grilling Q1~Q11)

**목표(Why)**: 매일 여는 사람(점장·직원·파트타이머)이 "오늘 뭐 해야 돼?"에 바로 답을 얻고, 사장님은 손익·직원 스케줄·원가를 아래쪽에서 확인한다.

- 정체: 오늘 할 일 + 지금 상태. 전체 바로가기 목록은 더보기 서랍으로.
- 뼈대 하나, 칸은 역할 이름이 아니라 **본인 직원 기록·매장 관리 권한·손익 공유 권한**에 따라 붙는다. 매장에서 일하는 사장님은 직원 칸 + 사장님 칸.
- 순서 원칙 유지: 오픈 준비 → 영업 중 → 마감 정리. 현재 코드에서 할 일보다 위에 있는 손익 카드는 아래로.
- 화면 순서: ① 맨 위 알림 한 줄 ② 출퇴근(본인 직원 기록) ③ 오늘 근무자(모두, 한두 줄로 작게, 누르면 바텀시트) ④ 시간대 칸(기존 홈 업무 편집 바로가기·체크리스트) ⑤ 오늘 매장·오늘 매출(관리 권한) ⑥ 이번 달 손익 요약(접힘, 펼치면 2×2, 손익 권한) ⑦ 내 것(내 스케줄·내 급여·근태).
- 알림: 가장 급한 것 하나만 한 줄 + "외 n건", 누르면 바텀시트(항목별 닫기·입력하러 가기). 기존 경고 배너(고정비·토스 미동기화·월마감)를 여기로 합침.
- 오늘 근무자: 이름·근무 시간·출근 여부만. 시급·급여·연락처는 넣지 않음.
- 시각 방향: 뱅크샐러드 뼈대(흰 바탕·큰 숫자·조용한 카드), 온기는 말투와 강조색 하나. 그라데이션 배경 제외. 승인된 'B안 따뜻한 분위기'를 다시 연 결정이라 S04 시안을 A(뱅크샐러드)·B(기존 B안)로 나란히 비교해 확정.

**하지 않을 것(Out of scope)**
- 새 기능 구현: 오늘 근무자 칸 동작, 대타 신청, 손익 펼침 안 원가율, 매출 빠진 날 알림 등은 노션 '6. 이번 아님 — 기능 후보'에 두고 시안에는 예시로만 그린다.
