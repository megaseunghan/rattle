# 앱 속도 측정 — 요청 순서 줄이기 기준선 — 확정 의도

- 확정일: 2026-11-24 · 확정자: 사용자(승한) · 인터뷰(grilling) 결과 v1
- 출발점: BreakingBreach 「Vibe-Coded App Too Slow? 31 Ways to Speed It Up」(https://www.youtube.com/shorts/8JsFi_ZOvio) 31개 항목을 Rattle에 대입한 검토(2026-11-23 세션)
- 기준 커밋: `main` 2b1d4c8 (작업 트리에 사용자 쪽 `package-lock.json` 미커밋 변경 있음, 건드리지 않음)

## 목표 (Why)

- 고칠 방향은 **요청 순서 줄이기(순차로 기다리는 요청 겹수 축소)**로 정했다. 서버 지역은 이미 서울(`ap-northeast-2`, `docs/개인정보처리방침-보완안-2026-11-14.md:10`)이라 지역 이전은 후보에서 뺐고, 서버 사양 변경은 이번 판단 대상이 아니다.
- 이번 측정은 고치기 전 **기준 숫자**를 남기고, **어떤 순차 구간부터 끊을지** 정하는 데 쓴다.

## 범위

- 측정 순간(우선순위): ① 탭 이동 — 매입 탭, 인건비 탭 ② 앱 시작 → 홈이 데이터를 다 보여 줄 때까지. 저장 버튼 반영은 제외.
- 탭은 **첫 진입(캐시 없음)**과 **재진입(캐시 있음)**을 나눠 각 5회 측정.
- 환경: Mac iOS 시뮬레이터 + 원격 개발 DB(실기기는 지금 사용 불가 → 나중에 가능할 때 추가). Network Link Conditioner 등 Mac 시스템 설정은 바꾸지 않는다.
- 주요 지표: **순차 겹수**, **요청 수**. 시간(ms, 중간값·최댓값)은 시뮬레이터가 실제 폰보다 빠르므로 참고 지표.
- 측정 방법(승인됨):
  - 앱: 개발 빌드에서만 켜지는 요청별 시작·끝 시각 기록. 측정 브랜치 `chore/perf-measure`에만 두고 커밋하지 않으며 측정 후 제거.
  - 서버: 원격 개발 DB에서 `pg_stat_statements` **조회(SELECT)만**. 쓰기·설정 변경 없음.
- 코드 조사로 이미 나온 가설(실행 확인 전, 측정으로 검증할 것):
  - 홈: 순차 5겹, 요청 약 22~24개(매장 1개 기준). 가장 긴 경로 두 개 — 매장 목록 → 권한 → 재무 요약 → 재무 접근 확인 → 일별 RPC 6개 / 매장 목록 → 권한 → 직원 → 시급 → 출퇴근.
  - 매입 탭: `readAllRows`가 0행일 때만 멈춰 목록마다 최소 2회 연속 요청(`lib/services/readAllRows.ts:8`), 카테고리 2회 중복, 비용 최대 3겹.
  - 인건비 탭: 직원 → 시급 2겹, 홈과 다른 캐시라 직원 재조회.
  - 끊기 후보: 부트스트랩에 권한 합치기(−1겹), 재무 접근 확인과 일별 RPC 동시 호출(−2겹), 권한 응답의 `employee_id`로 출퇴근 조회 앞당기기, `readAllRows` 500행 미만이면 종료.

## 완료 기준

1. 탭별·홈 요청 순서표(무엇이 무엇을 기다리는지, 실측 근거)
2. 끊을 수 있는 순차 구간 후보와 각각 줄어들 예상 겹수
3. 고치기 전 기준 숫자: 겹수, 요청 수, 시간 중간값·최댓값(첫 진입/재진입 구분)
4. 고친 뒤 같은 방법으로 다시 잴 수 있도록 측정 방법 기록
5. 결과 기록: `docs/workspaces/`의 작업계획 MD + Notion 기능별 진행 상황 페이지 요약

## 하지 않을 것 (Out of scope)

- 코드 수정(요청 순서 개선 구현 포함) — 측정 결과를 본 뒤 새로 정한다
- 서버 사양 변경, DB 지역 이전
- EAS 발행, 원격 DB 쓰기·마이그레이션 적용
- 저장 버튼 반영 속도, 뼈대 화면·낙관적 업데이트
- 측정용 기록 코드의 커밋·main 반영
