# 의도: POS 매출 요약 재사용 시간 (2026-11-24 사용자 확정)

## 목표(Why)

재진입 캐시(#150) 이후에도 POS 매출 조회(오늘 매출·월 일별 요약·품목)는 예전 30초 기준이 남아 있다. 그래서 관리자가 1분 안에 홈으로 돌아와도 요청이 2~3건 나간다.

POS 매출은 토스 웹훅이 아니라 앱의 동기화(기기별 최근 30분·과거 보정 6시간 제한, 수동 조회)로만 DB에 들어온다. 내 기기의 동기화가 끝나면 `invalidateStoreData(storeId, ['pos','financial'])`로 바로 무효화된다. 따라서 30초 기준이 실제로 지키는 것은 "다른 기기가 동기화한 결과를 늦게 보지 않기"뿐이다. 매출 자료는 이미 최대 30분 늦으므로 이 기준을 재진입 캐시 시간표에 맞춰 늘려 요청 수를 줄인다.

## 결정

- 적용 범위: 아래 세 조회 모두 `lib/query/staleTimes.ts` 시간표를 따른다.
  - 오늘 매출: `useTossSync`의 `pos/today`, 홈 카드·매출 탭 상단
  - 월 일별 요약: `usePosAnalytics`의 범위 요약
  - 품목별 매출: `usePosAnalytics`의 품목
- 재사용 시간
  - 오늘 매출: 5분
  - 월 일별 요약·품목: 이번 달 범위 5분, 지난 달(마감된 달) 범위 30분. 홈 손익 카드의 이번 달/지난 달 규칙과 같다.
- 강제 조회 유지: 당겨서 새로고침과 매출 탭 "조회" 버튼은 지금처럼 재사용 시간과 상관없이 항상 다시 받는다(`force ? 0`).
- 반영 방식: 작은 별도 PR(브랜치 `fix/pos-stale-times`, main `cdd1b97` 기준)로 낸다. 스켈레톤 PR보다 먼저 또는 함께 main에 병합해, 스켈레톤 병합 뒤 main에서 한 번에 하는 EAS Update에 포함한다.

## 완료 기준

- 세 조회의 30초 상수를 시간표 값으로 바꾸고, 이번 달/지난 달 구분은 조회 범위 기준으로 판정한다.
- Jest로 다음을 확인한다.
  - 재사용 시간 안의 재진입은 다시 요청하지 않는다.
  - 강제 조회는 항상 다시 요청한다.
  - 동기화가 끝난 뒤의 무효화는 바로 반영된다.
- `npx tsc --noEmit`, 관련 Jest, 전체 Jest를 통과한다.
- 시뮬레이터 관리자 계정으로 1분 안 홈 복귀와 매출 탭 재진입의 요청 수를 확인한다. 기준은 #150 검증 때 홈 복귀 2~3건, 매출 재진입 1건이다.

## 하지 않을 것(Out of scope)

- 토스 주문 동기화 주기 변경(최근 30분·과거 보정 6시간)
- 토스 웹훅에 주문 실시간 기록 추가, Realtime, 서버 RPC
- "n분 전 기준" 같은 새 화면 표시
- 재진입 캐시 검토의 나머지 항목(M-2, L-1~L-4)
- PR 생성·병합·EAS 발행은 각각 사용자 확인 후 진행한다
