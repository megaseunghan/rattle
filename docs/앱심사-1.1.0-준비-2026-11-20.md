### 로그인 접근 문제와 대안

현재 코드의 제공 수단은 카카오·Google·Apple이다. 앱/서비스 검색에서 `signInWithPassword`·`signInWithOtp`와 이메일 입력 화면을 찾지 못했다. Supabase가 이메일 인증을 지원한다는 사실만으로 현재 앱에 이메일 로그인이 있다고 안내하면 안 된다. QA broker는 `127.0.0.1:18765` + 시뮬레이터 제한이라 심사 접근 수단이 아니다.

## 6. 제출 절차 체크리스트 — 실행 담당자용, 이번 과제 미실행

### A. 제출 전 고정

- [ ] 조정자가 실제 ASC 상태를 확인: 앱 `6825832614`, bundle `com.seunghan.rattle`, 공개 버전 레코드·최대 빌드 번호·기존 심사 계정 적용 여부. 공개 심사/승인 여부는 과거 내부 배포 기록으로 단정하지 않음.
- [ ] 표시 버전 **1.1.0**, `app.json:16`의 로컬 buildNumber는 현재 **4**. 저장소 기록에도 빌드 4가 이미 있어 단순 재사용 금지. ASC/EAS에서 충돌 없는 번호 확정(최소 5 이상 후보이며 현재 최대값보다 큰 값 권장). EAS `autoIncrement:true` 결과와 실제 CFBundleVersion 확인.
- [ ] OCR 숨김 반영, 개인정보 안내 갱신, 기존 심사 계정 접근 검증, QA 가상 데이터 확인. 실제 출시 소스 커밋·dirty 포함 여부를 고정하고 앱/서버 버전을 대응시킴.
- [ ] Xcode 26+/iOS 26 SDK+ 요구사항 및 최신 인증서/계약 상태 확인. [Apple SDK 최소 요건](https://developer.apple.com/news/upcoming-requirements/?id=04282026a). 이번에는 도구 버전·서명을 조회/변경하지 않음.
- [ ] 실제 iPhone/iPad에서 소셜 로그인·재실행·권한 거절/복구·증빙 업로드/재시도·QR 등록/해제·계정 삭제·역할 차단 검사. 계정 삭제는 승인된 폐기 가능 기존 계정만 사용. 원격 RPC/RLS/Storage 적용 여부를 담당자 증거로 확인.

### B. 빌드 경로 선택

| 방법 | 승인 후 실행 예시 | 확인할 결과 |
|---|---|---|
| EAS production 클라우드 | `eas build --platform ios --profile production` | `eas.json:29` 기준 production 환경·채널, QA_LOGIN=0, 실제 1.1.0/새 빌드 번호, 서명·DB 연결. 기존 키·자격증명 재사용 가능 여부 먼저 확인 |
| 기존 Xcode 로컬 archive | 승인된 기준 소스를 native 프로젝트에 반영 → Release/실기기 대상 Archive → Organizer Validate/Distribute App → App Store Connect Upload | Expo 설정과 native Info.plist·프로젝트 버전/권한·채널·runtime의 일치. 과거 export 옵션을 그대로 재사용하지 않음 |

두 경로 중 하나를 선택한다. **과거 `testFlightInternalTestingOnly=true` 아카이브는 공개 App Store 심사 빌드로 재사용하지 않는다.** `docs/archive/2026-10/EAS-첫배포-2026-10-30.md`의 내부 전용 기록과 현재 목적이 다르다. 생산용 DB 분리는 요구하지 않지만 production 빌드의 실제 DB 대상은 사용자 확정한 개발 DB와 일치해야 한다.

app.json 기본 업데이트 헤더는 preview이고 production 프로필은 production이다. 로컬 archive는 특히 `scripts/configure-native-updates.cjs` 등 실제 설정 경로와 최종 산출물을 대조한다. runtime은 appVersion 정책으로 1.1.0이 기대값이나, 최종 manifest로 검증한다. 이 체크리스트는 채널 변경이나 OTA 발행 승인이 아니다.

### C. 업로드·ASC 메타데이터

1. 승인된 IPA를 `eas submit --platform ios --profile production` 또는 Xcode Organizer로 업로드한다. 결과불명 업로드는 ASC 조회 후 재시도하며 중복 업로드하지 않는다. [Expo iOS 제출 안내](https://docs.expo.dev/submit/ios/).
2. ASC → 나의 앱 → Rattle → App Store의 iOS 버전에서 **1.1.0** 레코드를 확인/준비한다. 기존 공개 심사 전 1.0.0 초안이 남았다면 새 버전 추가 가능 상태와 버전 필드 편집 가능 여부를 확인한 후 1.1.0으로 맞춘다. 이미 존재하는 레코드는 중복 생성하지 않는다.
3. 처리 완료 빌드를 연결하고 1.1.0/빌드 번호·App Store 사용 가능 상태를 확인한다. TestFlight ‘테스트 중’은 App Store 심사 접수나 승인 상태가 아니다.
4. 한국어 앱 이름·설명·키워드·카테고리·저작권·스크린샷·지원/개인정보 URL·가격/배포 지역을 확인한다. 사업자용이라는 설명과 로그인 후 이용 조건을 명시한다.
5. 앱 심사 정보 → 로그인 필요 표시 → **기존 검증 계정** 정보를 비공개 필드에 입력. 연락처, 한/영 메모, 두 기기 동작 영상 첨부. 대괄호/임시 안내를 모두 제거한다.
6. App Privacy를 §2와 SDK/운영 확인 결과로 확정한다. 연령 등급은 **현재 ASC의 갱신된 설문**을 실제 콘텐츠에 맞춰 답한다. 업무용·급여 데이터만으로 특정 등급을 임의 지정하지 않는다. 광고/메시지/사용자 콘텐츠 공유/웹 접근의 실제 범위를 확인한다.
7. 수출 규정: `app.json:18`은 `ITSAppUsesNonExemptEncryption=false`. HTTPS·OS 암호화 외 QR HMAC/SHA 구현과 `@noble/hashes` 등 전체 의존성을 확인하고 면제 요건을 판단한다. 암호화를 사용하지 않는다고 무조건 답하지 않음. 자체 독점 암호 여부·문서 필요 여부를 [Apple 수출 규정](https://developer.apple.com/documentation/Security/complying-with-encryption-export-regulations)과 [키 정의](https://developer.apple.com/documentation/BundleResources/Information-Property-List/ITSAppUsesNonExemptEncryption)에 따라 확인.
8. 빠진 정보·계약·경고를 해결하고, 자동/수동 출시 정책을 사용자와 확정한다. 심사에 추가 → 최종 심사 제출은 별도 실행 권한 하에 진행한다. 이번 과제에서는 버튼을 누르지 않았다.

## 7. 최종 인수인계와 검증 기록

3. 개인정보 운영 주체·보관 기간·공동 자료 보존/삭제 기준과 SDK/위탁 처리 범위 최종 확정. 앱·웹 안내 수정 및 공개 적용 담당 지정.
4. EAS production 또는 로컬 archive 선택과 새 빌드 번호·배포 채널. 실제 빌드/업로드/심사 제출 실행 범위 및 출시 방식(공개/Unlisted 등)·가격·지역. 이번 과제의 문서 승인으로 대신하지 않는다.
5. iPad 지원 유지에 필요한 실기기 검증·캡처 담당(현재 true 유지). OCR 완전 숨김은 이미 확정되어 재승인하지 않는다.
