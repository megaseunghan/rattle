# Google·Apple 로그인 설정

## 적용 상태와 범위

- 카카오 로그인은 유지하고 세 로그인 버튼을 모든 플랫폼에 동일하게 표시한다. Google은 iOS·Android·웹 브라우저 OAuth를 사용한다. Apple은 iOS에서 기본 인증 창을 사용하고 Android·웹에서는 Apple 웹 OAuth를 사용한다.
- 브라우저 OAuth는 PKCE와 기존 공통 콜백 검증을 사용한다. 취소는 오류로 표시하지 않고 인증 중 다른 버튼의 중복 실행을 막는다.
- Apple은 임의 nonce의 SHA-256을 Apple에, 원문을 Supabase에 전달한다. 이름은 최초 승인 때 제공되는 경우에만 저장한다.
- 10월 20일 기존 SQL 01·02·03은 사용자가 적용 완료했다고 안내했다. **이번 확장에 추가 SQL은 없다.**
- 2026-10-21에 `delete-account` 버전 11을 실제 서버에 배포했다. 상세 결과는 `탈퇴-함수-배포-확인-2026-10-21.md`를 따른다. Provider 콘솔 설정과 실제 계정 로그인·탈퇴 검증은 별도 확인이며, Apple Developer·Google Cloud 계정은 사용자가 준비했다고 안내했다.

## 1. Google 설정

현재 공식 문서 기준 절차다. 개인 콘솔의 설정값을 직접 확인하거나 수정한 상태는 아니다.

1. Supabase 대상 프로젝트 → **Authentication → Sign In / Providers → Google**에서 Callback URL을 복사한다. 형식은 `https://YOUR_PROJECT_REF.supabase.co/auth/v1/callback`이다.
2. Google Cloud 대상 프로젝트 → **Google Auth Platform**에서 **Branding**(앱 이름·지원 이메일), **Audience**(사용 대상), **Data Access**를 설정한다. 로그인에는 기본 이메일·프로필만 사용하고 Drive·Calendar 권한은 요청하지 않는다. 외부 앱이 Testing 상태라면 사용할 직원 계정을 테스트 사용자에 등록한다.
3. **Clients → Create client → Web application**을 선택한다. 이번 구현은 Supabase가 Google 코드를 처리하므로 Web 클라이언트를 사용한다.
4. **Authorized redirect URIs**에 1번에서 복사한 Supabase Callback URL을 등록한다. 여기에 `rattle:///`를 넣지 않는다.
5. 발급받은 **Client ID·Client Secret**을 Supabase Google Provider에 입력하고 활성화·저장한다. Client Secret을 앱 환경 변수나 Git에 넣지 않는다.
6. Supabase **Authentication → URL Configuration → Redirect URLs**에서 `rattle:///`를 허용한다. 기존 `rattle://**` 설정이 이 주소를 허용하는지도 확인한다. 이 주소는 Supabase에서 앱으로 돌아오는 주소다.
7. Expo Go 대신 Rattle 개발 빌드 또는 배포 빌드에서 로그인 후 원래 앱으로 돌아오는지 확인한다. 시뮬레이터는 `xcrun simctl openurl booted 'rattle:///'`로 앱이 열리는지 먼저 확인한다. 실패한다면 Provider 설정보다 앱 설치·URL scheme 등록을 먼저 확인한다.

근거: [Supabase Google 설정](https://supabase.com/docs/guides/auth/social-login/auth-google), [Redirect URL 설정](https://supabase.com/docs/guides/auth/redirect-urls).

## 2. Apple 설정 — iOS 기본 인증, Android·웹 브라우저 OAuth

앱 Bundle ID는 `com.seunghan.rattle`이다.

1. Apple Developer → **Certificates, Identifiers & Profiles → Identifiers**에서 Bundle ID `com.seunghan.rattle`인 명시적 App ID를 연다. 목록에 없다면 이 Bundle ID로 App ID를 먼저 등록한다. **Sign in with Apple → Configure**에서 처음 설정하는 앱이면 **Enable as a primary App ID**를 선택하고 저장한다. 이미 다른 primary App ID에 묶인 상태라면 Services ID 연결 목록에 표시되지 않을 수 있다.
2. **웹·Android Apple 로그인용**으로 Apple Developer → **Identifiers → + → Services IDs**에서 Services ID를 별도로 만든다. 여기서 App IDs를 새로 만드는 단계가 아니다. 예: `com.seunghan.rattle.service`. 해당 Services ID의 **Sign in with Apple → Configure**에서 1번의 Primary App ID `com.seunghan.rattle`을 선택하고, Supabase Apple OAuth callback 주소(`https://YOUR_PROJECT_REF.supabase.co/auth/v1/callback`)를 Return URL에 등록한다.
3. Apple Developer **Keys → +**에서 **Sign in with Apple** 키를 만들고 Primary App ID `com.seunghan.rattle`에 연결한다. `.p8` 원본, Key ID, Team ID를 안전하게 보관한다. 키는 최초 다운로드 이후 다시 받을 수 없다.
4. Supabase → **Authentication → Sign In / Providers → Apple**에서 제공자를 켠다. **Client IDs**에는 `Services ID, com.seunghan.rattle` 순서로 입력한다. Services ID는 Android·웹 OAuth용이고 첫 번째여야 한다. Bundle ID는 iOS 기본 인증용이다. 앱은 iOS에서 native ID token, Android·웹에서 브라우저 OAuth를 사용한다.
5. 같은 화면의 **Secret**에는 `.p8` 파일 자체가 아니라 Apple client secret(JWT)을 입력한다. 3번에서 만든 키의 Team ID·Key ID·`.p8`와 Services ID를 이용해 생성한다. Supabase Apple 설정 안내의 client secret 생성 도구를 사용하면 된다. 이 JWT는 최대 6개월 유효하므로 만료 전에 새로 생성해 교체한다.
6. Supabase 프로젝트 → **Edge Functions → Secrets**에 아래 네 값을 저장한다. 이들은 Auth Provider 설정과 별개이며 `.p8` 본문은 줄바꿈을 포함한 전체 PEM이다. `APPLE_CLIENT_ID`는 Edge Function secret이 아니며, Provider의 Services ID를 뜻한다.

| Secret 이름 | 입력값 |
|---|---|
| `APPLE_NATIVE_CLIENT_ID` | `com.seunghan.rattle` (iOS native 탈퇴 재인증용) |
| `APPLE_TEAM_ID` | Apple Developer의 Team ID |
| `APPLE_KEY_ID` | 위에서 발급한 키의 Key ID |
| `APPLE_PRIVATE_KEY` | `.p8` 전체 본문. `BEGIN PRIVATE KEY`·`END PRIVATE KEY` 포함 |

Edge Function 값들은 앱의 `EXPO_PUBLIC_*`, 저장소, 채팅에 넣지 않는다. 서버는 탈퇴 시 Apple 토큰 해제를 위해 Bundle ID를 client ID로 하여 5분짜리 client secret을 생성한다.

근거: [Supabase Apple 로그인](https://supabase.com/docs/guides/auth/social-login/auth-apple), [Expo AppleAuthentication](https://docs.expo.dev/versions/v55.0.0/sdk/apple-authentication/), [Apple 키 발급](https://developer.apple.com/help/account/keys/create-a-private-key/).

## 3. 서버 재배포와 앱 재빌드

Provider를 직원에게 제공하기 전에 Apple 탈퇴 처리를 포함한 새 함수를 먼저 배포한다. `YOUR_PROJECT_REF`는 적용 대상 Supabase 프로젝트 참조값으로 바꾼다.

```sh
npx supabase functions deploy delete-account --project-ref YOUR_PROJECT_REF
```

`app.json`에 Apple capability·플러그인이 추가됐으며 네이티브 모듈도 설치됐다. 기존 개발 앱에 Metro 새로고침이나 OTA 업데이트만 적용해서는 사용할 수 없다. 로컬 iOS 빌드는 다음 순서를 따른다.

```sh
npx expo prebuild --platform ios
npx expo run:ios --device
```

기존 iOS 네이티브 파일에 수동 수정이 있다면 prebuild 전에 변경을 보관한다. 이번 작업에서 로컬 `ios/` 생성 파일과 서명 설정은 수정하지 않았다. EAS 빌드도 새 iOS 바이너리를 생성하고 Sign in with Apple entitlement·프로비저닝을 확인한다. Google 테스트용 Android 개발 앱도 새 의존성이 포함되도록 재빌드한다.

## 4. 계정 연결과 탈퇴 동작

- 같은 이메일의 소셜 계정 연결 여부는 Supabase Auth의 인증·연결 정책을 따른다. 앱은 이름이나 직원 전화번호만으로 소셜 계정을 병합하지 않는다. [Supabase Identity Linking](https://supabase.com/docs/guides/auth/auth-identity-linking)
- Apple 이메일 가리기를 쓰면 기존 카카오·Google과 다른 계정이 생성될 수 있다. 기존 매장이 안 보이면 원래 로그인 수단으로 접속한다. 서로 다른 이메일의 로그인 수단을 수동으로 연결하는 화면은 이번 범위에 포함하지 않았다.
- 새 계정의 매장 참여는 기존 신청·관리자 승인 절차를 따른다. 소셜 로그인만으로 기존 직원 급여나 관리자 권한을 가져오지 않는다.
- Apple이 연결된 계정은 탈퇴 시 같은 Apple 계정으로 한 번 재인증한다. 서버는 소유권 검사 → 인증 코드 교환 → Apple 사용자 대조 → 토큰 해제 → Rattle 계정 삭제 순서로 처리한다. 해제에 실패하면 계정을 삭제하지 않는다. [Apple 토큰 해제](https://developer.apple.com/documentation/signinwithapplerestapi/revoke-tokens)
- Apple 해제와 DB 삭제는 하나의 트랜잭션이 아니다. 해제 후 DB 삭제가 실패하면 Rattle 계정이 남으므로 다시 인증해 탈퇴를 재시도한다. Apple 토큰 장기 보관·재시도 테이블·예약 작업은 추가하지 않았다.
- Apple이 연결된 계정의 탈퇴 재인증은 현재 iOS에서만 지원한다. Android·웹에서도 로그인은 가능하지만 탈퇴 재인증은 Apple 로그인이 가능한 iOS 앱에서 진행해야 한다.
- 카카오는 계정 삭제 후 즉시 연결 해제를 시도하며 실패 항목은 기존 수동 재처리 대상으로 남는다. Google 외부 API 접근 토큰의 별도 보관·연동은 추가하지 않았다.

## 5. 실제 계정 확인

실제 직원 자료와 분리된 테스트 계정을 사용한다.

| 확인 | 기대 결과 |
|---|---|
| 기존 카카오 로그인 | 로그인·로그아웃·재로그인 후 기존 매장 유지 |
| iOS·Android Google 로그인 | 계정 선택 후 앱 복귀, 재실행 후 세션 유지 |
| 인증 창 취소 | 오류 팝업 없이 로그인 화면으로 복귀 |
| iOS Apple 최초·재로그인 | 이름이 없는 재로그인도 성공, 기존 이름을 빈 값으로 덮어쓰지 않음 |
| Apple 이메일 가리기 | 해당 Apple 계정으로 다시 접속 가능, 타인 매장 자동 연결 없음 |
| Apple 탈퇴 취소·다른 계정 인증 | Rattle 계정과 업무 자료 유지 |
| Apple 소유자 탈퇴 | 소유권 이전 전 서버에서 거절 |
| Apple 일반 계정 탈퇴 | Apple 해제·Rattle 삭제 완료, 공용 매장 기록 유지 |

개인정보처리방침의 앱 화면·HTML 원본에도 Google·Apple 제공 항목을 반영했다. 공개 URL의 HTML 게시 완료는 별도 확인해야 한다.

## 로컬 검증 결과

타입 검사, 전체 Jest 29개 묶음·176개 테스트, 서버 연결 해제 Deno 11개 테스트와 서버 함수 타입 검사, iOS·Android 배포용 JS 번들 생성 및 변경 공백 검사를 통과했다. 외부 인증·해제 응답은 테스트에서 대체했다. Xcode 네이티브 컴파일·서명, 실제 Provider 콘솔 값과 실제 계정 로그인·탈퇴를 검증한 결과는 아니다. 웹 번들은 기존 `react-native-web` 의존성 미구성으로 생성하지 않았다.
