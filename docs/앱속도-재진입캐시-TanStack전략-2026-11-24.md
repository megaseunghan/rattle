## 1. 결론과 추천 시간표 (검토 당시안 — 0장이 우선)

### 1-1. 한 줄 결론

**포커스할 때마다 `refetch()`를 직접 부르는 코드를 없앤다. 탭 전환은 `enabled: active`와 `staleTime`에 맡기고, 스택 화면에서 돌아올 때는 오래된 쿼리만 다시 받는다. 캐시가 없는 useState 훅은 기존 쿼리 키 체계의 `useQuery`로 옮긴다.** 이렇게 하면 기존 저장 후 무효화(`invalidateCachedStore` → `invalidateStoreData`)가 그 훅들에도 자동으로 적용된다. 따라서 시간을 늘려도 내가 저장한 값은 바로 반영된다.

### 1-2. 왜 이 방식인가 (요약)

1. **[소스]** `QueryObserver.refetch()`는 `this.fetch()`를 그대로 호출한다. staleTime을 보지 않는다. 그래서 지금처럼 `useFocusEffect` 안에서 `query.refetch()`를 부르면 staleTime을 몇 분으로 올려도 요청 수는 줄지 않는다.
2. **[소스]** `enabled`가 `false`에서 `true`로 바뀌면 `shouldFetchOptionally` 조건에 따라 **데이터가 stale일 때만** 요청한다. 이 앱은 탭 페이지를 언마운트하지 않고 `active` prop으로 켜고 끈다(`app/(tabs)/_layout.tsx`의 `visited` 유지). 그래서 `enabled: active && ...`만으로 "탭에 들어올 때 오래된 것만 다시 받기"가 된다.
3. **[공식]** React Native 가이드의 `useRefreshOnFocus`는 첫 포커스를 건너뛴다. 그 뒤에는 `refetchQueries({ queryKey, stale: true, type: 'active' })`로 **stale인 활성 쿼리만** 다시 받는다.
4. **[사실]** 서비스 계층의 쓰기는 이미 `invalidateCachedStore(storeId[, domains])`를 40곳 넘게 호출한다. 하지만 useState 훅은 쿼리 캐시 밖에 있어 이 무효화를 받지 못한다. 그래서 지금은 포커스 때마다 다시 받는 방식으로 보완하고 있다. useQuery로 옮기면 이 보완이 필요 없어진다.

공통 규칙(논의안 유지 + 보강)

- 당겨서 새로고침은 항상 다시 받는다. `refetch()`나 `refetchQueries` 필터 없이 호출하며, staleTime과 무관하다.
- 저장 후에는 `cancel → invalidate` 순서를 지킨다. 기존 `invalidateStoreData`를 그대로 쓴다.
- 계정·매장·권한이 바뀌면 `clearQueryData()`로 비운다. 쿼리 키 2번째 칸 `useQueryScope()`에 역할·권한 개정판이 들어 있어 섞이지 않는다.
- 앱 복귀 때는 오래된 것만 받는다. 이미 연결된 `focusManager` + `refetchOnWindowFocus: true`가 그렇게 동작한다. 단, 직접 붙인 AppState 리스너는 무조건 다시 받으므로 걷어낸다(3장).
- 금액 캐시는 메모리에만 둔다. persist 플러그인과 AsyncStorage 저장은 하지 않는다(AGENTS.md).
- **(보강)** 금액 자료는 **월·매장이 바뀔 때 `keepPreviousData`를 쓰지 않는다.** 이전 달 금액이 새 달 제목 아래에 잠깐이라도 보이면 틀린 금액이 된다. 같은 키를 다시 받는 동안에만 이전 값을 보여준다(SWR).
- **(보강)** 급여 확정·정산 같은 **확정 행동 직전에는 `fetchQuery({ staleTime: 0 })`로 다시 확인**한다. 캐시를 오래 두어도 확정은 최신 값 기준이 된다.
- **(보강)** `gcTime`은 15분을 유지한다. 페이저 탭은 마운트를 유지한다. 비활성 탭의 쿼리도 disabled 관찰자가 붙어 있으므로 GC되지 않는다([소스] `Query.isActive`). 따라서 gcTime은 스택 화면과 이전 달 키에만 영향을 준다.

### 2-2. 화면 포커스와 탭

- [공식] Expo Router `useFocusEffect`는 "Hook to run an effect whenever a route is focused."다. https://docs.expo.dev/router/reference/hooks/ . React Navigation 문서는 콜백이 바뀌어도 다시 실행된다고 설명한다. https://reactnavigation.org/docs/use-focus-effect/
- [사실] 이 앱의 탭은 하나의 라우트 안 PagerView 페이지다. 그래서 탭 전환은 라우트 포커스가 아니다. 지금은 `useFocusEffect` 콜백 의존성에 `active`를 넣었기 때문에 탭 전환 때도 실행된다. 스택 화면에서 돌아오면 **방문했던 모든 탭**의 포커스 콜백이 실행되고, 각 콜백이 `active`를 확인한다.
- [사실] `app/pos/index.tsx`의 `useFocusReturn`이 바른 선례다. 콜백을 고정하고 첫 포커스를 건너뛰어 탭 활성화 effect와 중복 요청하는 것을 막는다.
- **설계**: 탭 전환은 `enabled: active`가 맡는다. 스택에서 돌아오는 경우는 `useFocusReturn` 형태의 공통 훅이 `refetchQueries({ ..., stale: true, type: 'active' })`로 맡는다. `subscribed`는 쓰지 않는다. 구독을 끊으면 관찰자가 없어져 gcTime 뒤 캐시가 지워지고, `refetchType: 'active'` 무효화에서도 빠진다. AGENTS.md의 `active` prop 규칙과도 겹친다. 숨은 탭의 리렌더를 줄이는 효과는 있으므로 후속 후보로 둔다.

### 2-3. 금액 화면의 stale-while-revalidate UX

| 관행 | 근거 |
|---|---|
| 캐시를 즉시 보여주고 뒤에서 재검증한다 | RFC 5861 "allows a cache to immediately return a stale response while it revalidates it in the background" https://www.rfc-editor.org/rfc/rfc5861 , https://web.dev/articles/stale-while-revalidate |
| 오래된 값이 스피너보다 낫다(단, 신선도는 staleTime으로 조절) | TkDodo "stale data is better than no data, because no data usually means a loading spinner" https://tkdodo.eu/blog/react-query-as-a-state-manager , https://tkdodo.eu/blog/practical-react-query |
| 응답 시간이 들쭉날쭉하면 대기 중 피드백이 중요하다 | NN/g "Feedback during the delay is especially important if the response time is likely to be highly variable" https://www.nngroup.com/articles/response-times-3-important-limits/ |
| 1초 넘는 작업에는 진행 표시를 한다 | NN/g https://www.nngroup.com/articles/progress-indicators/ |

Rattle 적용안(**[추정] 설계 제안**, 화면 문구·시안은 디자인 확인 필요)

1. 다시 받는 동안 숫자는 그대로 둔다. 머리글에 작은 "업데이트 중" 표시만 한다(`isFetching && !isPending`). 기존 `HomeFinancialCard`의 `refreshing` prop과 같은 방식이다. 전체 스피너나 스켈레톤으로 바꾸지 않는다.
2. 값이 바뀌면 자리 이동 없이 숫자만 바꾼다. 강한 애니메이션은 쓰지 않는다. 줄이기 설정을 따른다.
3. 뒤에서 받다가 실패하면 이전 값을 유지하고 "최신 값을 불러오지 못했어요 · n분 전 기준"으로 안내한다. 0원이나 빈 값으로 바꾸지 않는다(`number | null` 규칙). 기준 시각은 `dataUpdatedAt`에서 계산한다.
4. 확정·정산 버튼은 확정 직전에 다시 확인한다(1-3 보강 규칙). 다시 확인한 값이 화면 값과 다르면 확정을 멈추고 새 값을 보여준다.
5. 월·매장 전환 때는 이전 금액을 보여주지 않는다(keepPreviousData 금지). 새 키는 로딩 상태로 시작한다.

### 2-4. 다른 사용자가 바꾼 자료가 늦게 보이는 문제

| 클라이언트 쪽 완화 방법 | 효과 | 한계 |
|---|---|---|
| 자료별 staleTime 차등(1-3 표) | 남이 자주 바꾸는 자료일수록 짧게 둔다 | 최대 staleTime만큼 늦게 보일 수 있다 |
| 앱 복귀 때 stale 재검증(focusManager) | 다른 앱을 쓰다 돌아오면 갱신된다 | 앱을 켠 채로 계속 보고 있으면 효과가 없다 |
| 당겨서 새로고침 | 사용자가 원할 때 즉시 갱신한다 | 사용자가 오래된 자료라는 사실을 알아야 쓴다 → "n분 전 기준" 표시로 보완 |
| 확정 직전 재확인 | 오래된 값으로 확정하는 일을 막는다 | 확정 행동에만 적용된다 |
| 같은 기기의 다른 화면이 같은 키를 갱신 | 예: 내 QR 화면의 5초 확인이 홈 출퇴근 카드 캐시를 갱신한다 | 다른 기기의 변경에는 효과가 없다 |
| 보이는 화면에만 `refetchInterval` | 거의 실시간이 된다 | Nano 서버 부하가 커진다. 매장폰 스캐너처럼 꼭 필요한 곳에만 쓴다(기존 유지) |
| 서버 변경 시각 RPC, Supabase Realtime | 바뀐 경우에만 받는다 | 서버 작업이 필요하다. **이번 범위 밖**(논의안 유지) |

[결론] 클라이언트만으로는 "남의 변경을 즉시 보기"를 보장할 수 없다. 이번 단계의 목표는 **늦게 보일 수 있는 최대 시간을 자료별로 정하고 화면에 기준 시각을 드러내는 것**이다.
