# 조회·정규화·캐시 변경 적용

> **현재 상태 · 2026-10-23:** 분류·읽기 모델·POS 함수와 View의 원격 존재 및 함수 본문 일치를 확인했다. 이번에 해당 파일을 재실행하지 않았다. 아래 원격 미적용 서술은 당시 기록이다. 최신 근거는 [SQL 원격 적용 확인](SQL-원격적용-확인-2026-10-23.md)을 따른다.

## 상태

2026-10-21 작업. SQL 파일 버전은 기존 10/22 변경 이후를 구분하기 위해 `20261023`을 사용한다.

- 앱 코드·새 SQL·로컬 자동 검증 구현 완료.
- 원격 SQL 미적용. 운영 데이터 보정·원격 함수 배포·앱 배포는 하지 않았다.
- 검증은 저장소의 작업 중 변경 전체를 포함한다. 로컬 SQL 검사는 축약 스키마와 가상 자료이며 원격 마이그레이션 성공을 대신하지 않는다.
- 네이티브 기기에서 새 로그인·매장 전환·입력 흐름은 아직 확인하지 않았다. Expo iOS export 성공은 JS 번들 생성 확인이다.

## 적용할 SQL

기존 10/20~10/22 운영 SQL이 적용된 DB를 전제로 아래 순서대로 실행한다. 기존 마이그레이션 전체를 파일명순으로 재실행하지 않는다. 기존 원격 이력표만 보고 새 DB에 전체 적용됐다고 판단하지 않는다.

1. [20261023120000_read_models_and_integrity.sql](../supabase/migrations/20261023120000_read_models_and_integrity.sql)
2. [20261023121000_pos_read_models.sql](../supabase/migrations/20261023121000_pos_read_models.sql)

두 파일은 각각 트랜잭션으로 실행된다. 첫 파일의 분류 테이블·호환 트리거·View·함수를 만든 뒤 POS 집계·일괄 저장 함수를 만든다. 데이터 컬럼 삭제나 과거 급여 자동 채움은 없다. UNIQUE 제약에 필요한 인덱스 외 성능용 인덱스를 일괄 추가하지 않았다.

**새 앱은 위 RPC·View에 의존하므로 SQL을 먼저 적용하고 새 앱을 배포한다.** SQL 누락·오류를 구형 조회로 조용히 우회하거나 0원으로 처리하지 않는다. Release 설치본은 새 JS가 포함된 빌드·설치가 필요하다.

## 먼저 확인할 급여 이력

2026-10-21 원격 점검에서 재직 정규직 2명·파트타이머 1명의 급여 조건 이력이 없었다. 현재 기본급과 과거 적용일을 추정해 채우지 않았다.

1. [급여 이력 누락 조회](../supabase/operations/review-wage-history-gaps.sql)를 SQL Editor에서 실행해 대상만 확인한다. 이 파일은 읽기 전용이며 마이그레이션이 아니다.
2. 계약·기존 자료를 대조해 최초 적용일과 급여 조건을 확정한다.
3. 새 앱의 인건비 → 해당 직원 정보에서 급여 조건을 저장하고 적용일을 확인한다. 이력이 없는 직원은 금액을 바꾸지 않아도 적용일 확인을 거친다.
4. 해당 월·과거 월 손익과 기존 급여 명세를 대조한다. 과거 명세는 자동 재계산하거나 덮어쓰지 않는다.

새 손익 집계는 재직 정규직의 계산 기간 첫 적용일부터 이력이 없으면 `WAGE_HISTORY_REQUIRED`로 중단한다. 따라서 이력 확인 전에는 해당 매장 손익이 표시되지 않을 수 있다. 누락을 인건비 0원으로 간주하는 것보다 확인 필요 상태로 남긴다. 입사 전·미래 기간을 누락으로 취급하지 않는다.

## 바뀐 구조

### 분류와 매입 유형

- `store_taxonomies`: 매장·영역·이름, 안정적인 ID, 정렬·활성 상태.
- `ingredients.category_id`, `purchases.category_id/purchase_type_id`, `purchase_items.category_id` 추가.
- 기존 배열·문자열은 삭제하지 않고 ID와 동기화한다. 기존 이름과 사용 기록을 보존하며, 사용 중이던 비목록 분류는 임의 병합하지 않는다.
- 새 앱의 추가·이름 변경·제거는 `change_store_taxonomy` 한 트랜잭션을 사용한다.
- 매입 품목 분류는 품목별로 독립적이다. 부모 매입의 대표 분류를 모든 품목에 복사하지 않는다.
- 선택 품목의 분류 일괄 수정은 매장 조건을 붙인 UPDATE 한 번과 캐시 갱신 한 번으로 처리한다.

### 급여 조건과 계산

- 신규 직원·초기 급여 이력: `create_employee_with_initial_wage` 한 트랜잭션.
- 적용일별 조건 변경·현재 조건 반영: `add_employee_wage_change` 한 트랜잭션.
- `current_employee_wages` View는 한국 날짜 기준 현재 유효한 이력을 조회한다. NULL 이력을 0원으로 변환하지 않는다.
- 정규직 일할 계산은 실제 입사일 이후부터 집계하고, 새 집계 함수와 기존 상세 계산의 기준을 맞췄다.
- 작성된 급여의 적용 시급·세전·공제·계산 버전과 감사 기록은 그대로 보존한다.

### View와 집계 RPC

- `recipe_costs` View: 목록·상세에서 현재 단위환산 원가·마진을 공유한다. kg/g, L/mL, 개당 용량, 단위 NULL의 기존 재고 단위 대체를 포함한다.
- `get_financial_summaries`: 여러 매장·월의 손익을 일괄 조회한다. 월별 원본 자료를 앱에 보내 반복 합산하지 않는다. 정규직은 급여 조건 적용 구간의 겹치는 일수로 합산해 직원×일수별 조회를 줄인다.
- 기존 홈 RPC는 일괄 집계 함수를 사용한다. 승인 구성원에게는 합계만, 관리자 통합 조회는 모든 대상 매장의 관리자 권한을 검증한다.
- POS 일별·상품별 집계는 기간 RPC를 사용하고 한국 시간·매장 마감시간·반개방 구간 `[시작,끝)`을 적용한다.
- 주간 청소는 항목·기간 로그를 각각 한 번, 주간 스케줄은 전체 요일을 한 번 조회해 묶는다. 별도 View를 늘리지 않는다.
- POS 주문·카드/현금·상세 품목은 500건 이하 묶음별 원자적 저장을 사용한다. 여러 묶음 중 실패하면 앞서 완료한 묶음은 남으므로 성공으로 보고하지 않고 캐시를 재확인한다.
- Materialized View·자동 집계 예약은 추가하지 않았다. 읽기 View는 호출자 권한을 적용하며 직원별 급여 원본을 공유하지 않는다.
- 공개된 대기 가맹점 조회 함수는 관리자와 관련 사업자번호 범위로 제한했다.

### 화면·공유 캐시

- TanStack Query의 메모리 캐시를 사용한다. 금액·직원 자료를 새로 디스크에 저장하지 않는다.
- 사용자·실제/표시 권한·미리보기·매장·기간·마감시간·자료 종류별 키를 사용한다.
- 선택 월 숫자·추세·청소·스케줄을 독립 표시한다. 같은 월의 요약은 홈·통합 화면에서 공유한다.
- 이번 달 요약은 30초, 과거 월 요약은 5분, 재고·레시피·직원은 60초를 기본으로 재사용한다. 사용하지 않는 운영 캐시는 15분 후 정리한다.
- 앱 활성 복귀 시 오래된 활성 조회를 갱신한다. 수동 새로고침은 재사용 시간을 무시한다.
- 매입·비용·급여·급여 조건·재고·레시피·수기 매출·합류 승인 등의 저장 성공 후 관련 매장 조회를 갱신한다. ID만 있는 기존 저장 경로는 메모리의 앱 조회를 한 번에 무효화해 누락을 막는다.
- 청소·스케줄 변경은 해당 운영 현황과 알림만 갱신하며, 손익 전체를 다시 계산하지 않는다.
- 무효화 전에 진행 중 요청을 취소해 수정 이전 응답이 새 값을 덮지 않게 한다.
- 계정·권한·미리보기 경계 변경 시 기존 캐시를 제거한다. 일반 매장 전환만으로 전체 캐시를 지우지 않는다.
- 기존 `pos_summaries_*` 저장값만 정리하고 인증·사용자 설정 저장소는 보존한다.
- 자동 POS 동기화는 계정·매장별 진행 요청을 공유한다. 성공한 자동 작업만 간격 제한을 소비하고 수동 동기화는 제한을 우회한다.
- 알림은 홈·목록이 15초 캐시와 활성 상태의 30초 폴링 한 개를 공유한다. 읽음 상태는 함께 반영하고 마지막 구독이 끝나면 타이머를 해제한다. 기존 매장 공용 읽음 의미는 바꾸지 않았다.

## 검증

최종 로컬 결과: 타입 검사 통과, Jest **46개 스위트·289개 테스트 통과**, 기존 SQL 검사 101개·82개와 새 읽기 모델 검사 49개 통과, POS 집계·원자 저장 SQL 검사 통과, iOS Metro/Hermes 번들 생성 통과, 변경 코드 리뷰 차단 사항 없음, `git diff --check` 통과.

이 수치는 원격 적용·실제 계정·기기 성능 검증의 완료 수치가 아니다.

기본 명령:

```sh
npm run typecheck
npm test -- --runInBand --no-coverage
npm run test:sql
npx --no-install expo export --platform ios --output-dir /private/tmp/rattle-readmodel-export
```

SQL 검사는 기존 운영·배포 검사 외 새 분류 ID·본문 호환, 혼합 분류 매입, 급여 이력 누락과 적용일, 집계 합계·권한, 레시피 단위환산, POS 경계·다른 매장 차단·부분 실패 롤백을 포함한다.

앱 검사는 요청 공유·재방문 재사용·수동 새로고침·계정/매장/권한 격리·늦은 응답 차단·직원 중복 추가 방지·저장 후 갱신·오류 복구를 포함한다. 코드 리뷰에서 발견된 캐시 정리 경합·NULL 이력 처리·혼합 분류·단위 NULL·입사일 계산 차이는 수정했다.

## SQL 적용 후 확인

1. 관리자 계정으로 A → B → A 매장 전환. A의 이전 결과가 먼저 보이고 갱신 중 다른 매장 숫자가 섞이지 않는지 확인한다.
2. 통합 월간·연간 요약을 상세 손익과 대조한다. 이력 누락은 확인 안내가 표시돼야 한다.
3. 매입·고정비·급여 조건을 수정한 뒤 홈·통합 합산·영향받는 과거 월이 갱신되는지 확인한다.
4. 분류·매입 유형 이름을 바꿔 ID와 기존 이력이 보존되고 혼합 품목의 분류가 각각 유지되는지 확인한다.
5. 정규직·파트타이머 본인/다른 직원·다른 매장 권한을 확인한다. 로그아웃 후 다른 계정에서 이전 금액이 보이면 안 된다.
6. 화면을 60초 그대로 두고 자동 POS 요청이 반복되지 않는지, 동기화 실패 후 다시 시도할 수 있는지 확인한다.
7. iOS·Android 기기에서 첫 진입·재방문·수정 후 표시 시간을 따로 측정한다. 로컬 통과만으로 체감 개선 비율을 확정하지 않는다.
