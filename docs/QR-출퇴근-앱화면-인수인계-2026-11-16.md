# QR 출퇴근 앱 화면 인수인계 (2026-11-16)

이 문서는 QR 출퇴근 1단계 **앱 화면(S43~S46)** 을 이어서 구현할 작업자(Codex 등)에게 확정된 정책과 서버 계약을 전달한다.
- 상세 설계와 결정 근거: [QR-출퇴근-설계안-2026-11-16.md](QR-출퇴근-설계안-2026-11-16.md). **9장이 1~8장보다 우선한다.** 1~8장의 "30초 구간·intent 포함 QR·`attendance_token_uses`"는 폐기된 초안이다.
- DB: `supabase/migrations/20261116120000_qr_attendance.sql`. 원격 적용 완료(2026-11-16, 재조회 확인). 검증 스크립트는 `scripts/validate-qr-attendance-sql.mjs`(63개, `npm run test:sql`에 포함)이다.
- 작업 전에 저장소 `AGENTS.md`의 디자인·검증·보안 규칙을 따른다. 이 문서는 그 규칙을 넓히지 않는다.

## 1. 확정 정책 (사용자 결정)
| 주제 | 결정 |
|---|---|
| 범위 | 위치정보(GPS·Wi-Fi·기지국·비콘)를 수집하지 않는 **QR 출퇴근만** 제공한다. 위치 권한·모듈을 출시 빌드에 넣지 않는다. 사진도 쓰지 않는다 |
| 방향 | **반대 방향 QR**: 직원 폰이 QR을 보여주고, **등록된 매장폰(스캐너)** 이 스캔한다. 기록은 스캐너에서만 생긴다 |
| 직원 폰 | **온라인 필수**. QR 화면에서 서버의 45초짜리 일회용 값(nonce)을 받아 서명한다. 미리 만든 QR은 막는다. 영상통화 같은 실시간 전달은 남는 위험으로 둔다 |
| 기기 등록 | **사람(로그인 계정) 기준**이라 여러 매장에서 같은 기기를 쓴다. 등록 이력이 없으면 첫 등록은 즉시 활성, 이후 기기 변경은 **관리자 승인** 후 활성. 활성 기기는 1인 1대. 퇴사(모든 매장 비활성) 시 서버가 자동 해제 |
| 매장폰 | "매장폰 등록"이다. 관리자가 로그인한 상태에서 등록하면 **출퇴근 기록 전용 토큰**을 1회 받는다. 앱은 토큰을 저장한 뒤 **관리자 세션을 로그아웃**한다. 이후 스캐너는 로그인 없이 동작한다. 분실 시 관리자가 해제하면 즉시 막힌다 |
| 출근/퇴근 | **서버가 자동 판단**한다(열린 근무가 있으면 퇴근). 직원이 고르는 UI를 만들지 않는다. 틀리거나 누락되면 직원이 정정을 요청하고 관리자가 승인·반려한다 |
| 원본·정정 | 출퇴근 원본은 수정 불가다. 정정은 새 요청 테이블에 담기고, 승인되면 새 정정 기록이 생긴다. 변경 전 스냅샷(`original_snapshot`)이 보존된다. 화면에는 "무엇이 어떻게 바뀌었는지"를 보여준다 |
| 대상 | 정규직·파트타이머 모두 기록 대상이다. 사장님 본인은 직원으로 등록된 경우만 해당한다 |
| 폰 없는 직원 | 관리자가 **사유를 적고 직접 기록**한다(`source=manual`) |
| 오프라인 | 1차는 대기열을 지원하지 않는다. 실패하면 "저장 안 됨 — 관리자에게 정정 요청"을 분명히 표시한다. 성공처럼 보이면 안 된다 |
| 보관 | 퇴직일 기준 3년이다. 매장 삭제 전에는 내보내기를 안내한다(내보내기 기능은 후속) |
| 급여·손익 | **1차에서 급여에 반영하지 않는다.** 출퇴근 기록을 확정 인건비로 표시하지 않는다(2차: 매장별 반영 주기 매일/주별/월별, 손익에 "미반영 출퇴근 추정 인건비"를 따로 표시) |
| 출시 | S43(QR)과 S44(스캐너)는 **같은 네이티브 빌드로 함께** 내보낸다. 기능 플래그 뒤에 두고, QR만 먼저 EAS Update로 내보내지 않는다 |

## 2. 화면 범위 (새 ID, 매니페스트·명세·E2E에 추가)
| ID | 화면 | 사용자 | 경로(안) | 1차 범위 |
|---|---|---|---|---|
| S43 | 내 출퇴근 QR | 직원 | `app/attendance/my-qr.tsx` | 기기 등록(미등록·승인 대기·해제 상태 안내), QR 표시·자동 갱신, 오늘 내 기록, 정정 요청 진입 |
| S44 | 매장 스캐너 | 매장폰 | `app/attendance/scanner.tsx` | 카메라 스캔, 결과 피드백(출근/퇴근·가린 이름·시각·중복), 오류 안내, 화면 꺼짐 방지, 카메라 권한 거부 상태, 종료는 관리자 재인증 |
| S45 | 출퇴근 확인·정정 | 관리자 | `app/attendance/review.tsx` | 기간별 기록 목록, **확인 필요**(flags 있는 기록) 목록, 정정 요청 승인·반려(변경 전후 표시), 직접 기록 |
| S46 | 출퇴근 기기 관리 | 관리자 | `app/settings/attendance-devices.tsx` | 직원 기기 승인·해제, 매장폰 등록·해제 |
- 진입: 직원은 홈의 오픈/마감 흐름 근처, 관리자는 더보기 설정에서 들어간다.
- 역할 미리보기(dev role switcher) 중에는 QR 발급·기기 등록·정정 요청을 막는다(실제 계정 행동이므로).
- 대기·미연결 계정은 서버가 `ATTENDANCE_NOT_EMPLOYEE`로 막는다. 화면에서도 진입 안내를 따로 둔다.

## 3. QR 생성 규칙 (직원 폰)
1. `register_attendance_device(p_label)`의 응답 `{device_id, status, secret}`을 받는다. `secret`은 base64 32바이트이고 **이때 한 번만** 내려온다.
2. 저장은 `expo-secure-store`의 `WHEN_UNLOCKED_THIS_DEVICE_ONLY`를 쓴다. 키 이름에 user_id와 device_id를 넣는다. 로그아웃·계정 전환 시 삭제하고, Android 자동 백업에서 제외한다. 출퇴근 기록과 위치는 기기에 저장하지 않는다.
3. QR 화면을 열거나 만료가 가까우면 `issue_attendance_qr(p_device_id)`로 `{nonce, expires_at}`을 받는다. nonce는 24자 hex, 유효 시간은 45초, 1회용이다. 미사용 nonce는 5개까지라 너무 자주 부르면 `ATTENDANCE_QR_RATE_LIMIT`이 난다.
4. 서명은 `sig = hex( HMAC_SHA256(secret_bytes, utf8("{device_id}.{nonce}"))[0..16] )`로 만든다. 16바이트이므로 32자 hex다(`@noble/hashes` 권장).
5. QR 문자열은 `rattle-punch:v1.{device_id}.{nonce}.{sig}`다. device_id는 소문자 UUID, 모든 hex도 소문자다. 서버는 이 형식을 정규식으로 엄격히 검사한다.
6. 갱신은 만료 전에 미리 새 nonce를 받는다(예: 30초마다). 화면 캡처 차단(`expo-screen-capture`)과 밝기 올림(`expo-brightness`)은 선택이다.
7. 기기 상태가 `pending`이면 QR을 만들지 않고 "관리자 승인 대기"를 안내한다. 기기가 해제됐거나 secret이 없어 재등록이 필요하면 새로 등록하며, 이 경우 관리자 승인이 필요하다.

## 4. 서버 계약 (RPC)
권한 표기: auth = 로그인 사용자(`authenticated`), anon = 로그인 없음(스캐너).

| RPC | 권한 | 인자 | 반환 |
|---|---|---|---|
| `register_attendance_device` | auth, 활성 직원 | `p_label text` | `{device_id, status: 'active'\|'pending', secret}` |
| `issue_attendance_qr` | auth, 본인 활성 기기 | `p_device_id uuid` | `{nonce, expires_at}` |
| `approve_attendance_device` | auth, 관리자 | `p_device_id uuid` | void |
| `revoke_attendance_device` | auth, 본인 또는 관리자 | `p_device_id uuid, p_reason text` | void |
| `list_store_attendance_devices` | auth, 관리자 | `p_store_id uuid` | rows `device_id, employee_id, employee_name, label, status, requested_at, activated_at, first_punch_at` |
| `register_attendance_scanner` | auth, 관리자 | `p_store_id uuid, p_label text`(1~40자) | `{scanner_id, token}` — token은 1회만 내려온다. 서버는 해시만 저장한다 |
| `revoke_attendance_scanner` | auth, 관리자 | `p_scanner_id uuid` | void |
| `attendance_scanner_status` | **anon** | `p_scanner_token text` | `{scanner_id, store_name, label}` — 스캐너 시작 시 토큰 유효성 확인용 |
| `punch_attendance` | **anon** | `p_scanner_token text, p_qr text` | `{punch_id, kind, punched_at, flags, duplicate, employee_name}` — 이름은 `김**`처럼 가려서 온다 |
| `record_manual_attendance` | auth, 관리자 | `p_store_id, p_employee_id, p_kind('clock_in'\|'clock_out'), p_at timestamptz, p_reason` | punch id |
| `request_attendance_correction` | auth, 본인 또는 관리자 | `p_store_id, p_employee_id, p_action('add'\|'change'\|'void'), p_target_punch_id, p_kind, p_time, p_reason` | request id |
| `review_attendance_correction` | auth, 관리자 | `p_request_id, p_approve boolean, p_note` | 승인 시 새 punch id. 반려 시와 **대상 기록이 그사이 바뀌어 자동 반려된 경우 NULL** |
| `cancel_attendance_correction` | auth, 요청자 | `p_request_id` | void |

- 조회: 기록은 `attendance_effective_punches` 뷰(무효·대체된 원본 제외)로, 원본 이력은 `attendance_punches`로, 정정 요청은 `attendance_correction_requests`로 읽는다. RLS상 본인 기록과 관리자 매장 기록만 보인다. `attendance_scanners.token_hash`는 조회할 수 없다.
- 직접 INSERT/UPDATE 권한은 없다. 모든 쓰기는 RPC로 한다. DB 접근은 `lib/services/`에만 두고 도메인 훅으로 감싼다(AGENTS.md 컨벤션).
- `punch_attendance`는 같은 QR을 다시 보내거나 60초 안에 연속 스캔하면 **새 기록 없이 기존 기록과 `duplicate: true`** 를 돌려준다. 응답이 유실되면 같은 QR로 그대로 재시도한다.
- `flags` 값은 `no_schedule`(스케줄 없는 날 출근), `early_clock_in`(시작 10분 전보다 이름), `late_clock_out`(종료 10분 후보다 늦음), `previous_open_over_16h`(16시간 넘게 열린 근무 뒤의 출근), `new_device`(관리자 승인 기기의 첫 기록)다. 하나라도 있으면 S45 "확인 필요"에 올린다.
- 정정 요청 입력 제한: `add`는 kind·시각 필수, `change`는 시각 필수, `void`는 대상만 필요하다. 시각은 1년 전~현재+5분, 사유는 1~500자, 직원당 대기 요청은 10건까지다. 화면에서 먼저 검사한다.
- 날짜 귀속: 출근은 KST 날짜 기준이다. 퇴근은 16시간 안의 마지막 출근 날짜에 붙는다(`work_date`). 화면은 `work_date` 기준으로 묶는다.

### 오류 코드 → 사용자 문구
내부 오류 원문은 보여주지 않는다(AGENTS.md). 아래처럼 짧게 다음 행동만 안내한다.

| 코드 | 의미·안내 방향 |
|---|---|
| `ATTENDANCE_QR_EXPIRED` | QR 시간이 지남 → 직원 폰 QR을 새로 고쳐 다시 스캔 |
| `ATTENDANCE_QR_INVALID` | 인식할 수 없거나 이미 쓴 QR → 직원 폰의 Rattle 출퇴근 QR인지 확인 |
| `ATTENDANCE_DEVICE_INACTIVE` / `ATTENDANCE_DEVICE_NOT_FOUND` | 승인 대기·해제된 기기 → 관리자 승인 필요 |
| `ATTENDANCE_NOT_EMPLOYEE` | 이 매장 직원이 아님(또는 대기·퇴사) |
| `ATTENDANCE_SCANNER_INVALID` | 매장폰 등록이 해제됨 → 관리자가 다시 등록(스캐너 토큰 삭제 후 등록 화면으로) |
| `ATTENDANCE_DEVICE_RATE_LIMIT` / `ATTENDANCE_QR_RATE_LIMIT` / `ATTENDANCE_CORRECTION_RATE_LIMIT` | 잠시 후 다시 |
| `ATTENDANCE_ADMIN_REQUIRED` / `ATTENDANCE_AUTH_REQUIRED` / `ATTENDANCE_EMPLOYEE_REQUIRED` | 권한·로그인 필요 |
| `ATTENDANCE_REASON_REQUIRED` / `ATTENDANCE_INPUT_INVALID` / `ATTENDANCE_TARGET_INVALID` | 입력 오류(현재 단계에서 위치 안내) |
| `ATTENDANCE_CORRECTION_PENDING` / `ATTENDANCE_CORRECTION_NOT_PENDING` | 같은 기록에 대기 중 요청 있음 / 이미 처리됨 |
| 네트워크 실패·응답 없음 | **"저장 안 됨"** 으로 표시. 같은 QR 재시도는 안전함 |

## 5. 앱 구조·빌드 주의
- **스캐너 경로**는 로그인 없이 열려야 한다. `app/_layout.tsx`의 인증 리다이렉트에 예외를 둔다. 스캐너 토큰은 SecureStore에 저장한다. 관리자 세션은 등록 직후 로그아웃해서 매장폰에 급여·계좌 화면이 남지 않게 한다. 스캐너 화면에서는 다른 화면으로 나갈 수 없다.
- 스캐너 anon 호출은 일반 supabase 클라이언트의 세션과 섞이지 않게 한다(세션 없는 상태에서 RPC 호출).
- 새 패키지는 `expo-camera`, `expo-keep-awake`, `react-native-qrcode-svg`, `@noble/hashes`(선택: `expo-screen-capture`, `expo-brightness`)다. 네이티브 모듈이 추가되므로 런타임 정책(`appVersion`)에 따라 **앱 버전을 1.0.0 → 1.1.0** 으로 올린다. 증빙(매입·비용 사진 첨부) 브랜치의 네이티브 모듈과 **한 번의 새 네이티브 빌드**로 묶는다.
- iOS 권한 문구는 카메라 하나만 둔다: "매장 출퇴근 QR을 스캔하기 위해 카메라를 사용합니다". **위치 권한 문구는 추가하지 않는다.**
- 시뮬레이터 Release 빌드는 `CODE_SIGN_IDENTITY=-`로 만든다(`CODE_SIGNING_ALLOWED=NO`면 SecureStore가 ERR_KEY_CHAIN으로 실패한다; `docs/EAS-업데이트-운영-2026-10-30.md`).
- 카메라 스캔은 시뮬레이터에서 실제로 확인할 수 없다. 실기기 2대(직원 폰과 매장폰) 확인을 별도 항목으로 보고한다.
- 개인정보처리방침(`app/legal/*`)에 출퇴근 기록(일시·매장·매장폰)과 출퇴근 기기 식별자를 수집 항목으로 추가한다. "출퇴근 기록을 새로 수집하지 않으며" 문구는 고친다. 위치정보 미처리는 유지한다. 초안은 `docs/개인정보처리방침-보완안-2026-11-14.md`에 있다.

## 6. 1차 범위 밖 (만들지 않음)
- 급여·일별 근무 반영(`apply_punches_to_daily_work`), 반영 주기 설정, 손익 추정 인건비 표시 → 2차
- 이상 감지 **알림** 발송(1차는 S45 확인 필요 목록 표시만), POS 결제 시각 대조
- 스캐너 오프라인 대기열, App Attest / Play Integrity
- GPS 판정 모듈(별도 브랜치·기능 플래그, 사업자등록과 위치기반서비스 신고 전에는 출시 빌드 제외)
- 옛 `attendance`(GPS 구조, 원격 14행)·`attendance_corrections` 테이블 사용·수정 → 보존하고 건드리지 않는다. 정규화·정리는 후속 작업이다

## 7. 남은 서버 후속 (화면 작업 중 필요하면 PM에게)
- 야간 스케줄의 늦은 퇴근 판정, 직원 행 삭제나 user_id 변경 시 기기 처리, 관리자 본인 정정의 자기 승인 허용 여부, 출퇴근 기록 삭제 차단과 3년 보관, 자정 너머 정정 시 짝 퇴근 날짜 재계산(설계안 9-6)
- 화면에 필요한 조회 RPC(예: 기간 목록·확인 필요 목록 집계)가 부족하면 **새 마이그레이션 파일**로 추가한다. 이미 적용된 `20261116120000_qr_attendance.sql`은 수정하지 않는다. 원격 적용은 별도 승인을 받는다.
