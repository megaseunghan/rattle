설계 근거: [PostgreSQL procedure 트랜잭션 제어](https://www.postgresql.org/docs/current/plpgsql-transactions.html), [Supabase cron의 CALL 예시](https://supabase.com/docs/guides/cron/quickstart). procedure는 트랜잭션 제어를 위해 SECURITY INVOKER이며 SET 절을 두지 않고, 객체명을 스키마로 한정하고 실행 권한을 회수한다. 최상위 CALL로 실행해야 하며 BEGIN으로 감싸 실행하지 않는다.

미검증: 실제 다중 연결 try-lock 경합·원격 pg_cron 예약/실행·Nano DB 실제 지연·전체 운영 migration chain·기기/EAS. push/PR/원격 DB/EAS/기기 조작은 과제 금지로 미실행이다. PGlite의 procedure 직접 실행은 원격 cron 성공 증거가 아니다.

Supabase에서 SQL 적용을 진행해줘: 선행 이력을 확인한 후 신규 `20261119130000_attendance_kind_corrections.sql` → `20261119131000_attendance_unprocessed_notifications.sql` → `20261119132000_attendance_notification_schedule.sql`. 세 파일 모두 이번 과제에서는 원격 미적용이며, 적용과 예약·실행 재조회는 조정자가 별도 승인 범위에서 진행한다.
