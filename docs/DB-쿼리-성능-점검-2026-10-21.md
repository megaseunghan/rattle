### 자동 동기화 순환의 코드 근거

1. `app/(tabs)/index.tsx:384`의 effect가 `autoSyncOnForeground` 변경 시 다시 실행된다.
2. `lib/hooks/useTossSync.ts:273`의 콜백은 `autoSync`, `autoSyncRecent`에 의존한다.
3. `autoSync`는 `autoSyncing`에 의존하면서 내부에서 이 값을 true → false로 변경한다(`:142`, `:192`).
4. 상태 변경으로 콜백 참조가 바뀌면 홈 effect가 다시 실행될 수 있다. 같은 매장에 주문이 이미 있어도 마감시간·건수·오늘 매출을 다시 읽는다.
5. `autoSyncRecent`도 `autoSyncing`, `lastSyncAt`에 의존한다(`:195`, `:240`). POS 화면의 `loadStoreStatus`도 이 콜백에 의존한다(`app/pos/index.tsx:116`).

따라서 반복 요청을 만드는 경로는 코드에서 확인된다. 누적 21만 회 전체가 이 경로 하나에서 발생했는지에 대한 기기별 추적은 수행하지 않았다.

추천 구현은 진행 중 여부·마지막 성공 시점을 조회 콜백의 재생성 원인에서 분리하고, 사용자·매장별로 요청을 공유하는 것이다. effect 의존성만 임의로 삭제하면 오래된 매장 참조를 사용할 수 있으므로 함께 처리해야 한다. 주문 존재만 필요하면 정확한 전체 건수 대신 한 건 존재 조회를 검토한다.

## 3. 원격 실행 계획

동일한 매장·2026년 10월 범위·POS 결제액 442행을 대상으로 측정했다. 원본 행은 출력하지 않았다.

| 조건 | 실행 시간 | 계획 시간 | shared hit blocks |
|---|---:|---:|---:|
| authenticated 관리자, RLS 적용 | 10.686ms | 11.811ms | 1,378 |
| 내부 postgres 조회, RLS 우회 권한 | 0.350ms | 0.096ms | 58 |
| 홈 월 요약 RPC, authenticated 관리자 | 49.750ms | 0.029ms | 2,084 |

두 원본 조회 모두 기존 `idx_toss_sales_order_at(store_id, order_at DESC)`를 사용했다. RLS 적용 계획에는 `user_has_store_access(store_id)`와 기존 소유자 정책의 OR 조건이 있다. 행별 접근 함수와 계획 차이에 비용이 붙는다.

단일 순차 측정이고 뒤쪽 조회는 캐시가 더 따뜻할 수 있다. 약 30배 차이가 모든 매장·기기에서 재현되거나 정책 정리 후 앱이 30배 빨라진다는 뜻은 아니다. 내부 postgres 조회는 비용 비교용이며 앱에 관리자 키를 넣거나 RLS를 끄는 개선안을 뜻하지 않는다.

요약 RPC의 이번 측정 49.75ms와 누적 평균 345.3ms는 다른 시점·부하·입력의 결과다. 함수를 여러 매장·기간으로 반복 측정하고 내부 급여 일할 계산도 분해해야 한다. 현재 함수는 정규직 × 월 일수 × 급여 이력 LATERAL 조회를 사용한다.

RLS 최적화는 입력 행에 의존하지 않는 인증 함수의 결과 재사용, 필요한 인덱스, 허용 매장 집합 계산 등을 검토한다. 행별 매장 ID를 받는 함수를 무조건 `(select 함수(...))`로 감싸는 방식은 적용하지 않는다. [Supabase RLS 성능 지침](https://supabase.com/docs/guides/troubleshooting/rls-performance-and-best-practices-Z5Jjwv)

SELECT에 적용될 수 있는 정책이 둘 이상인 테이블은 13개다. `FOR ALL` 정책이 SELECT에도 적용되는 경우를 포함한다. 테이블별 의미가 다르므로 모두 불필요한 정책으로 간주하지 않는다.

## 5. 통합 화면 조회와 표시 방식

- `lib/services/adminDashboard.ts`: 월간 합산용 2개월 + 추세용 6개월 = 매장당 8회 월 손익 계산. 이 중 선택 월과 전월은 중복된다.
- 연간 화면은 선택 연도·전년과 최근 6년이 중복된다. 현재 연도를 선택하고 당월을 M이라 하면 매장당 월 계산 수는 `(M + 12) + (M + 5 × 12) = 2M + 72`. 2026년 10월 기준 92회이며, 관리 대상이 4곳이면 368회다. 이는 SQL 문 개수가 아니라 월 손익 함수 호출 수다.
- 월 손익 한 번은 관리자 접근 확인 후 POS·수기매출·매입·비용·고정비·급여·급여 이력·직원 등을 조회하고 매입 품목도 추가 조회한다.
- 주간 스케줄은 매장별 요일 7번 조회한다. 청소도 날짜별 로그를 나눠 조회한다. 주간 범위 한 번 조회 후 요일별로 묶는 방식으로 줄일 수 있다.
- `useAdminDashboard.ts:50`은 손익·추세·청소·스케줄의 모든 작업이 끝난 후 결과를 반영한다.
- 매장 홈은 최근 6개월 요약 RPC가 모두 끝난 다음 선택 월 숫자를 표시한다.
- `app/(tabs)/_layout.tsx:174`는 매장 ID를 key로 사용해 방문한 탭을 재생성한다. 재생성 제거 시 기존 자료 혼입·권한 변경·늦은 응답 반영을 막는 처리가 선행돼야 한다.
- 알림은 목록 전체를 읽어 미읽음 수를 계산한다. 인스턴스별 30초 타이머가 있으므로 화면 간 공유와 요약 조회를 검토한다.
- POS·손익 원본 조회 중 페이지 순회 없는 경로가 있다. API 최대 반환 행 설정은 이번에 확인하지 않았으므로 누락이 실제 발생했다고 단정하지 않는다. 서버 합산 전환 시 현재 합계와 함께 검증한다.

따라서 기존 AGENTS.md의 “10/22 원격 미적용” 기록과 현재 서버가 다르다. 이번에는 문서의 과거 상태를 적용 사실로 사용하지 않았다. 이 결과는 원격 객체 존재와 정의 확인이며 실제 계정으로 최종 합류 흐름을 통과했다는 의미는 아니다.

저장소에서 찾은 테이블 이름의 차이는 `toss_sales` → `toss_orders` 이름 변경으로 설명된다. 저장소에서 선언한 함수·인덱스 이름은 원격에 모두 존재했다. 객체 존재만으로 모든 컬럼·정책·업무 동작의 완전한 일치를 증명하지 않는다.

### 적용 이력의 한계

- 로컬 마이그레이션 파일 62개, 원격 `schema_migrations` 이력 14행.
- 원격 이력의 마지막 버전은 `20260811`이지만 10월 객체는 실제로 존재한다.
- 로컬에는 같은 날짜 버전을 가진 파일이 여러 개 있다. 이력표와 실제 객체가 일치하지 않는 이유 전체는 확인하지 않았다. 수동 SQL 적용 또는 이력 밖 적용 가능성이 있다.
- `deliver_order`는 `20260609_ingredient_drop_container.sql` 본문과 일치한다. 같은 날짜의 `stock_member_access` 파일에는 이전 container 계산이 있어 파일명 정렬로 재적용하면 잘못된 정의가 복원될 수 있다.

전체 SQL을 무작정 재실행하거나 `migration repair`로 이력을 채우지 않는다. 현재 실제 정의를 기준으로 기준 스키마와 고유 버전의 후속 변경을 정리해야 한다.

### 저장소에서 찾지 못한 원격 함수 3개

- `confirm_toss_installation`
- `find_store_by_business_number`
- `list_pending_toss_installations`

이 중 `list_pending_toss_installations`는 확인한 정의에 사용자 권한 검사가 없고 anon EXECUTE가 허용돼 있다. 반환 정의에는 가맹점·사업자번호·대표자·주소가 포함된다. **반환 데이터를 실제로 호출하지는 않았다.** 성능과 별개로 실행 권한과 사용하는 화면을 대조해 정리할 항목이다.

## 8. 남은 확인과 완료 기준

이번에는 공개 스키마 전체 메타데이터·함수 본문 대조와 선택 조회의 계획을 확인했다. 모든 RPC의 실제 쓰기 실행, 모든 권한 조합, Supabase 관리 스키마 전체, 요금제·CPU 추이·I/O 크레딧·네트워크 지연, Edge Function 배포 버전과 네이티브 렌더링은 확인 범위 밖이다. Supabase Advisor 전체를 실행한 결과도 아니다.

수정 후에는 같은 기기·계정·4개 매장 조건에서 다음을 비교한다.

1. 매장 선택부터 첫 요약 표시, 통합 대시보드 진입부터 숫자 표시까지 시간.
2. 화면을 60초 그대로 둘 때 자동 동기화 호출이 계속 반복되지 않는지.
3. 한 번 진입 시 DB/API 요청 수, 캐시가 있는 재방문 시 요청 수.
4. 기존 계산과 서버 합산 결과의 일치, 실패·미조회와 0원 구분.
5. 일반 직원의 본인 급여 권한과 매장 간 격리가 유지되는지.

현재는 **진단 완료·튜닝 미적용** 상태다. 새 마이그레이션은 만들지 않았으며 Supabase에서 적용할 SQL 변경도 없다.

측정 방식 참고: [쿼리 최적화](https://supabase.com/docs/guides/database/query-optimization), [누적 쿼리 통계](https://supabase.com/docs/guides/database/extensions/pg_stat_statements).

## 9. 캐싱 추가 점검

**공유 메모리 캐시와 진행 중 요청 공유가 필요하다.** 우선 홈 요약·통합 대시보드·직원 조회에 적용하고, 수정 후 관련 결과를 다시 조회하는 규칙까지 함께 만든다. 이번 추가 점검은 로컬 코드 검토이며 캐시 구현·설치·실기기 속도 측정은 하지 않았다.

### 현재 구현

| 영역 | 현재 상태 | 문제 |
|---|---|---|
| 홈 최근 6개월 | `useProfitLossTrendChart`의 화면 내부 state만 사용 | 재방문·월 이동 시 공통 월도 재조회. 동일 범위의 이전 결과를 갱신 중 보관하지만 영역 UI는 loading 분기로 가림 |

### 기존 POS 저장 캐시 보완

`usePosAnalytics.ts:8`의 키는 매장 ID와 조회 종료 시각에서 뽑은 연·월만 포함한다. 사용자·권한·정확한 시작/종료 범위·마감시간은 빠져 있다. 다음 달 1일 마감시간을 종료 시각으로 넘기면 1초를 빼도 다음 달이므로 월 이름도 의도와 어긋날 수 있다.

또한 저장 시각·유효기간이 없고 로그아웃은 `LAST_STORE_ID`만 삭제한다. 따라서 기존 POS 요약은 계정 변경·권한 회수 후 저장 자료 표시를 막는 경계가 부족하다. 권한 조회가 거절돼도 이미 표시한 저장값을 지우는 처리도 없다. 실제 다른 계정 노출을 기기에서 재현한 결과는 아니며 코드상 보완 사항이다.

초기 개선은 금액·직원 자료를 디스크에 저장하지 않는 세션 메모리 캐시를 권한다. 기존 `pos_summaries_*` 저장값은 전환 시 선별 제거하고, 기존 인증 세션 저장소는 건드리지 않는다.

### 제안하는 캐시 정책

다음 시간은 실측 확정값이 아닌 시작 설정안이다. fresh 시간과 메모리 보관 시간을 구분한다. fresh 시간 경과 자체가 자동 타이머 조회를 의미하지 않으며 화면 재진입·앱 복귀·명시적 갱신 시 재확인한다.

| 자료 | 최신으로 간주할 시간 | 갱신 원칙 |
|---|---|---|
| 이번 달 손익·오늘 매출 | 30초 | 저장값 먼저 표시, 오래됐으면 뒤에서 조회. POS 동기화·금액 수정 성공 시 즉시 재확인 |
| 과거 월 손익·월별 추세 | 5분 | 과거 자료 수정도 무효화. 과거라고 무기한 고정하지 않음 |
| 재고·청소·스케줄 | 15~30초 | 변경 성공·앱 복귀 시 갱신. 실패 시 이전값과 갱신 실패 구분 |
| 직원 목록·기본 설정 | 1~5분 | 직원 변경·최종 합류·권한 변경 시 갱신. 급여 포함 목록은 권한별로 분리 |
| 알림 | 15~30초 | 활성 화면에서 하나의 갱신 경로 사용. 읽음 처리 결과 즉시 반영 |

사용하지 않는 결과의 메모리 보관 시간은 우선 15분으로 두고 개수도 제한한다. 로그아웃·계정 변경·권한 회수 시 시간과 무관하게 제거한다. 정산 확정·급여 반영·최종 합류 같은 쓰기 작업은 서버에서 현재 상태·버전을 다시 검증하고, 캐시만 보고 승인하지 않는다.

### 캐시 식별과 수정 후 갱신

- 키: 로그인 사용자 + 권한/미리보기 범위 + 자료 종류 + 매장 + 대상 월/정확한 날짜 범위 + 계산 기준·마감시간 + 목록 필터·페이지. 요청 결과에 영향을 주는 값을 모두 포함한다.
- 같은 키의 진행 중 요청은 공유한다. 실패 응답은 정상 결과로 저장하지 않는다.
- 다른 매장·권한·기간의 결과를 임시 표시하지 않는다. 재조회 실패 시 남은 이전 자료에 확인 시각과 실패를 표시한다. 권한 거절은 캐시 표시도 중단한다.
- 수동 새로고침은 fresh 시간 제한을 무시한다. 이전 조회와 수정 후 조회가 엇갈리면 수정 전에 시작한 응답이 새 결과를 덮지 못하게 한다.
- 매입 변경: 해당 월 매입·손익·통합 합산·추세. 재고를 변경했다면 해당 재고도 갱신한다. 날짜 변경은 이전·새 월 모두 포함한다.
- 비용 변경: 해당 월 손익·합산·추세. 고정비는 이후 월에 이어질 수 있으므로 영향을 받는 후속 월도 포함한다.
- 급여·근무분·급여 조건·재직 상태 변경: 관련 급여·직원 목록·영향 월의 손익과 추세. 이력 소급과 현재 계산의 수습 판단을 고려해 현재 월 하나만 무효화하지 않는다.
- POS 동기화: 동기화된 날짜·월 요약·관련 손익·통합 합산·추세. 항목별 저장마다 전체 캐시를 갱신하지 않고 동기화 묶음 완료 후 갱신한다.
- 다른 기기에서 발생한 변경은 앱 복귀·화면 진입·제한된 갱신 주기로 확인한다. 당장 모든 테이블에 실시간 구독을 추가할 필요는 없다.

홈 요약과 상세 손익은 현재 다른 API·다른 결과 구조다. 키 이름만 같게 해서 공유하지 않는다. 공통 월 요약 계약을 정리한 뒤 요약·추세·합산이 같은 결과를 재사용하게 한다.

### 구현 선택과 순서

여러 hook의 캐시·재시도·무효화·요청 공유를 직접 관리하기보다 **TanStack Query 기반의 공통 조회 계층**을 추천한다. 기존 서비스는 DB 호출을 담당하고 기존 도메인 hook이 이를 감싸는 구조를 유지한다. 새 의존성은 아직 추가하지 않았다.

라이브러리 기본 staleTime은 0이므로 설치만으로 재조회를 줄였다고 볼 수 없다. 위 정책을 설정하고, React Native 앱 활성 상태와 현재 사용 중인 Pager의 `active` 상태를 연결해야 한다. [기본 캐시 동작](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults), [React Native 연동](https://tanstack.com/query/latest/docs/framework/react/react-native), [수정 후 무효화](https://tanstack.com/query/latest/docs/framework/react/guides/query-invalidation).

1. 자동 동기화 순환 제거·중복 요청 공유.
2. 홈·통합 대시보드의 월 요약 캐시와 영역별 표시.
3. 수정 경로의 무효화 연결, 기존 POS 디스크 캐시 정리, 사용자·권한 경계 확인.
4. 직원·재고·알림으로 점진 확장. 화면 재생성 제거는 범위 격리 검증 후 진행.
5. 최초 진입은 서버 일괄 집계로 개선. 이후에도 DB 실행 자체가 느린 부분만 인덱스·정책 튜닝.

합격 기준은 A → B → A 전환 시 A 자료 재사용, 6개월 범위 한 달 이동 시 겹치는 월 재사용, 동시 화면 조회 공유, 수동 새로고침 강제 갱신, 변경 직후 손익 반영, 로그아웃·권한 변경 후 이전 자료 차단이다. 최초 조회·재방문·수정 후 재방문의 요청 수와 표시 시간을 따로 측정한다.

### 우선 판단

### 먼저 처리할 데이터 정합성 사항

**급여 조건 이력이 없는 재직 직원 3명: 정규직 2명, 파트타이머 1명.**

현재 손익 계산은 정규직 급여를 `employee_wage_history`에서 읽으며 이력이 없으면 0으로 계산할 수 있다. 따라서 정규직 2명은 캐시·성능 작업보다 먼저 기존 자료와 대조할 대상이다. 과거 급여 조건·적용일은 확인하지 않았으므로 현재 기본급을 임의로 과거에 채우지 않았다. 파트타이머의 누락 영향은 적용 시급 조회 경로까지 별도 대조한다.

직원 생성 후 초기 급여 이력 저장은 `useEmployees.ts`에서 별도 요청으로 실행하고 실패를 `.catch(() => {})`로 삼킨다. 누락을 만들 수 있는 경로지만 원격의 누락 3건이 실제로 이 경로에서 발생했는지는 확인하지 않았다. 현재값과 유효 이력이 모두 있는 직원들 사이에는 금액 불일치 0건이었다. 이는 이력 누락 직원은 제외한 검사다.

추가 점검 결과:

- 부모·자식 매장 연결 불일치: 매입 품목·POS 품목·스케줄·급여 이력·급여·합류 신청·레시피 재료의 7개 검사 모두 0건.

분류·유형 테이블은 예를 들어 `store_purchase_types(id,store_id,name,sort_order,is_active)`와 `store_categories(id,store_id,domain,name,sort_order,is_active)` 형태다. `domain`으로 재고·매입처럼 의미가 다른 분류를 구분하고 매장·영역·이름 중복을 제한한다. 모든 시스템 고정 enum까지 같은 테이블로 옮기지는 않는다. 품목의 category ID와 매입 헤더 대표 category의 의미도 구분한다.

현재 `categoryTaxonomy.renameCategory`는 stores 목록 저장 후 대상 테이블 이름 변경을 별도 요청으로 수행한다. 중간 실패 시 분류 목록과 품목의 이름이 어긋날 수 있다. 삭제 시 연결 자료 이동 요청은 오류도 검사하지 않는다. 매입 유형 이름 변경은 RPC가 이미 원자적으로 처리하므로 같은 실패 구조라고 일반화하지 않는다.

카테고리 ID 전환 시 기존 이름을 매장·분류 영역별로 매핑하고, 기존 매입 유형 이름 변경이 과거 화면에도 반영되는 현재 제품 동작을 유지한다. 잘못된 이름을 자동 병합하거나 과거 품목 자체를 삭제하지 않는다.

### 정규화한다고 제거하면 안 되는 중복

- `payroll`의 적용 시급·세전 금액·공제·계산 버전: 정산 당시의 값이다. 현재 직원 급여와 조인해서 매번 재계산하면 과거 명세가 바뀐다.
- 매입·POS 상세의 이름·단가·옵션: 거래 당시 스냅샷이다. 현재 재고명·카탈로그 가격만 참조하도록 대체하지 않는다.
- `store_join_profiles`의 직원 제출 값과 관리자 검토본, 급여 변경 로그의 old/new JSON: 감사·검토 목적의 서로 다른 사실이다.
- 자식 테이블의 `store_id`: 부모로부터 유도 가능하지만 RLS·매장 범위 조회에 의도적으로 유용하다. 일괄 제거 대신 부모와 소속 일치를 보장한다. 복합 FK는 추가 UNIQUE 인덱스 비용도 있으므로 기존 트리거와 비교해서 선택한다.
- 직원의 계좌·연락처를 별도 제한 테이블로 분리하는 것은 접근 경계 설계다. 읽는 컬럼 선택·권한 정리로 충분하면 1:1 테이블을 늘릴 필요 없다.
- `schedule_requests.days`, POS 옵션·외부 원문, 감사 로그는 묶음 신청·스냅샷이면 JSON 유지 가능. 개별 값으로 검색·관계 검증할 실제 요구가 있을 때만 분리한다.
- 고정 세액표의 부양가족 열, 단위·고용형태 같은 고정 코드도 반복 열·문자열이라는 이유만으로 지금 전부 분리하지 않는다.

### View와 RPC 배치안

일반 View는 결과를 저장하는 캐시가 아니며 조회할 때 정의한 쿼리가 실행된다. View 이름만 붙이는 것으로 빨라진다고 볼 수 없다. [PostgreSQL CREATE VIEW](https://www.postgresql.org/docs/current/sql-createview.html)

| 후보 | 적합한 형태 | 줄일 수 있는 중복·조건 |
|---|---|---|
| 레시피 현재 원가·마진 | 공통 단위환산 함수 + recipe_costs View | 목록은 `recipeLineCost` 재계산, 상세 상단은 저장 cost·margin_rate 사용 중. 두 화면의 계산 기준을 통일 |
| 직원의 현재 유효 급여 조건 | employee_effective_wages View 또는 기준일 인자를 받는 함수 | 조회 시점 조건을 한곳에서 결정. 과거·미래 적용일 조회는 날짜 인자 함수가 명확 |
| POS 영업일별 매출·건수 | 완료 주문 필터·영업일 계산을 공유하는 View 또는 기간 RPC | 원본 주문을 앱으로 보내고 JS로 합산하는 중복 제거. 실제 기간 필터가 원본 인덱스까지 적용되는지 측정 |
| POS 날짜·상품별 매출 | 기간·매장 인자 RPC, 내부 공통 조인 | 주문 ID 목록 → 품목 → 카탈로그의 여러 요청을 서버에서 조인·집계. 현재 카테고리 보완 규칙과 당시 품목 스냅샷 유지 |
| 월별 매입·비용 분류 합계 | 분류·기간 집계 View 또는 내부 CTE | 분류 ID 정리와 함께 활용. 고정비 전월 이월은 단순 월합계와 별도 처리 |
| 홈·통합 월별 손익 | **여러 매장·월을 받는 집계 RPC** | 권한 확인·기간 필터·고정비 이월·급여 일할을 함께 처리. 1개월 RPC를 N번 부르는 것을 새 RPC 내부에 그대로 옮기는 것만으로는 부족 |
| 주간 청소·스케줄 | 매장·주간 범위 한 번 조회, 서버 또는 앱에서 묶기 | 현재는 요일·날짜마다 개별 요청. 한 번 조회만으로 충분하면 View를 새로 만들지 않음 |

레시피의 kg/g·L/mL·개당 용량 환산과 반올림은 기존 `recipeLineCost`를 기준으로 대조해야 한다. 레시피 원가는 현재 원가 용도와 스냅샷 용도가 확정되기 전 저장 컬럼을 삭제하지 않는다. 현재 원격 레시피는 148개이며 저장값과 계산값 차이의 실제 건수는 이번에 산출하지 않았다.

일반 직원은 자기 급여만 조회할 수 있으면서 매장 인건비 합계는 볼 수 있어야 한다. 따라서 직원 RLS를 그대로 따르는 View로 급여를 합산하면 본인 자료만 합산돼 틀릴 수 있다. 홈의 합계는 승인된 매장 구성원 권한을 검증하고 합계만 반환하는 기존 RPC 경계를 유지한다. 관리자 통합 조회는 대상 매장 모두의 관리자 권한을 확인한다.

직접 노출하는 View는 `security_invoker=true` 등으로 호출자의 권한을 적용하고 기본 테이블 RLS 의미를 유지한다. 내부 관리자 집계용 View는 노출하지 않고 검증된 함수에서만 사용한다. View를 통한 급여 원본 공개는 하지 않는다. [Supabase View 권한 지침](https://supabase.com/docs/guides/database/views)

Materialized View·집계 테이블은 지금 도입 우선순위가 낮다. 갱신·실패 복구·과거 정정·마감시간 변경·급여 조건 소급 처리 부담이 생기기 때문이다. 먼저 일반 집계와 요청 수를 줄인 뒤에도 비용이 크면 과거 영업일별 POS 집계부터 검토한다. 급여를 포함한 과거 손익은 현재 코드의 재직·수습 조건에 따라 달라질 수 있어 고정 자료로 취급하지 않는다. [Materialized View의 저장·갱신 특성](https://www.postgresql.org/docs/current/rules-materializedviews.html)

### 이번 단계의 실행 상태

원격 조회와 구조·코드 검토를 완료했고 보고서·건수 근거를 추가했다. View 생성, 테이블 분리, 이력 보정, 정책 변경, 새 마이그레이션 적용은 하지 않았다. 정규화에 따른 실제 속도 개선이나 모든 권한 조합은 구현 후 검증 대상이다.
