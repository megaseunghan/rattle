# 운영 입력 흐름 개선 — 2026-10-19

## 현재 상태

코드 작성·로컬 검증을 마쳤으며 **원격 Supabase에는 새 SQL을 적용하지 않았다.** 기존 DB의 개발·운영 구분도 아직 확인되지 않았다. DB 적용 전에 새 앱을 운영 배포하면 유형 조회·읽음 처리·근무시간 제출·참여 신청/승인에서 오류 안내가 나온다. 실제 계정 두 개를 이용한 저장·승인 검증과 실기기 검증은 남아 있다.

| 요청 | 반영 상태 |
|---|---|
| 매입 유형 추가·편집 | 매장별 유형 목록과 관리자 추가·이름 변경 화면 구현. 새 SQL 적용 필요 |
| 매입 등록 품목별 고정 | ‘금액만’ 선택 제거. 품목·수량·단가로만 신규 등록 |
| 파트타이머 본인 입력 → 관리자 확인 | 근무 분 제출·확인·반려·급여 반영을 구분해 구현. 새 SQL 적용 필요 |
| 토스 포스 메뉴 | 사용자 요청으로 이번 작업에서 제외 |
| 플로팅 버튼 미동작 | 탭/드래그 분리·접근성 버튼·저장 위치 복원·메뉴 위치 보완 |
| 직원 계정 연결 방법 변경 | 사업자번호로 참여 신청 → 관리자 승인 시 이름·휴대폰 번호로 직원 자동 연결. 새 SQL 적용 필요 |
| 재고 탭 품절 개수 → 홈 알림 | 하단 재고 숫자 배지 제거. 홈 상단에 품목별 품절/부족 안내 구현 |
| 사용자별 홈 알림 읽음 | 개인별 DB 읽음 기록·확인 후 숨김·실패 안내 구현. 새 SQL 적용 필요 |

## 매입 유형

- 매입 등록 → **유형 관리**에서 관리자가 유형을 추가하거나 이름을 변경한다.
- 이름 변경은 매장 유형 목록과 기존 매입 내역을 한 트랜잭션으로 갱신한다.
- 이름이 바뀐 유형을 오래 열린 다른 기기의 폼에서 저장하면 DB가 거부한다. 새로고침 후 현재 유형을 선택해야 한다.
- 유형은 앞뒤 공백을 제거한 1~40자이며 ‘전체’와 중복 이름은 허용하지 않는다.
- 유형이 많아져도 매입 탭에서 가로로 넘겨 선택할 수 있다. 기존 전자세금계산서 유형도 이력에 있으면 보존한다.
- 매입 카테고리(식자재·주류·비품)와 구매 유형(쿠팡·네이버·직접구매 등)은 별도다.

## 품목별 매입 등록

- 신규 수기 매입은 **품목 추가 → 수량·단가 입력 → 합계 확인 → 매입 등록**으로 고정한다.
- ‘금액만’ 전환과 카테고리별 금액 일괄 입력은 제거했다. 과거 금액만 등록한 이력은 보존한다.
- 품목이 없으면 등록 버튼이 비활성화된다. 품목별 등록은 기존 원자적 RPC를 사용해 금액·재고·최근 단가를 함께 반영한다.

## 직원 계정 자동 연결

### 직원이 신청하는 순서

1. 로그인 → **기존 매장 참여**로 들어간다.
2. 관리자에게 등록한 **이름·휴대폰 번호**, 매장의 **사업자번호 10자리**를 입력한다. 초대코드는 필요 없다.
3. **참여 신청** → 신청 완료 안내를 확인한다. 관리자 승인 전에는 매장 데이터 접근·직원 연결이 열리지 않는다.

사업자번호와 직접 입력한 이름·번호는 본인 인증을 대신하지 않는다. 관리자는 실제 직원의 신청인지 확인한 뒤 승인한다.

### 관리자가 확인하는 순서

1. **멤버 관리 → 승인 대기**에서 이름·휴대폰 번호를 실제 직원과 확인한다.
2. **승인**을 누르면 이름·정규화한 휴대폰 번호가 모두 일치하는 유일한 재직 직원에 로그인 계정만 연결한다. 기존 직원 ID·고용형태·급여·시급은 보존한다.
3. 이름과 번호가 전혀 겹치지 않는 신규 신청자는 새 직원으로 등록한다. 승인 완료 후 **인건비**에서 고용형태·시급·공제 등 급여 정보를 설정한다. 신규 직원의 DB 기본 고용형태는 정규직이므로 파트타이머라면 반드시 변경한다.
4. 이름/번호 일부만 일치하거나, 여러 재직 직원이 일치하거나, 퇴사 직원·다른 계정 연결 직원과 겹치면 승인을 취소하고 오류를 안내한다. 신청은 대기 상태로 남는다.
5. **직원 정보 확인**으로 인건비 화면을 열어 이름·번호를 맞춘 뒤 다시 승인한다. 중복 재직 직원은 올바른 직원만 재직 상태로 정리한다. 다른 계정에 이미 연결된 경우 기존 연결이 맞는지 별도 확인하며 자동으로 덮어쓰지 않는다.
6. 연락처가 없는 과거 신청, 신청자의 오타, 거절 후 재신청은 기존 신청/멤버를 제거한 뒤 직원이 다시 신청한다. 멤버 제거는 급여 이력을 삭제하지 않는다.

- 같은 사업자번호의 매장이 여러 개면 임의의 매장을 선택하지 않는다. 관리자에게 사업자번호 중복 등록 여부를 확인한다.
- 인건비 직원 편집의 수동 계정 선택 칩은 제거했다. 직원 정보 편집은 계정 연결 값을 전송하지 않아 승인 직후 오래 열린 폼이 연결을 지우지 않는다.
- 기존 승인된 멤버는 이 SQL만으로 소급 재연결하지 않는다. 기존 직원 중복·오연결은 실제 자료를 확인해 별도로 정리해야 한다.

## 파트타이머 근무시간

### 직원

1. 로그인된 계정이 관리자가 등록한 파트타이머 직원 정보에 연결돼 있어야 한다.
2. **홈 → 근무시간 제출**, 또는 **마이페이지 → 근무시간 제출**로 들어간다.
3. 대상 월을 선택하고 휴게시간을 제외한 총 실근무 분을 입력한다.
4. 분 단위 합계와 입력 근거를 적고 관리자에게 제출한다. 160시간은 9,600분, 미근무는 0분이다.
5. ‘관리자 확인 대기’ 표시를 확인한다. 반려 시 사유를 보고 수정 후 다시 제출한다.

직원은 시급·공제·최종 급여를 수정하지 않는다. 관리자 미리보기에서는 직원 명의 제출이 차단된다. 미입력과 실제 0분을 구분한다.

### 관리자

1. **인건비 → 파트타이머 근무시간 제출**에서 해당 월 제출 내역을 확인한다.
2. 제출한 근무시간을 확인한 뒤 **확인 후 급여 작성**을 누르거나 사유를 적어 **반려**한다.
3. 확인 완료 후에도 급여 금액은 바로 바뀌지 않는다. 근무시간 입력 폼에서 적용 시급·공제를 확인해 저장해야 급여에 반영된다.
4. 폼을 닫았다면 ‘확인 완료 · 급여 반영 대기’ 내역의 **급여에 반영**으로 다시 진행한다.
5. 급여 반영 완료와 정산 확정은 서로 다른 단계다. 최종 공제·실수령액 검토 후 정산한다.

- 제출 이력은 버전별로 남는다. 제출 대기 중 재제출하면 이전 제출은 ‘이전 제출’로 보존한다.
- 확인 후 재제출해도 승인 전에는 기존 급여 금액을 바꾸지 않는다. 기존 정산 확정은 해제하고 다시 확인을 요구한다.
- 최신 미확인 제출이 있으면 정산을 차단한다. 이전 제출 ID나 다른 근무 분을 연결해 급여를 저장하는 것도 차단한다.
- 최종 급여의 직접 수정은 DB에서도 관리자만 허용한다. 본인 제출 권한은 직원 계정 연결과 매장 참여 상태로 검사한다.
- 월급제 정규직의 월급 계산과 근무 분 선택 입력 정책은 그대로 유지한다.

## 홈 알림

- 하단 ‘재고’ 탭의 숫자 배지를 없앴다.
- 홈 상단에서 품목명과 ‘현재 품절 상태를 확인해 주세요’ 또는 남은 수량을 표시한다.
- 안전 수량이 0이어도 실제 수량이 0 이하이면 품절 안내를 만든다. 안전 수량이 0이고 재고가 남아 있으면 부족으로 표시하지 않는다.
- 품목 확인 또는 체크 버튼으로 읽음 처리한다. **로그인 사용자·매장·이벤트별로** DB에 기록하고 성공한 알림만 숨긴다.
- 다른 직원의 읽음 상태에 영향을 주지 않는다. 재고 기록이 갱신되면 새로운 이벤트로 다시 안내한다.
- 읽음 저장 실패 시 알림을 남기고 실패를 알린다. 저장 중 계정·매장을 전환하면 이전 알림으로 뒤늦게 이동하지 않는다.
- 매장 홈과 통합 홈 모두 반영했다. 통합 홈은 매장별 재고 알림, 매장 홈은 역할에 맞는 재고/고정비/매출/월말 알림을 제공한다.
- 기존 알림 센터의 매장 공용 `notifications.is_read`는 이번 개인별 홈 알림과 별도다.

## 플로팅 버튼

- 탭과 드래그 인식을 별도로 두어, 단순 탭이 드래그 취소로 처리되지 않게 했다.
- 접근성 버튼 이름과 직접 실행 동작을 추가했다.
- 기기에 저장된 위치를 복원할 때 메뉴에도 같은 좌표를 전달한다. 공유값을 쓰자마자 읽어 이전 좌표가 전달되던 경로를 제거했다.
- 메뉴가 화면 밖으로 나가지 않도록 위치를 제한하고, 메뉴를 다른 화면 내용보다 위에 배치했다.
- 시뮬레이터에서 메뉴 열기 → 매입 등록 이동과 최신 유형 관리 모달을 확인했다. 실제 매입·급여는 저장하지 않았다.

## DB 적용 전 확인

기존 `20261016_manual_work_minutes.sql`, `20261018_part_time_minutes_settlement.sql`의 적용 이력과 대상 DB를 먼저 확인한다. 이미 적용된 파일을 무조건 재실행하지 않는다.

새 파일:

1. `supabase/migrations/20261019_home_alert_reads.sql`
2. `supabase/migrations/20261019_purchase_types.sql`
3. `supabase/migrations/20261019_payroll_submissions.sql`
4. `supabase/migrations/20261019_member_employee_auto_link.sql` (3번 적용 후 실행)

검증용 DB와 백업을 확보한 다음 적용한다. 관리자 1명·파트타이머 2명으로 읽음 상태 분리, 본인 제출, 타인 제출 거부, 확인·반려, 급여 반영, 재제출·정산 해제를 확인한 뒤 앱을 배포한다. 신규 이력을 지우거나 RLS를 끄는 방식으로 복구하지 않는다. 실패하면 오류 원인을 확인하고 해당 변경을 수정한다.

## 검증 기록

- TypeScript: 통과.
- Jest: 20개 묶음, **125개 테스트 통과**.
- 로컬 PostgreSQL(PGlite): 기존 근무 분 마이그레이션과 새 SQL 실행 및 **50개 권한·동작 검사 통과**. 실제 Supabase 계정/운영 DB 검증을 대신하지 않는다. 단일 로컬 연결로 검사했으므로 실서버의 다중 연결 경합은 추가 확인 대상이다.
- 코드 리뷰: 유형 칩 넘침, 이전 유형 재생성, 알림 저장 뒤 오래된 화면 이동, 직원 조회 누락, 계정 탈퇴 FK 연결 해제, 확인 중 월 변경, 한국 시간 월초 기준 문제를 발견해 수정했다.
- 추가 검증: 참여 신청 대기·자기 승인 차단·기존 직원 급여/고용형태 보존·부분 일치/다른 계정/중복/퇴사 충돌·구형 승인/재참여·사업자번호 중복 거부를 로컬 SQL로 확인했다. 직원 목록 조회 실패/재시도·매장/계정 전환도 테스트했다.
- 추가 UI 확인: 시뮬레이터의 빠른 등록 → 매입 등록에서 ‘금액만’ 제거와 품목 없는 등록 비활성화를 확인했다. 새 참여 신청·승인 저장과 오류 복구 버튼의 실제 인건비 이동은 원격 SQL 적용 후 확인해야 한다.
- 추가 코드 리뷰: 오류 복구 버튼이 URL만 바꾸고 실제 인건비 pager를 선택하지 못하던 문제를 수정했다. 수정 후 TypeScript 리뷰에서 신규 결함은 발견되지 않았다.
- `git diff --check`: 통과.
- 원격 DB 적용·운영 배포·커밋: 실행하지 않음.

로컬 SQL 검증 재실행 예시:

## SQL 적용 요청

**Supabase에서 위 SQL 4개 적용을 진행해줘.** 기존 적용 이력과 개발/운영 대상을 확인한 뒤 위 순서대로 진행한다. 적용 후 참여 신청 → 관리자 승인 → 직원 연결 → 본인 근무시간 제출을 실제 테스트 계정으로 확인해야 운영 반영 완료다.

## 레시피 추가·매입서 스캔 제거 (추가 변경)

- **재고 → 레시피**를 선택하면 목록 상단에 **레시피 추가** 버튼을 항상 표시한다. 기존 레시피가 있어도 바로 새 레시피를 등록할 수 있다. 기존 레시피 관리 권한을 그대로 따른다.
- 매입서 스캔 버튼·카메라/앨범 선택·이미지 OCR 호출·검토 경로와 사용하지 않는 OCR 서비스/함수 소스를 제거했다. 매입은 품목별 직접 입력을 사용한다.
- 스캔 전용 이미지 패키지와 카메라 권한 플러그인도 제거했다. 설치된 기존 앱의 네이티브 권한 설정 변경은 다음 앱 빌드에 반영된다.
- 이번 추가 변경은 SQL 수정이 없다. 기존 매입·OCR DB 기록은 보존한다. 배포된 원격 OCR 함수의 삭제/배포는 실행하지 않았다. 앞서 준비한 SQL 4개의 미적용 상태와 적용 순서는 위와 같다.

- 이번 추가 변경 검증: 타입 검사 통과, OCR 전용 테스트 제거 후 남은 19개 묶음 111개 테스트 통과. 시뮬레이터에서 기존 레시피가 있는 목록의 추가 버튼 → 새 레시피 진입과 매입 화면의 스캔 버튼 제거를 확인했다. 실제 레시피/매입 저장은 수행하지 않았다.

## 기본 뒤로가기 헤더 정리

- 레시피 등록 화면에서 `(tabs)`가 표시되던 네이티브 스택 헤더를 제거했다. 앱 자체의 ‘취소 / 새 레시피 / 등록’ 헤더를 사용한다.
- 루트와 인증 스택의 기본 헤더 숨김 설정을 확인하고, 화면별로 기본 헤더를 다시 켜던 예외를 제거했다. 현재 존재하지 않는 `orders/new`, `orders/[id]`의 스택 선언도 정리했다.
- 이번 변경은 SQL 수정이 없다.
- 헤더 변경 검증: 전체 `app/`에서 기본 헤더 활성화 예외가 없는지 점검하고 타입 검사를 통과했다. 시뮬레이터에서 새 레시피 진입 시 `(tabs)` 기본 뒤로가기·중복 제목이 사라지고 기존 취소 버튼으로 목록에 복귀하는 것을 확인했다.

## 사용자 설명·오류 표시 정리

- 근무시간 입력·저장·정산 화면의 외부 도구 도입 및 대조 안내를 제거했다. 입력 예시는 ‘10월 근무 합계, 휴게시간 제외’로 바꿨다.
- 사용자에게 보여줄 입력 검증 오류는 `UserFacingError`로 구분한다. 알 수 없는 내부 오류는 짧은 실패/재시도 안내로 바꾼다. 서버에서 발생한 직원 연결·중복 신청·승인 충돌 등은 필요한 행동만 보여준다.
- 오류 원문은 내부 서비스 예외에서 유지하되 사용자 화면의 알림/오류 상태에서는 표시하지 않는다. 근무시간 작성·승인·급여 계산·이력·정산 해제 규칙은 유지한다.
- 이번 문구 변경은 SQL 수정이 없다. 기존 준비 SQL의 적용 여부는 별도다.
- 이번 문구 검증: 타입 검사 및 20개 묶음 116개 테스트 통과. 시뮬레이터를 새로고침한 뒤 파트타이머 미리보기의 근무시간 제출 화면에서 외부 도구 안내 제거와 새 입력 예시를 확인했다. 실제 제출·저장은 수행하지 않았다.
